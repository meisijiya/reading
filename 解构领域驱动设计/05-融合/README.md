> 📖 **原文**（§18 引言）：领域驱动统一过程的架构映射阶段对应解空间的战略设计，领域建模阶段对应解空间的战术设计。二者位于不同的设计层次，彼此之间又相互影响。

> 📖 **原文**（§18.1）：限界上下文对整个目标系统进行了纵向的业务能力切分，在限界上下文内部构成了自己的架构体系，是为菱形对称架构。

> 📖 **原文**（§18.1.1）：若限界上下文之间为进程内的通信方式，意味着它们的代码模型运行在同一个进程中，通过对象实例化的方式即可调用另一个限界上下文内部的对象。

> 📖 **原文**（§18.1.2）：数据库共享架构是一种折中的手段。划分限界上下文时，可能出现一种状况：代码的运行是进程分离的，数据库却共享彼此的数据，即多个限界上下文共享同一个数据库。共享数据库可以更加便利地保证数据的一致性，这或许是该方案最有说服力的证据，但也可以视为对一致性约束的妥协。

> 📖 **原文**（§18.1.2）：数据库共享架构可能传递“反模式”的信号。当两个分处不同限界上下文的服务需要操作同一张数据表（这张表被称为“共享表”）时，意味着设计可能出现了错误。

> 📖 **原文**（§18.1.3）：Fowler建议应该单体架构优先，通过该架构风格逐步探索系统的复杂度，确定限界上下文构成组件的边界，待系统复杂度增加，证明了微服务的必要性时，再考虑将这些限界上下文设计为独立的微服务。

> 📖 **原文**（§18.1.3）：一种审慎的做法是在无法明确微服务边界的合理性时，考虑将微服务的粒度设计得更粗一些，而在服务内部，通过限界上下文的边界对代码模型进行控制。

> 📖 **原文**（§18.2）：无论采用何种编程模式与框架来封装分布式通信，都只能做到让进程间的通信方式尽量透明，却不可抹去分布式通信固有的不可靠性、传输延迟性等诸多问题

> 📖 **原文**（§18.2.1）：一旦决定采用分布式通信，就需要考虑如下3个因素。

> 📖 **原文**（§18.2.2）：许多开发人员发现REST风格服务在分布式通信方面无法满足高并发低延迟的需求，HTTP/1.0的连接协议存在许多限制，以JSON为主的序列化既低效又冗长，这就为RPC带来了新的机会。

> 📖 **原文**（§18.3.1）：Bertrand Meyer认为：“一个方法要么是执行某种动作的命令，要么是返回数据的查询，而不能两者皆是。换句话说，问题不应该对答案进行修改。

> 📖 **原文**（§18.3.2）：CQRS模式做出的革命性改变是将模型分为命令模型和查询模型。

> 📖 **原文**（§18.3.5）：引入命令总线并不意味着必须引入事件，它仅仅改变了命令请求的处理模式。一旦CQRS模式引入了事件总线，它的设计与事件溯源模式更为匹配，就能够更好地发挥事件的价值。

> 📖 **原文**（§18.4.1）：Vaughn Vernon就认为：“通常来说，我们将事务放在应用层中。常见的做法是为每一组相关用例创建一个外观(facade)。外观中的业务方法往往定义为粗粒度方法，常见的情况是每一个用例对应一个业务方法。

> 📖 **原文**（§18.4.2）：CAP平衡理论是Eric Brewer教授在2000年提出的猜想，即“一致性、可用性和分区容错性三者无法在分布式系统中被同时满足，并且最多只能满足其中两个！”

> 📖 **原文**（§18.4.3）：如果将满足数据强一致性（即ACID）要求的分布式事务称为刚性事务，则满足数据最终一致性的分布式事务称为柔性事务。

> 📖 **原文**（§18.4.3）：可靠事件模式结合了本地事务与可靠消息传递的特性。当前限界上下文的业务表与事件消息表位于同一个数据库，因此，本地事务就能保证业务数据更改与事件消息插入的强一致性。

> 📖 **原文**（§18.4.3）：TCC模式根据业务角色的不同，将参与整个完整业务用例的分布式应用分为主业务服务和从业务服务。主业务服务负责发起流程，从业务服务执行具体的业务。业务行为被拆分为3个操作，即Try、Confirm和Cancel,这3个操作分属于准备阶段和提交阶段

> 📖 **原文**（§18.4.3）：Saga模式又称作长时间运行事务(long-running-transaction)，由普林斯顿大学的H. Garcia-Molina等人提出，可在没有两阶段提交的情况下解决分布式系统中复杂的业务事务问题。

> 🧭 **归纳**：第18章把"战略"具象化为四个相互交织的横切关注点：**限界上下文的物理边界**（进程内 vs 进程间）、**分布式通信机制**（REST / RPC / 事件）、**CQRS 与命令/事件总线**（查询端解耦 + 异步化）、**事务**（本地事务 → 分布式事务 → 柔性事务）。①**边界决定一切**——同一份遵循菱形对称架构的代码可在进程内运行（单体）也可跨进程运行（微服务），物理边界只影响"通信方式"，不影响"业务能力"；数据库共享与零共享是两条物理边界路线，前者便利一致但易传递反模式，后者彻底自治但代价是分布式问题。③**微服务 ≠ 限界上下文 1:1**——Fowler 主张"单体优先"，团队粒度和技术栈异化都可能让微服务粒度粗于或细于限界上下文；折中方案是"进程内限界上下文 + 粗粒度微服务"的混合架构。④**分布式通信三因素**：通信协议（TCP / HTTP / gRPC）、数据协议（JSON / Protobuf / Thrift / Avro）、接口定义（资源 / 行为 / 事件契约）；REST 友好跨平台但延迟欠佳、RPC 高性能但跨平台弱、事件消息彻底解耦但部署复杂。⑤**CQRS 是 CQS 的架构化**：当命令/查询的关注点差异大到无法共享同一模型时（同步 vs 异步、富UI vs 干净落库），拆为命令模型 + 查询模型，再按需引入命令总线（异步化）、事件溯源（聚合状态变更即事件）、事件总线（命令端→查询端完全解耦）；复杂度随引入项数指数上升，**慎用**。⑥**事务的金字塔**：进程内 = 本地事务（应用层 @Transactional = 工作单元）；跨进程且要求强一致 = X/A 二/三阶段提交（CAP 取 C 弃 A）；跨进程且允许最终一致 = 柔性事务——可靠事件（本地事务 + 事件表 + at-least-once 投递 + 幂等消费）、TCC（Try 预留 / Confirm 提交 / Cancel 补偿，业务级加锁替代 DB 级加锁）、Saga（协同式 via 事件 vs 编排式 via Saga 编排器，无 Try 阶段直接走补偿；ServiceComb Pack 提供协调者 Alpha + 拦截引擎 Omega 的封装）。一句话：**战略考量 = 在菱形对称架构的"代码模型不变"前提下，把进程边界、通信机制、命令查询分离、事务一致性这四类横切选择"有意识地"摆到网关层，让领域内核保持纯粹**。

## §19 第19章 领域驱动设计的战术考量

- **章节 UID**: 24
- **章节号**: §19
- **字数**: 31297
- **父模块**: 第五篇 融合
- **原文出处**: [`uid-24-领域驱动设计的战术考量.md`](../00-原书档案/fulltext/uid-24-领域驱动设计的战术考量.md)

> 📖 **原文**（§19 引言）：虽然领域驱动战术设计将关注重心放在“领域”上，但要让限界上下文的业务能力真正发挥出来，就得融合领域逻辑与技术实现，同时，又不能让技术复杂度影响到业务复杂度。

> 📖 **原文**（§19.1）：领域驱动设计引入了一套自成体系的设计概念：限界上下文、应用服务、领域服务、聚合、实体、值对象、领域事件以及资源库和工厂。

> 📖 **原文**（§19.1.1）：Plain Old Java Object(POJO)的概念来自Martin Fowler、Rebecca Parsons和Josh MacKenzie在2000年一次大会的讨论。它的本来含义是指一个常规的、不受任何框架、平台的约束和限制的Java对象。

> 📖 **原文**（§19.1.1）：Martin Fowler等人之所以提出POJO，是因为他们看到了“使用POJO封装业务逻辑的益处”，而2000年恰恰属于EJB开始流行的时代。

> 📖 **原文**（§19.1.1）：在领域驱动设计中，如果一个实体或值对象除内部字段之外只有一系列的getter/setter方法，即可被称为贫血对象。

> 📖 **原文**（§19.1.1）：有了Martin Fowler对贫血模型的创造，所谓的“血”就用来指代领域逻辑，故而有人在贫血模型的基础上衍生出各种与“血”有关的各种模型，如失血模型、充血模型和胀血模型。这些模型非但没有进一步将领域模型的正确定义阐述清楚，反而引入太多的概念造成领域模型的混乱不清。

> 📖 **原文**（§19.1.2）：Martin Fowler将其定义为：“用于在进程间传递数据的对象，目的是减少方法调用的数量。”

> 📖 **原文**（§19.1.2）：数据访问对象(data access object，DAO)对持久化对象进行持久化，实现数据的访问。它可以持久化领域模型对象，但对领域模型对象的边界没有任何限制。

> 📖 **原文**（§19.1.3）：通过对诸多设计概念的历史追寻与本质分析，我们理清了这些概念的含义与用途，将它们归纳到领域驱动设计体系中，得出设计统一语言如下。

> 📖 **原文**（§19.1.3）：领域模型必须是富领域模型。

> 📖 **原文**（§19.2）：领域驱动设计主要通过限界上下文应对复杂度，它是绑定业务架构、应用架构和数据架构的关键架构单元。

> 📖 **原文**（§19.2.1）：对象与关系往往存在“阻抗不匹配”的问题，主要体现为以下3个方面。

> 📖 **原文**（§19.2.2）：JPA作为一种规范，全面地考虑了各种阻抗不匹配的情形，规定了标准的映射元数据，如@Entity、@Table和@Column等Java注解。

> 📖 **原文**（§19.2.2）：无论是Address、Email还是EmployeeId类，在领域对象模型中虽然被定义为独立的类，但在数据模型中，却都是employees表中的列。

> 📖 **原文**（§19.2.3）：瞬态类属于领域模型的一部分。相较于聚合内的实体和值对象，它更加纯粹，无须依赖任何外部框架，属于真正的POJO类；它的设计符合整洁架构思想，即处于内部核心的领域类不依赖任何外部框架。

> 📖 **原文**（§19.2.4）：在进行领域建模时，一定是先有领域模型，后有数据模型！在定义了领域模型之后，将其映射为数据模型时，不能破坏限界上下文和聚合确定的边界。

> 📖 **原文**（§19.3）：资源库的实现取决于开发人员对ORM框架的选择。Hibernate、MyBatis、jOOQ、Spring Data JPA（当然也包括基于.NET的Entity Framework、NHibernate或Castle等）……每种框架自有其设计思想和原则，提供了不同的最佳实践来指导开发人员以更适宜的方式编写持久化实现。在领域驱动设计统一过程中，无论选择什么样的ORM框架，为聚合定义管理其生命周期的资源库

> 📖 **原文**（§19.3.1）：Repository类的内部使用了JPA的EntityManager管理实体的生命周期，提供了“增删改查”等持久化的基本方法。

> 📖 **原文**（§19.3.3）：领域设计模型以聚合为单位，对领域模型的持久化需要遵循“一个聚合对应一个资源库”的设计原则。

> 📖 **原文**（§19.3.3）：将工作时间卡添加到列表中，但不会在数据库中插入一条新的工作时间卡记录。聚合不操作数据库，与数据库打交道的只能是资源库适配器，这是明确规定的资源库角色构造型的职责。

> 📖 **原文**（§19.3.4）：领域模型不建议聚合依赖资源库，更不允许将持久化的职责分配给聚合。如果业务需求要求对聚合的状态变更进行持久化，就需要调用资源库。调用工作由领域服务完成。

> 🧭 **归纳**：第19章解决"领域层代码如何写才不会因为外部技术而腐化"的战术问题，三大主题：**统一语言、ORM 阻抗不匹配、资源库实现**。①**统一语言（§19.1）**——POJO ≠ Java Bean：POJO 重在"不依赖框架"，Java Bean 重在"反射可访问"；贫血模型 = 只有 getter/setter 的对象（反模式），富领域模型 = 封装数据 + 行为（领域模型唯一正确形式）；"失血/充血/胀血"是后人乱造的概念，应被 Martin Fowler 的二分法取代；DTO（消息契约）/ VO（视图模型）/ BO（领域对象，慎用）/ DO（领域对象 / 数据对象歧义）/ PO（持久化对象，理想为 PI）/ DAO（DDD 中被资源库取代）必须先在团队内约定简称指代，避免 VO/DO/PO 三种歧义。**结论：领域模型必须是富模型；远程服务/应用服务接口的消息契约遵循 DTO 模式；只有资源库，没有 DAO；事件存储独立于资源库持久化领域事件**。②**ORM 阻抗不匹配（§19.2）**——类型（枚举→@Enumerated(STRING)、日期→@Temporal / AttributeConverter、ID→值对象 + @EmbeddedId + Serializable + equals/hashCode）；样式（一对多→@OneToMany + JoinColumn；值对象集合→@ElementCollection + @CollectionTable，无主键，靠实体主键维系）；对象模式（嵌套组合→@Embedded + @Embeddable；继承→Single-Table / Joined-Subclass / Table-Per-Class 三策略，**继承主要用于多态，复用是次要价值**）。瞬态类（聚合外、不持久化、纯 POJO 的领域对象，如 Period）属于领域模型的"轻量成员"。**领域模型先于数据模型**，进程内→单库多表、进程间→多库多表，ORM 元数据改库映射即可，领域代码不变。③**资源库实现（§19.3）**——通用 Repository<E, ID> 封装 EntityManager 增删改查；端口接口（HourlyEmployeeRepository）+ JPA 适配器 = 菱形对称架构的南向网关；**一个聚合 = 一个资源库**，访问聚合内部实体只能通过聚合根，TimeCard 不能有独立 Repository；持久化是领域服务的职责（TimeCardService.submitTimeCard），不是聚合的职责——`submit()` 方法操作内存 List，不动 DB。**测试**——领域服务用 Mockito 隔离资源库，资源库实现用 *IT 集成测试（Maven failsafe 分离单测与集成测试）。一句话：**战术考量 = 在不污染领域层的前提下，把 ORM 框架、Java 平台规约（Java Bean / 序列化 / 反射）、持久化透明原则（PI）这些技术事实重新解释为"端口 + 适配器 + 消息契约"的统一语言**。

> 📖 **原文**（§20 引言）：经验之说，只可意会，不可言传，而领域驱动设计若只有凭借经验才能做好，就不能称为一套方法体系了。为此，我针对领域驱动设计存在的不足，通过固化领域驱动设计的过程，提供更为直接有效的实践方法，建立具有目的性和可操作性的研发过程，即领域驱动设计统一过程(domain-driven design unified process，DDDUP)。

> 📖 **原文**（§20 引言）：领域驱动设计是以领域为核心驱动力的设计方法，此乃其根本要旨，也可认为是运用领域驱动设计的最高准则。

> 📖 **原文**（§20.1）：什么是领域驱动设计的精髓？它体现为两个要素：边界与纪律。

> 📖 **原文**（§20.1.1）：无论从问题空间到解空间，还是从战略设计推进到战术设计，领域驱动设计一直强调的核心思想，就是对边界的界定与控制。

> 📖 **原文**（§20.1.1）：问题空间的两重边界属于分析边界。

> 📖 **原文**（§20.1.1）：领域驱动设计解空间的四重边界属于设计边界。

> 📖 **原文**（§20.1.1）：领域驱动设计问题空间的两重边界与解空间的四重边界可以保证系统的有序性。

> 📖 **原文**（§20.1.2）：ThoughtWorks的杨云就指出：“领域驱动设计是一种纪律,”他进一步解释道,“领域驱动设计本身没有多难，知道了方法的话，认真建模一次还是好搞的，但是持续地保持这个领域模型的更新和有效，并且坚持在工作中用统一语言来讨论问题是很难的。纪律才是关键。”

> 📖 **原文**（§20.1.2）：结合领域驱动设计的知识体系和统一过程，我总结了领域驱动设计的“三大纪律八项注意”，可作为团队的纪律规范。

> 📖 **原文**（§20.2）：领域驱动设计能力评估模型(domain-driven design capability assessment model，DCAM)是我个人对领域驱动设计经验的一个提炼，可以指导团队进行能力的培养和提升。

> 🧭 **归纳**：第20章是全书的"封顶"——把前 19 章的方法、模式、过程收敛成**一个可操作的体系**，关键词：①**精髓 = 边界 + 纪律**。**边界**有两层六重——问题空间两重分析边界（系统范围 + 子领域优先级）、解空间四重设计边界（系统上下文 + 限界上下文 + 网关层/领域层 + 聚合）；**纪律**有"三大纪律八项注意"——三大纪律：领域专家与开发团队在一起工作 / 领域模型遵循统一语言 / 时刻坚守两重分析边界与四重设计边界；八项注意覆盖问题空间/解空间不混、跨进程走远程服务、进程内走应用服务、领域模型不外泄、先领域模型后数据模型、聚合关联只用聚合根ID、聚合不依赖南向网关等"反模式禁令"。②**DCAM（能力评估模型）**——四维 × 三级（初始/成长/成熟）：敏捷迭代、需求分析、领域建模、架构设计；不绑定 DDDUP，可独立演化。③**参考过程模型（RPM）** = DDDUP 的可操作填充——全局分析（商业模式画布→价值需求 / 服务蓝图→业务需求 / 子领域分解）+ 架构映射（C4 系统上下文 + V型映射→限界上下文 + 上下文映射 + 服务契约 + 系统分层架构）+ 领域建模（业务服务规约→快速建模法→领域分析模型 → 庖丁解牛→聚合 + 服务驱动设计→领域设计模型 → TDD→领域实现模型）；每个阶段都规定了输入工件和输出工件。④**EAS 案例**——把 RPM 落到一个真实的中等规模 B 端系统：全局分析阶段先用商业模式画布识别"集团决策者"为最关键利益相关者，确立"避免信息孤岛、实现人力资源供需平衡"的愿景；再以服务蓝图 + 业务流程图划分客户合作、项目管理、培训三大流程下的若干业务场景，每个场景下识别业务服务（如"归档合同"、"提名候选人"、"分配票"），并通过统一语言工作澄清"订单/合同/市场需求/客户需求"的混淆。子领域分核心（决策分析、市场需求管理、客户关系管理、员工管理、人才招聘、技能培训、项目进度管理）/ 通用（组织结构、认证授权）/ 支撑（资源分配、消息通知、文件共享）。架构映射用 V 型映射（语义相关性 + 功能相关性 → 业务主体 → 亲密度分析 → 单一抽象层次 + 正交原则验证 → 工作边界 + 应用边界调整）；教训：①"员工"和"储备人才"知识语境不同，不应抽象合并；②OA集成应作为独立上下文（防腐层重复建设 → 单独上下文）；③报表上下文先拆后合（按业务相关性分配 → 因"决策分析"独立保留）。上下文映射阶段用服务序列图驱动出协作方式（订单/客户合同/项目成员都走应用服务；OA 集成走发布者/订阅者）。领域建模阶段以"提名候选人"业务服务规约为输入：识别名词得领域概念 → 快速建模法得领域分析模型 → 庖丁解牛得 13 个聚合（Training / Course / Ticket / TicketHistory / Filter / ValidDate / ValidDateAction / CancellingAction / Candidate / Attendance / Learning / Blacklist）→ 服务驱动设计得任务树 + 序列图脚本 → TDD 驱动 Ticket / TicketService 实现 → 资源库 MyBatis Mapper（端口注解 + Mapper XML）→ 应用服务 @Transactional + 集成测试 → 远程服务 REST 资源 + Resources 辅助类捕获三种应用异常 → 最终代码模型（message / northbound{remote, local, appservice} / domain{按聚合切包} / southbound{port, adapter}）清晰呈现菱形对称架构。⑤**架构演进**——遵循此代码模型后，单体架构与微服务架构拥有**完全相同的代码结构**，迁移只需 4 个动作：去 eas-entry 入口、改南向网关 client 适配器为跨进程通信、改数据库 URL、引入分布式柔性事务；领域层代码无需任何修改。⑥**总结**——"明其道、求其术"：DDD 方法体系是道，各种实践是术，道引导方向，术帮助走得更快更稳健；**这一切的基础是成熟的领域驱动设计团队**——DCAM 评估 → 针对性培养 → 提升四能力 → 推进 DDD 无往不利。一句话：**领域驱动设计体系 = 精髓（边界 + 纪律）+ 能力（DCAM 四维三级）+ 过程（RPM 三阶段流水线）+ 案例（EAS 全程示范），其最高准则是"领域为核心驱动力"，所有方法/模式/过程都必须为这条最高准则服务，否则就不是 DDD**。
