## 一、DDDUP 三阶段里程碑速查

| 阶段 | 输入工件 | 产出工件 | 关键活动 | 里程碑标志 | 章节锚点 |
|---|---|---|---|---|---|
| **全局分析** | 利益相关者诉求 | 价值需求 + 业务需求 | 5W 模型（Who/Why/Where/When/What）+ 统一语言 + 可视化协作 + 子领域划分 | 问题空间清晰，业务服务正交无歧义 | §4-§6 |
| **架构映射** | 全局分析规格说明书 | 系统上下文 + 限界上下文 + 上下文映射 + 菱形对称架构 + 分层架构 | 组织级（系统上下文）→ 业务级（限界上下文 + 上下文映射）→ 系统级（分层架构 + 领域驱动架构） | 解空间边界确定，演进路径（单体↔微服务）规划完毕 | §7-§12 |
| **领域建模** | 限界上下文 + 业务服务规约 | 领域分析模型 + 领域设计模型 + 领域实现模型 | 快速建模法 → 领域模型设计要素 → 服务驱动设计 → TDD | 三个模型同步、可运行、可演进 | §13-§17 |

## 二、场景 → 方法速查

### A. 复杂度诊断与 DDD 适用性

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 软件复杂度为什么涨 | 三成因：规模（指数级增长）+ 结构（质量属性 + 康威定律）+ 变化（过度设计↔设计不足） | §1.2-§1.3 | 🧭归纳 |
| DDD 三大控制着力点 | 规模 → 子领域 + 限界上下文（分而治之）；结构 → 分层架构（隔离业务 vs 技术）；变化 → 领域模型/聚合（封装+抽象） | §2.3 | 🧭归纳 |
| 何时引入 DDD | DDD 不是银弹——主要应对"领域"这一核心复杂度，技术复杂度交给专门团队"隔离"；适用于大规模、业务复杂的中大型软件系统 | §2.4 | 🧭归纳 |
| 我的团队该不该上 DDD | 看 DDD 现存四点不足（统一过程/需求分析/架构体系/建模方法）是否在你的团队是瓶颈 | §3.1 | 🧭归纳 |
| 三阶段无法割裂 | 全局分析→架构映射→领域建模，但每个阶段都规定里程碑和产出物，前一阶段评审通过才能进入下一阶段 | §3.2.1 | 🧭归纳 |

### B. 全局分析阶段（问题空间）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 问题空间怎么探索 | 5W 模型（Who=利益相关者 / Why=系统愿景 / Where=系统范围 / When=业务流程 / What=业务服务）+ hoW 不在问题空间故不纳入 | §4.1 | 🧭归纳 |
| 怎么避免"盲人摸象" | 三件套：可视化 + 统一语言 + 局外人破除"知见障" | §4.2 | 🧭归纳 |
| 业务需求层次与粒度怎么定 | 用"业务服务"作为基本单元——角色与目标系统的一次完整功能交互（服务价值 + 角色 + 执行序列），正交无歧义 | §6.2.2 | 🧭归纳 |
| 子领域三分类怎么用 | 核心子领域（核心资产/核心价值，让最有才能的人开发）+ 通用子领域（缺乏领域个性）+ 支撑子领域（为核心提供支撑但不通用） | §6.3.1 | 🧭归纳 |
| 子领域划分的方法 | 业务职能 / 业务产品 / 业务环节 / 业务概念 4 种功能分类策略 | §6.3.2 | 🧭归纳 |
| 利益相关者怎么分 | 按价值需求的影响方向：受益者（beneficiary，接受输出价值）+ 支持者（problem stakeholder，提供输入价值） | §5.1.2 | 🧭归纳 |
| 系统范围怎么划 | 界线（收敛性）+ 方向（开放性），手电筒光束比喻——当前状态 + 未来状态 = 资源框定范围 | §5.3 | 🧭归纳 |
| 视觉协作工具怎么选 | 价值需求 → 商业模式画布；业务流程 → 服务蓝图 + 业务流程图；需求可视化 → 用例图；宏观探索业务全景 → 事件风暴 | §4.3 | 🧭归纳 |
| 价值需求 vs 业务需求 | 价值需求 = 目标系统的纲领（利益相关者/系统愿景/系统范围）；业务需求 = 纲领的填充（业务流程/业务场景/业务服务） | §5.4 / §6.1 | 🧭归纳 |
| 全局分析阶段禁什么 | 排除技术负责人、开发人员等技术角色入场（除非他们能分清问题空间与解空间） | §6.3.3 | 🧭归纳 |

### C. 架构映射阶段（解空间战略设计）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 怎么识别限界上下文 | 4 维度：业务（语义/功能相关性）+ 验证（亲密度/正交原则）+ 管理（团队粒度/康威定律）+ 技术（质量属性/异化） | §9.3 + §20.3.3 | 🧭归纳 |
| 8 种上下文映射模式怎么选 | 客户方/供应方（上游主导）/ 共享内核（紧密协作）/ 遵奉者（下游被迫接受）/ 分离方式（无协作）/ 开放主机服务（公共 API）/ 发布语言（跨技术栈数据交换）/ 防腐层（隔离上游腐化）/ 大泥球（放弃识别） | §10 | 🧭归纳 |
| 防腐层什么时候用 | 下游通过防腐层隔离上游限界上下文可能发生的变化；也用于隔离当前限界上下文之外的外部腐化（菱形对称架构北向网关） | §10.2.1 + §12.1.6 | 🧭归纳 |
| 共享内核怎么用 | 两个限界上下文对模型的子集有共同依赖时，由两团队共同维护该子集——避免重复但增加协作成本 | §10.1.2 | 🧭归纳 |
| 服务契约怎么设计 | 面向资源（REST）+ 面向行为（RPC）两条路线；菱形对称架构北向网关 = 一个业务服务 = 一个服务契约 | §11 + §15.5 | 🧭归纳 |
| 限界上下文内部的架构怎么定 | 菱形对称架构（作者原创）：北向网关 = 端口（应用服务接口）+ 适配器；南向网关 = 端口（资源库/客户端/发布者）+ 适配器；领域层 = 纯粹 POJO | §12.1 | 🧭归纳 |
| 微服务边界怎么划 | Fowler 主张"单体优先"——微服务粒度可粗于或细于限界上下文；折中方案：进程内限界上下文 + 粗粒度微服务 | §18.1.3 | 🧭归纳 |
| 限界上下文物理边界怎么选 | 进程内通信（单体/DLL）/ 数据库共享（折中但易传递反模式）/ 进程间通信（微服务）；决策只影响"通信方式"，不影响"业务能力" | §18.1 | 🧭归纳 |
| 限界上下文之间的通信机制 | 三因素：通信协议（TCP/HTTP/gRPC）+ 数据协议（JSON/Protobuf/Thrift/Avro）+ 接口定义（资源/行为/事件契约）；REST 友好跨平台、RPC 高性能、事件消息彻底解耦 | §18.2 | 🧭归纳 |
| CQRS 什么时候用 | 当命令/查询的关注点差异大到无法共享同一模型时（同步 vs 异步、富 UI vs 干净落库）；慎用——复杂度随引入项数指数上升 | §18.3 | 🧭归纳 |
| 分布式事务怎么选 | 进程内 = 本地事务（@Transactional）；跨进程强一致 = X/A 二/三阶段提交（CAP 取 C 弃 A）；跨进程最终一致 = 柔性事务（可靠事件/TCC/Saga） | §18.4 | 🧭归纳 |

### D. 领域建模阶段（解空间战术设计）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 怎么快速建模 | 快速建模法 = 名词建模（业务服务规约中的名词 → 领域对象）+ 动词建模（识别动词是否产生时标对象）+ 归纳抽象（多比少好）+ 确定关系（多对多隐藏新概念如 OrderItem） | §14.2 | 🧭归纳 |
| 实体 vs 值对象怎么选 | 看业务对相等判断依据：值相等 → 值对象（建模第一选择，优先不变性）；身份相等 → 实体 | §15.3.1 | 🧭归纳 |
| 聚合边界怎么划 | 4 原则（完整性/独立性/不变量/一致性）冲突时独立性优先；小聚合优于大聚合；只有聚合根是访问聚合的唯一入口 | §15.4.4 | 🧭归纳 |
| 聚合内对象怎么引用 | 同一限界上下文优先用身份标识引用（OrderItem 持有 String productId 而非 Product 对象）；跨上下文通过防腐层/开放主机服务 | §15.4.5 | 🧭归纳 |
| 聚合怎么持久化 | 一个聚合 = 一个资源库；端口接口贴近业务命名（orderOf 而非 findById）；订单类资源库通常不暴露 remove() | §15.5.2 + §19.3 | 🧭归纳 |
| 领域服务什么时候用 | 聚合无法承担的领域逻辑（"最后选择"）；四种场景：变化方向与聚合不一致的纯行为、聚合间协作、聚合与端口协作、无状态领域行为 | §15.6 | 🧭归纳 |
| 领域事件怎么命名 | 动词过去时（OrderCompleted），继承 DomainEvent 抽象类，含 eventId + occurredOn；命名贴近业务而非技术 | §15.7.2 | 🧭归纳 |
| 角色构造型怎么映射 | Wirfs-Brock 职责驱动设计 → DDD 专属：聚合=信息持有者 / 领域服务=服务提供者+控制器 / 工厂=构造者 / 应用服务=协调者 / 远程服务+南向端口=接口 | §16.1 | 🧭归纳 |
| 服务驱动设计怎么走 | 两步：①任务分解（业务服务 → 组合任务 → 原子任务）；②职责分配（远程服务=业务服务 / 应用服务=业务服务 / 领域服务=组合任务 / 聚合=原子任务 / 端口=原子任务） | §16.3.4 | 🧭归纳 |
| TDD 怎么落地 | 红-绿-黄节奏（写失败测试 → 写最少通过代码 → 重构）；三定律：①只写刚好失败的测试 ②不写产品代码除非让失败的测试通过 ③只在测试全通过前提下做重构或加新功能 | §17.2.2 | 🧭归纳 |
| 简单设计四原则 | 重要度递减：通过所有测试 > 尽可能消除重复 > 尽可能清晰表达 > 更少代码元素（最后一条即奥卡姆剃刀） | §17.2.3 | 🧭归纳 |

### E. 战略与战术融合（限界上下文能跑起来）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 富领域模型 vs 贫血模型 | 实体/值对象必须有领域行为（封装数据 + 行为）；只有 getter/setter 是贫血模型（反模式） | §15.2.3 + §19.1.1 | 🧭归纳 |
| POJO / Java Bean / DTO 怎么分 | POJO = 不依赖框架的普通 Java 对象；Java Bean = 反射可访问；DTO = 进程间数据传递；领域层 = 富 POJO；网关层 = DTO | §19.1 | 🧭归纳 |
| ORM 阻抗不匹配怎么办 | 类型（枚举/日期/ID 值对象）+ 样式（一对多/值对象集合）+ 对象模式（嵌套组合/继承三大策略）；领域模型先于数据模型 | §19.2 | 🧭归纳 |
| 资源库接口命名 | 贴近业务而非技术——orderOf / save / remove（订单类通常不暴露 remove） | §15.5.2 | 🧭归纳 |
| 单体 ↔ 微服务怎么迁移 | 遵循菱形对称架构的代码模型迁移只需 4 动作：去 eas-entry 入口、改南向网关 client 适配器为跨进程通信、改数据库 URL、引入分布式柔性事务；领域层代码无需任何修改 | §20.3.5 | 🧭归纳 |

## 三、关键概念与数字

| 概念 | 含义 | 章节锚点 |
|---|---|---|
| **DDDUP 三阶段** | 全局分析 → 架构映射 → 领域建模；每个阶段有里程碑和产出物；不可跨越 | §3.2.1 / §3.2.2 |
| **5W 模型** | Who=利益相关者 / Why=系统愿景 / Where=系统范围 / When=业务流程 / What=业务服务；hoW 属于解空间不纳入 | §4.1 |
| **业务服务三要素** | 服务价值 + 角色（用户/策略/伴生系统，必须主动触发）+ 执行序列（连续且不可中断） | §6.2.2 |
| **子领域三分类** | 核心子领域（核心资产/核心价值）+ 通用子领域（缺乏领域个性）+ 支撑子领域（为核心提供支撑但不通用） | §6.3.1 |
| **系统上下文** | 目标系统 + 利益相关者 + 伴生系统的关系图，确定解空间边界 | §8 |
| **限界上下文四要素** | 领域模型的知识语境 + 业务能力的纵向切分 + 自治的架构单元 + 团队工作的边界 | §9.2 |
| **限界上下文识别四维度** | 业务（语义/功能相关性）+ 验证（亲密度/正交原则）+ 管理（团队粒度/康威定律）+ 技术（质量属性/异化） | §9.3 / §20.3.3 |
| **8 种上下文映射** | 客户方/供应方 + 共享内核 + 遵奉者 + 分离方式 + 开放主机服务 + 发布语言 + 防腐层 + 大泥球 | §10 |
| **菱形对称架构** | 北向网关（端口 + 适配器）+ 领域层（纯粹 POJO）+ 南向网关（端口 + 适配器）；对称结构统一端口和适配器 | §12.1.4 |
| **领域模型三模型分立** | 领域分析模型（粗略，面向开发团队+领域专家）/ 领域设计模型（精细，面向软件设计人员）/ 领域实现模型（可运行，面向开发人员） | §13.3.3 |
| **设计要素七元模型** | 实体 + 值对象 + 聚合 + 工厂 + 资源库 + 领域服务 + 领域事件 | §15 |
| **聚合四原则** | 完整性 / 独立性（最高）/ 不变量 / 一致性；冲突时独立性优先 | §15.4.4 / §16.2.3 |
| **聚合最高原则** | 只有聚合根才是访问聚合的唯一入口；外部对象不能引用除根实体之外的内部对象 | §15.4.4 |
| **一个聚合 = 一个资源库** | 聚合根资源库管理增删改查；不能为内部实体单独建资源库 | §15.5.2 / §19.3.3 |
| **领域事件命名规则** | 动词过去时（OrderCompleted），无须 +Event 后缀 | §15.7.2 |
| **服务驱动设计两步** | 任务分解（业务服务 → 组合任务 → 原子任务）+ 职责分配 | §16.3.4 |
| **角色构造型 6 类** | 信息持有者（聚合）/ 服务提供者+控制器（领域服务）/ 构造者（工厂）/ 协调者（应用服务）/ 接口（远程服务+端口） | §16.1 |
| **TDD 三定律** | ①只写刚好失败的测试 ②不写产品代码除非让失败的测试通过 ③只在测试全通过前提下做重构或加新功能 | §17.2.2 |
| **FIRST 测试五原则** | Fast（快速）/ Isolated（独立）/ Repeatable（可重复）/ Self-verifying（自我验证）/ Timely（及时） | §17.1.3 |
| **简单设计四原则** | 通过所有测试 > 尽可能消除重复 > 尽可能清晰表达 > 更少代码元素 | §17.2.3 |
| **分布式通信三因素** | 通信协议（TCP/HTTP/gRPC）+ 数据协议（JSON/Protobuf/Thrift/Avro）+ 接口定义（资源/行为/事件契约） | §18.2 |
| **分布式事务三类** | 进程内 = 本地事务；跨进程强一致 = 刚性事务（2PC/3PC）；跨进程最终一致 = 柔性事务（可靠事件/TCC/Saga） | §18.4 |
| **三大纪律** | 领域专家与开发团队在一起工作 / 领域模型遵循统一语言 / 时刻坚守两重分析边界与四重设计边界 | §20.1.2 |
| **六重边界** | 问题空间两重（系统范围 + 子领域优先级）+ 解空间四重（系统上下文 + 限界上下文 + 网关层/领域层 + 聚合） | §20.1.1 |
| **DDD 魔方三轴** | X 轴=业务/技术/管理 × Y 轴=全局分析/架构映射/领域建模 × Z 轴=方法/模式/工件 | 附录C.2 |
| **DCAM 四能力** | 敏捷迭代 + 需求分析 + 领域建模 + 架构设计；每能力分初始/成长/成熟三级 | §20.2 |
| **领域事件四要素** | eventId（全局唯一）+ occurredOn（事件发生时间）+ 事件名（动词过去时）+ 数据载体（值对象/数据传输对象） | §15.7.2 + 附录B |
| **函数范式三特征** | 模块化 + 抽象化 + 可组合（Ken Scambler） | 附录A.3 |
| **事件溯源两原则** | 聚合每次状态变化都是一个事件的发生 + 事件不变以追加方式记录到事件日志 | 附录B.2 |
| **事件溯源三个要素** | 事件存储（持久化事件）+ 快照表（定期 JSON 序列化聚合）+ 聚合资源库（封装事件溯源底层） | 附录B.2.3 / 附录B.2.4 |
| **CQRS 起源** | 事件溯源仅支持主键查询 + 需要复杂查询 → 事件与聚合的分离 = 命令与查询的分离 = CQRS 的初衷 | 附录B.2.5 |

## 四、技术选型对照

| 决策点 | 对照项 | 结论 | 章节锚点 |
|---|---|---|---|
| 跨限界上下文同步查询怎么办 | 跨进程同步查询（强耦合）/ 跨进程异步查询（事件流缓存） | 引入事件流：本地缓存上游数据 → 跨查询变本地查询 → 限界上下文彻底自治 | 附录B.3.2 |
| 限界上下文 vs 微服务粒度 | 1:1 对应 / 粗于微服务（进程内限界上下文）/ 细于微服务（多个微服务共用上下文） | 单体优先（微服务粒度可粗于限界上下文），根据技术栈异化与团队粒度决定 | §18.1.3 |
| 上下文消息格式 | 文本（JSON/XML）vs 二进制（Protobuf/Thrift/Avro） | 跨平台首选文本（JSON）；同构内部首选二进制（Protobuf） | §18.2.2 |
| RPC vs REST | 面向行为（RPC）/ 面向资源（REST） | 内部微服务追求极限性能或事务一致性 → RPC；面向公网开放接口 → REST | §11.2.2 / §18.2 |
| 限界上下文进程边界 | 进程内通信 / 数据库共享 / 进程间通信 | 三选一：进程内（单体/DLL）/ 数据库共享（折中但易传递反模式）/ 进程间（微服务） | §18.1 |
| 限界上下文协作模式 | 编排（中心控制器）/ 协同（发布订阅事件） | 协同更松耦合；唯一耦合点是事件；纯事件驱动架构需慎用，复杂场景不直观 | 附录B.3.1 |
| 限界上下文内部架构 | 六边形架构 / 分层架构 / 整洁架构 / 菱形对称架构 | 菱形对称架构强调"对称"特质（北向网关 ↔ 南向网关 ↔ 领域层），更清晰体现端口-适配器 | §12.1 |
| 事件溯源持久化 | 持久化聚合 / 持久化事件 / 混合（事件 + 聚合快照） | 事件溯源持久化事件；复杂查询通过聚合快照 = CQRS 起源 | 附录B.2.5 |
| 建模范式选择 | 结构范式（过程式）/ 对象范式（OOP）/ 函数范式（FP）/ 事件范式 | DDD 推荐对象范式（主流生态）；函数范式与事件驱动天然契合（ADT + 纯函数 + 状态机） | 附录A |
| 事务一致性取舍 | ACID 强一致 / 柔性最终一致 / 不管 | 跨进程按业务容忍度选：金融核心强一致；电商订单最终一致；日志分析无需事务 | §18.4 |
| 服务粒度（领域 vs 应用 vs 远程） | 应用服务 vs 远程服务 vs 领域服务 | 应用服务=协调者（不含业务逻辑）；远程服务=对外契约（不含业务逻辑）；领域服务=封装领域行为（含业务逻辑） | §16.1.1 / §16.3.4 |
