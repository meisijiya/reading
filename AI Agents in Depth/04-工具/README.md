# 第四章 工具

> Agent 的"手脚"——把语言大脑与数字世界连起来。本章从五类工具总览 → 通用设计原则 → MCP 协议 → 感知/执行/协作 → 事件驱动异步 → 主动工具发现。

## Q4-1 工具的五大分类是什么？两轴审视法

- 章节: ch005 §4.1
- 主题: 工具分类

> 📖 **原文** (ch005 §4.1)： 第一章介绍了 Agent 的五类工具（感知、执行、协作、事件触发、用户沟通）。为了帮助理解这五类工具的设计差异，可以从两个特征来审视它们： **调用方向** （这次交互由谁发起）和 **作用对象** （这次交互作用于什么）。

🧭 **归纳**：

| 工具类型 | 调用方向 | 作用对象 | 示例 |
|---|---|---|---|
| **感知工具** | Agent 主动调用 | 获取信息 | web_search、knowledge_base_search、fetch_url、find_file、grep_file、read_file |
| **执行工具** | Agent 主动调用 | 改变世界 | shell_exec、code_interpreter、write_file、edit_file、send_email |
| **协作工具** | Agent 主动调用 | 驱动其他 Agent 或人类 | spawn_subagent、send_message_to_subagent、list_agents |
| **用户沟通工具** | Agent 主动调用 | 向用户传递信息 | reply_to_user、send_card_to_user、send_user_notification |
| **事件触发工具** | Agent 注册、外部触发 | 驱动 Agent 开始执行 | set_timer、monitor_shell、connect_channel |

➕ **补充**：前四类 Agent 主动调用；第五类涉及"注册/触发"两个时刻——是 Agent "在线"能力的根源。

## Q4-2 工具能力应该用专用工具还是 Skill + 通用执行器？

- 章节: ch005 §4.2.1
- 主题: 能力表达形态选择

> 📖 **原文** (ch005 §4.2.1)： Agent 的能力有两种基本的表达形态： **专用代码工具** ：结构化的函数调用，确定性高、可测试，但每个工具会占据数百个 token，且数量膨胀会破坏 KV Cache。 **Skill + 通用执行器** ：用自然语言编写的 Skill 文档来描述操作流程，Agent 通过终端或代码解释器来执行，只需少量的通用工具就能覆盖大量场景（如第五章将论证的七个核心工具）…… **选择哪种形态取决于三个维度** 。 **参数复杂度** …… **变更频率** …… **模型能力** ……

🧭 **归纳**（三维度选择）：

| 维度 | 选专用工具 | 选 Skill + 通用执行器 |
|---|---|---|
| 参数复杂度 | 嵌套对象/多字段联合校验 | 简单参数（CLI 传参） |
| 变更频率 | 稳定底层操作 | 频繁变化（改文本比改代码省事） |
| 模型能力 | 弱模型（需结构化 schema 引导） | SOTA 模型（自主用代码编排） |

## Q4-3 工具粒度怎么定？功能相似性 + 使用场景重叠度

- 章节: ch005 §4.2.2
- 主题: 粒度权衡

> 📖 **原文** (ch005 §4.2.2)： 当工具数量过多时（比如超过 100 个），即使是最先进的大语言模型也容易在工具选择上出错。 **判断是否应该整合的核心标准是功能相似性和使用场景的重叠度** 。以文档处理为例 …… 更好的设计是提供一个统一的 read_document 工具，通过 file_type 参数来区分格式。整合 **降低了 LLM 的认知负担** …… 但并非所有工具都应整合——例如图片解析（OCR）和视频解析（关键帧提取）虽然都是"内容提取"，但参数形态、延迟特性差异很大 ……

🧭 **归纳**：整合标准 = 功能相似性 + 使用场景重叠度。例外：参数集差异大 / 高频工具应保持独立。

## Q4-4 工具描述的核心原则：边界比能力更重要

- 章节: ch005 §4.2.4
- 主题: 工具描述

> 📖 **原文** (ch005 §4.2.4)： **工具描述的核心是让 LLM 知道"什么时候用"，而不只是"能做什么"** …… **清晰列出工具的边界条件——做不到什么、不接受什么输入——往往比描述能力本身更重要** ，因为大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做到什么 …… **加入示例后，工具调用的准确率往往明显提升** ——在一些基准上可从约 72% 提升到 90% …… 当 Agent 频繁选错工具时，应 **优先检查工具描述** 而不是怀疑模型能力。

🧭 **归纳**（工具描述四要素）：
1. **何时用**（路由条件），不是"能做什么"
2. **边界条件**（做不到什么 + 不接受什么输入）——比能力描述更关键
3. **具体参数示例**（E.164 格式 + "+8613888888888" 比单写"RFC3339 格式"有效得多）
4. **1-5 个真实调用示例**——JSON Schema 描述不了"时间戳是秒还是毫秒"等隐式约定

**调试铁律**：选错工具时**先查描述**再换模型。准确率可从 ~72% 提升到 ~90%。

## Q4-5 参数传递的保真性原则：静默输入转换是反模式

- 章节: ch005 §4.2.5
- 主题: 保真性

> 📖 **原文** (ch005 §4.2.5)： 一种比功能缺失更隐蔽的反模式是 **静默输入转换** ——工具在执行前悄悄地"修正"模型的输入参数 …… **模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差** 。工具的参数传递必须保持透明，不得在模型不知情的情况下修改输入或输出 ……

🧭 **归纳**：
- **静默输入转换**（如 Cursor 旧版把弯引号改直引号）→ 模型看到的 ≠ 文件里的 → 反复失败无法自诊
- **静默参数注入**（如某 IDE bash 工具自动加 `git commit` 标记参数）→ 旧版 Git 不识别 → 报莫名错误
- **铁律**：模型所见与工具所操作必须一致；如需规范化必须在描述中说明 + 返回中告知

## Q4-6 工具设计的三代演进是什么？

- 章节: ch005 §4.2.6
- 主题: 设计演进

> 📖 **原文** (ch005 §4.2.6)： 第一代 是直接的 API 封装 …… **第二代** 是本节讨论的 ACI（Agent-Computer Interface）原则——工具应该对应 Agent 的目标而非底层的 API 操作 …… **第三代** 在单个工具的设计之上，进一步优化工具被调用、串联和发现的方式 ……

🧭 **归纳**：

| 代 | 关注点 | 范式 |
|---|---|---|
| **第一代** | API 封装 | 一个端点 = 一个工具（粒度过细） |
| **第二代** | ACI（Agent-Computer Interface） | 工具对应 Agent 目标（粒度权衡/通用性/描述） |
| **第三代** | 调用/串联/发现 | 示例驱动调用 + 动态工具发现 + 代码编排执行（让模型一次性写脚本，返回最终结构化结果，token 降约两个数量级） |

## Q4-7 MCP 是什么？MCP 在大规模工具下的三大挑战

- 章节: ch005 §4.3
- 主题: MCP 协议

> 📖 **原文** (ch005 §4.3)： **Model Context Protocol（MCP）** 是 Anthropic 于 2024 年底发布的开放标准，旨在统一 AI 模型与外部工具、数据源之间的通信协议 …… **一次开发，处处可用** 。一个 MCP 服务器可以同时被 Cursor、Claude Desktop、OpenClaw 等任何兼容的客户端使用 …… **MCP 在实践中面临三个递进的挑战** ——同步调用的限制、工具过多时的上下文开销、以及如何将工具能力沉淀为可复用的知识。

> 📖 **原文** (ch005 §4.3)： 仅仅 5 个 MCP 服务器就可能引入数万 token 量级的工具定义开销（约 55,000 token，视具体服务器而定），在 200K 的上下文窗口里还没开始对话就用掉了近三成 …… 一种缓解方案：将工具描述同步到文件夹中，Agent 默认只看到工具名称的索引，需要时再查询具体的定义 …… **使 MCP 工具相关任务的总 token 消耗减少了 46.9%** ……

🧭 **归纳**（MCP 三大挑战）：

1. **同步调用限制**：协议支持多轮交互/订阅/长任务，但跨会话/多事件源/离线唤醒需在协议之上另行构建
2. **工具过多上下文开销**：5 个服务器 ≈ 55K token（占 200K 窗口近三成）→ 工具描述文件化（只暴露名称索引）→ 总 token 降 46.9%
3. **能力沉淀为可复用知识**：与 Skills 体系结合（详见 Q4-8）

➕ **补充**：Cursor A/B 测试：工具描述文件化 → token -46.9%。Anthropic 动态工具发现 → Opus 4 工具使用准确率 49% → 74%。

## Q4-8 怎么管理"工具规模成百上千"的问题？两种思路

- 章节: ch005 §4.3（尾部）
- 主题: 工具规模管理

> 📖 **原文** (ch005 §4.3)： 层次化组织与动态工具发现。除了按需加载工具描述，当工具的数量增长到上百个时，层次化的组织方式也比扁平列表更有效。一种有效的方式是 **按信息源的性质分类** ：- 搜索工具：主动查找信息（网络搜索、知识库搜索、文件搜索）；- 读取工具：从已知位置提取内容（网页阅读、文档读取、数据库查询）；- 解析工具：处理非结构化数据（图片 OCR、视频分析、音频转录）；- 查询工具：访问结构化数据源（天气 API、股票 API、公开数据库）。在系统提示词中显式说明分类结构，可以帮助 LLM 快速定位到相关的工具组。更进一步的方案是前文"工具设计的演进"预告的 **动态工具发现** ：不把全部工具定义一次性注入上下文，而是让 Agent 通过搜索按需发现工具定义。**Anthropic 的实验显示，这种按需检索的方式使 Opus 4 在工具使用基准上的准确率从 49% 提升到 74%** 。

🧭 **归纳**：

| 思路 | 做法 | 效果 |
|---|---|---|
| **层次化分类** | 搜索/读取/解析/查询四大类写在系统提示词 | 帮助 LLM 快速定位 |
| **动态工具发现** | 不一次性注入，按需检索工具定义 | Opus 4 准确率 49% → 74% |
| **代理工具**（如 pi-mcp-adapter） | 模型默认只看到 ~200 token 代理；按"搜索→查看定义→调用"发现 | MCP 服务器延迟到首次使用才启动 |

## Q4-9 执行工具的安全设计：隔离 + 幂等 + 预检-确认

- 章节: ch005 §4.5
- 主题: 执行工具安全

> 📖 **原文** (ch005 §4.5)： 真正的隔离依靠操作系统及更底层的机制，按隔离强度递增排列： **进程级隔离** …… **容器隔离** …… **microVM/虚拟机** …… 容器和 microVM/虚拟机隔离层次应设置 CPU、内存、磁盘、网络的使用上限 …… **Python 虚拟环境（venv）不是沙盒** …… 在 venv 中运行的代码照样可以删除任意文件、访问任意网络。

> 📖 **原文** (ch005 §4.5)： 发送邮件、拨打电话、对外转账 这类操作，每执行一次就产生一个不可撤销的真实世界事件。对这类 **不可幂等** 的操作，应采用 **"预检-确认"两段式** ……

🧭 **归纳**：

**隔离层级（递增）**：
1. 进程级（Claude Code/Codex/OpenClaw 本地执行）
2. 容器（Docker，独立文件系统+网络栈，共享内核）
3. microVM/虚拟机（Firecracker，独立内核，最强隔离）

**幂等性**：
- 可幂等 → 携带唯一标识去重；或"先查询后变更"
- **不可幂等**（邮件/电话/转账）→ "预检-确认"两段式：预演→令牌→凭令牌真执；失败不盲目重发

**反模式**：
- venv ≠ 沙盒（只隔离包依赖）
- 长输出必须截断 + 引导读文件（不能塞爆上下文）

## Q4-10 子 Agent 提示词的四要素是什么？

- 章节: ch005 §4.6
- 主题: 子 Agent 协作

> 📖 **原文** (ch005 §4.6)： 子 Agent 提示词的关键要素。**角色定义要清晰**。开门见山说明"你是专门负责 XXX 的助手 Agent"。**上下文来源要明确标注**。子 Agent 可能接收来自多个来源的信息。提示词中应该明确区分各个来源：" [FROM_MAIN_AGENT] 是主协调 Agent 给你的任务指令； [FROM_USER] 是用户直接补充的信息； [TOOL_RESULT] 是你调用工具后的返回结果"。这种标注可以防止子 Agent 混淆信息来源，避免**提示注入**（前文 Sidecar 一节已介绍）攻击。**任务边界要明确界定**。什么在职责范围内，什么需要转交或上报。**输出格式要标准化**。无论使用 JSON 还是 Markdown 格式，都要在提示词中明确子 Agent 的输出格式，这可以保证子 Agent 考虑了所有需要考虑的方面，可以降低主 Agent 的解析负担，也使错误处理更加可靠。

🧭 **归纳**（子 Agent 提示词四要素）：
1. **角色定义清晰**——开门见山"你是专门负责 XXX 的助手 Agent"
2. **上下文来源明确标注**——`[FROM_MAIN_AGENT] / [FROM_USER] / [TOOL_RESULT]` 防提示注入
3. **任务边界明确**——什么在职责内、什么需转交
4. **输出格式标准化**——JSON/Markdown 固定格式；降低主 Agent 解析负担

➕ **补充**：协作工具三组原语——启动与取消（spawn/cancel）/ 消息传递（send_message）/ 发现（list_agents）。HITL（人在回路）需设置超时+默认行为+优先级队列+反馈循环（详见 Q4-12）。

## Q4-11 事件驱动的异步 Agent 架构：为什么需要？核心矛盾

- 章节: ch005 §4.7
- 主题: 异步架构

> 📖 **原文** (ch005 §4.7)： 传统的同步 Agent 架构就像一个只会排队的柜台，每次只能处理一个顾客 …… 而异步范式落地到当前 LLM 时遭遇的根本矛盾在于： **LLM 的训练范式假设同步——发出工具调用后，下一条消息必须是工具结果；而真实部署却要求异步** …… 这一 **"训练同步 / 部署异步"** 的矛盾贯穿了本节后续讨论的所有工程取舍。

> 📖 **原文** (ch005 §4.7)： 真正的 **"主动服务"** 不仅需要 Agent 能定时检查世界，更需要 **世界能主动通知 Agent** 。将所有输入——用户消息、工具返回、外部回调、定时触发—— **统一建模为事件流** ，通过事件循环驱动 Agent 的思考和行动，是实现这一目标的架构基础。

🧭 **归纳**：
- 同步 = "做一件再做下一件"；异步 = "多件同时进行，按优先级调度 + 中断恢复"
- **核心矛盾**：训练假设同步 vs 部署要求异步
- **解决思路**：所有输入统一建模为事件流 → 事件循环驱动 Agent
- **三类内置事件驱动机制**（OpenClaw）：Hooks（生命周期）/ Cron（定时）/ Heartbeat（轮询）
- **短板**：内置机制都是时间驱动，第三方事件源（邮件到达/外部 API 回调）只能等下个周期——这就是 Channel 机制要解决的事

## Q4-12 事件触发工具 + 用户沟通工具有哪些设计要点？

- 章节: ch005 §4.7.3-4.7.4
- 主题: 事件/沟通工具

> 📖 **原文** (ch005 §4.7.3)： 在设计层面，事件触发工具应定义**清晰的触发条件和过滤规则**，避免无关事件唤醒 Agent 浪费算力；**事件载荷（payload）应包含足够的上下文信息**，减少 Agent 被唤醒后还需要额外查询的次数。事件触发工具是外部事件驱动 Agent 行动的入口。如果没有事件触发工具，Agent 只能连续循环思考、调用工具，最后输出一个结果，然后等待用户的下一步输入。

> 📖 **原文** (ch005 §4.7.4)： OpenClaw 打破了这一人机沟通范式 …… OpenClaw 并不是直接把模型输出的 assistant 消息输出给用户，而是使用专门的工具发送消息 …… 很多 Agent 已经开始尝试 **生成式 UI** （Generative UI）…… 在设计层面，用户沟通工具应支持 **异步消息模式** …… 提供 **已读/未读状态追踪** ，并在多渠道场景下保持消息的一致性 …… Agent 根据 **紧急程度、用户状态、内容性质、用户偏好** 综合决定渠道的选择。

🧭 **归纳**：

| 工具 | 设计要点 |
|---|---|
| **事件触发工具** | 触发条件 + 过滤规则（避免无谓唤醒）；payload 含充分上下文（少额外查询） |
| **用户沟通工具** | 异步消息模式 + 已读/未读状态 + 多渠道一致；紧急程度/用户状态/内容性质/用户偏好综合决定渠道 |

## Q4-13 虚拟身份 + 隔离执行环境的设计原则

- 章节: ch005 §4.7.5
- 主题: 虚拟身份

> 📖 **原文** (ch005 §4.7.5)： 更稳妥的方案是赋予 Agent 一套独立的虚拟身份——如同秘书拥有自己的办公电话和邮箱 …… 虚拟身份需要落地在隔离的执行环境上。 **虚拟电脑** （VM/容器）和 **虚拟手机** （Android 模拟器）为 Agent 提供操作系统级的隔离和完整的桌面/移动操作能力 …… 独立身份也带来两个现实挑战。一是 **反机器人机制** …… 二是 **访问用户真实账号的场景** ：当任务必须以用户本人的身份登录时，应采用 **Human-in-the-Loop 认证** ——通过 VNC/RDP 远程桌面让用户在可视化环境中亲自完成登录 ……

🧭 **归纳**：
- **虚拟身份**：独立账号 + 独立存储 + 独立计算环境；**增强而非削弱**信任
- **隔离执行环境**：虚拟电脑（VM/容器）+ 虚拟手机（Android 模拟器）
- **两大现实挑战**：
  1. 反机器人（CAPTCHA / IP 信誉）—— 实践需住宅代理
  2. 必须用用户身份登录 → HITL 认证（VNC/RDP）+ 会话令牌复用
- **数据交换**：共享文件系统（卷挂载）→ 传递路径字符串而非内容拷贝
