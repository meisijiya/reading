# 第五章 Coding Agent 与通用 Agent

> 开放任务型通用 Agent 的核心 = Coding Agent + 文件系统。本章从七个核心工具 → OpenClaw 案例 → 工程流程 → 故障恢复 → 元能力。

## Q5-1 为什么 Coding 是每个 Agent 的基础能力？七个核心工具是什么？

- 章节: ch006 §5.1.1
- 主题: Coding 基础 + 七工具

> 📖 **原文** (ch006 §5.1.1)： **代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力** 。 …… 这五个操作（浏览目录/读取代码/修改文件/运行命令/查找模式）覆盖了几乎所有 Coding Agent 的核心动作。为了支持这五类操作，一个基础的 Coding Agent 只需配备以下 **七个核心工具** ：Code Interpreter、Bash Shell、读文件、写文件、编辑文件、搜索文件名（Glob）、搜索文件内容（Grep）…… **为什么每个通用 Agent 都应该具备 coding 能力？因为代码生成不只是写程序，它是一种通用的问题解决手段** 。

🧭 **归纳**（七个核心工具）：

| # | 工具 | 作用 |
|---|---|---|
| 1 | Code Interpreter | 隔离沙盒执行 Python |
| 2 | Bash Shell | 终端命令 |
| 3 | 读文件 | 读代码/配置/文档/日志 |
| 4 | 写文件 | 创建或完全重写 |
| 5 | 编辑文件 | 局部修改（核心操作） |
| 6 | Glob | 文件名模式匹配 |
| 7 | Grep | 文件内容搜索 |

**Coding 是元能力**——可在运行时动态创造新工具/能力。

## Q5-2 通用 Agent 的架构长什么样？Coding Agent + 文件系统为什么是核心？

- 章节: ch006 §5.1.2
- 主题: 通用 Agent 架构

> 📖 **原文** (ch006 §5.1.2)： 以 Manus 为代表的通用 Agent 产品，将 Deep Research（深度调研）、Computer Use（电脑操控）和 Coding（代码生成）三大能力融合在一个系统中，凸显了一个已经被多类实践反复验证的洞察：**Coding Agent 加上文件系统，是开放任务型通用 Agent 最核心的技术基础**。开源项目 OpenClaw 也采用了类似思路，以开源实践展示了这一架构范式。

> 📖 **原文** (ch006 §5.1.2)： 为什么 Coding Agent 是核心而非其他两种？因为**几乎所有高效的内容生成最终都要落到代码上**。PPT 本质上是 OOXML（Office Open XML，微软推出的办公文档开放标准）格式的代码，Word 文档和 PDF 报告可通过代码生成，数据分析和可视化由 Python 脚本完成，甚至 GUI 操作中成功的浏览器操作序列也可以被固化为可复用的 RPA（机器人流程自动化，Robotic Process Automation）代码。**Deep Research 的搜索和信息综合可通过代码驱动的 Web 请求和解析实现，Computer Use 虽然通用性更强，但成本、延迟和稳定性远不如直接通过代码或 API 来完成相同操作。代码生成是效率最高、成本最低、可复用性最强的能力基座。**

🧭 **归纳**：
- **架构 = Coding Agent + 文件系统**（信息流转的枢纽）
- **文件系统角色**：远超数据存储——是 Agent 记忆、知识和能力的**中枢**
  - 长期记忆存 MEMORY.md（高层级事实/偏好）+ 日期归档 Markdown
  - Markdown 优先于向量库——用户可读可改 + 保留时间序 + Git 版本控制
- **适用边界**：仅适用于"以开放任务为目标的通用 Agent"（深度调研/内容生成/数据处理）；垂直客服 Agent 仍是固定业务流程 + coding 作基础能力
- **典型执行流**（分析销售数据）：读记忆 → 调工具 → 写代码 → 生成产物 → 更新记忆

## Q5-3 Coding Agent 的工程化流程是什么？

- 章节: ch006 §5.1.3
- 主题: 流程

> 📖 **原文** (ch006 §5.1.3)： 下面描述的是一套**推荐的工程化流程**，它把软件工程的最佳实践投射到 Agent 身上，勾勒的是理想形态。现实中的 Coding Agent（如 Claude Code、OpenClaw）更多按反应式的迭代循环工作，会**按需裁剪**这套流程——简单任务会跳过设计文档、不会每一步都阻塞等待用户批准，只有当任务复杂、影响面大时才会完整走完各阶段。不同模型裁剪这套流程的方式并不相同。有些 Coding 模型会在第一次修改前广泛阅读目录、实现、调用方和测试；另一些则会读少数最可能相关的文件，马上提交一个补丁，再把编译与测试反馈当作调查的一部分。这种"何时停止收集信息、开始行动"的阈值可以在更换 Harness 后继续跟随模型。**这套流程体现了软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化**。

🧭 **归纳**（五阶段流程）：

| 阶段 | 关键动作 |
|---|---|
| **1. 项目文档化** | 首次接触先建认知；缺文档时主动补写；项目指令文件（CLAUDE.md / AGENTS.md / .cursorrules）作为 Agent 专用形态 |
| **2. 任务理解与需求澄清** | 简单需求直接进实现；复杂需求通过探索性调研 + 主动对话澄清边界 |
| **3. 编写设计文档** | 修改哪些模块/原因/方案/新依赖/影响；提供人类高效介入点 |
| **4. 代码实现与测试** | 写测试 → 跑测试 → 失败就修；**"测试通过"而非"代码写完"才是完成** |
| **5. 文档同步与交付** | 架构变更必须更新文档；过时文档比没有更糟糕 |

➕ **补充**：Anthropic 长任务拆分 = 初始化 Agent（拆任务清单）+ 执行 Agent（逐步推进，把中间成果留给下一轮）——解决长时运行的"一次想做太多"或"过早声称完成"。

## Q5-4 Harness 工程在 Coding Agent 中的实践

- 章节: ch006 §5.1.4
- 主题: Harness 实践

> 📖 **原文** (ch006 §5.1.4)： 能不能稳定运行，往往不取决于用了多强的模型，而取决于围绕 Agent 搭建的基础设施有多扎实。第一章将 Harness 分为两个层面—— **上下文与工具** （让 Agent 能做事）和 **约束、验证与纠正** （让 Agent 不做错事）……

🧭 **归纳**：

| 组件 | 落地形式 |
|---|---|
| **验收基线** | 测试套件 + CI 管道 + 代码审查标准 |
| **执行边界** | 模块边界 + 依赖规则 + 权限控制 |
| **反馈信号** | Linter 输出 + 测试结果 + 类型检查错误 |
| **回退手段** | Git 版本控制 + 沙盒隔离 + 快照回滚 |

**四象限任务分类**（目标清晰度 × 验证自动化）：

|  | 结果可自动验证 | 结果需人工验证 |
|---|---|---|
| 目标明确 | 最佳区域：修复有测试用例的 bug | 吞吐受限：代码重构需人工审查 |
| 目标模糊 | 高效地跑偏：linter 优化"代码质量" | 难以启动："让 UI 更好看" |

**通用 Harness 四大原则**：
1. **约束优先于指导**：能用 Linter 强制就别写文档建议
2. **验证要自动化**：人工审查不可扩展
3. **反馈越快越好、越结构化越好**：错误越接近发生时刻纠正越高效
4. **回退要可靠**：Git 分支 + 沙盒 + 快照，让 Agent 大胆试错

## Q5-5 故障与错误恢复：四层分类 + 分级升级 + 熔断器

- 章节: ch006 §5.1.5
- 主题: 故障恢复

> 📖 **原文** (ch006 §5.1.5)： 按故障发生的位置，可以分为四层： **API 层** ：限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断 …… **工具层** ：幻觉调用、参数畸形、执行抛异常，以及最危险的一种—— **工具反复返回同一个错误，而模型不加改变地反复重试** 。 **上下文层** …… **控制流层** ：死循环 …… 与 **死亡螺旋** （错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应）。

> 📖 **原文** (ch006 §5.1.5)： **恢复手段按对用户透明的程度分级** ，能用低级别解决就不升级： 1. **静默重试** …… 指数退避叠加随机抖动 …… 2. **降级与接续** …… 3. **暴露给用户** 。 **每条恢复路径都必须有明确的熔断上限** …… 以 Claude Code 的压缩熔断为例，"连续 3 次"的阈值来自真实会话统计——曾有一个会话在这条恢复路径上连续失败三千余次 …… **逾千个会话出现过 50 次以上的连续失败** 。

🧭 **归纳**（四层故障）：

| 层 | 典型故障 | 关键检测 |
|---|---|---|
| **API** | 限流/超时/截断 | 服务端 Retry-After |
| **工具** | 幻觉调用/参数畸形/反复同一错误 | 工具名+参数指纹 + 失败计数 |
| **上下文** | 窗口溢出/压缩失败/轨迹损坏 | 完整性监控（自动修补配对） |
| **控制流** | 死循环/死亡螺旋 | 递归深度计数器 + 全局熔断 |

**检测三件套**：错误分类 → 模式识别（指纹+计数） → 活性与完整性监控（每个长连接要 watchdog）

**恢复三级**：静默重试 → 降级与接续 → 暴露给用户
- **熔断阈值从产线数据来**，不拍脑袋：Claude Code 压缩熔断 = 3 次（数据：曾有会话连续失败 3000+ 次，全球日浪费 25 万次 API 调用；1000+ 会话出现 50+ 次连续失败）

**死亡螺旋防护**：错误路径禁用会再次调模型的副作用逻辑 + 递归深度计数器。

## Q5-6 Coding Agent 的五个实现技巧

- 章节: ch006 §5.1.6
- 主题: 实现技巧

> 📖 **原文** (ch006 §5.1.6)： 上面的工作流程是理想状态。要让它在实践中真正跑起来，还需要几个具体的实现技巧——在保证思考质量的前提下，把响应速度提上去、把上下文消耗降下来。它们是第二章、第四章讨论的通用 Agent 技术在编程领域的具体应用。**这五个实现技巧——并行与流式、上下文管理、环境感知、状态持久化、即时反馈——共同构成了高效 Coding Agent 的技术基础**。它们不是孤立的优化点，而是相互配合的设计决策，共同指向一个目标：让 Agent 能够像经验丰富的开发者那样流畅地工作。

🧭 **归纳**：

| 技巧 | 关键点 |
|---|---|
| **并行工具调用 + 流式执行 + 级联中止** | 第一个调用参数一完整就启动；独立调用并行；失败只中止同批依赖（不波及独立调用和父级） |
| **上下文精细管理** | 大文件按行号范围读；**返回值必带行号前缀**（让模型精确引用"第 42 行"）；终端长输出截断 + 引导读文件 |
| **环境信息动态注入**（状态栏应用） | 当前工作目录、git 分支、最近提交、暂存区变更——**不能硬编码在 system prompt**（破坏 KV Cache） |
| **命令执行环境状态持久化** | 默认共享长会话（保 workdir/env/venv）；隔离终端只用于并行任务 |
| **即时语法反馈** | 文件写入后自动跑 linter；结果作为工具返回值呈现；像 IDE 红线那样立即修正 |

## Q5-7 Coding Agent 搜索工具的四种互补方式

- 章节: ch006 §5.1.7
- 主题: 搜索工具

> 📖 **原文** (ch006 §5.1.7)： **这四种搜索方式构成互补的工具箱，实践中往往组合使用：先用语义搜索找到相关模块，再用正则匹配精确定位具体代码行，最后通过符号搜索追踪调用链——"从粗到细、从语义到语法"的渐进式策略。** 是否值得为语义搜索建立嵌入索引，业界存在明显的路线之争。以 Claude Code 为代表的终端型 Agent 刻意**不建嵌入索引**，纯靠 agentic 的 grep + glob 现场检索——这样既不必维护随代码演化而不断陈旧的索引、也省掉了一整套索引基础设施，更避免了把代码嵌入外发到第三方服务的风险。Cursor 这类 IDE 型工具则走相反路线：愿意为**跨文件的语义召回**付出建索引的成本，靠嵌入索引在大型代码库中快速找到语义相关但用词不同的片段。两条路线的取舍，本质上是在"基础设施与数据外发的代价"和"跨文件语义召回的收益"之间做权衡。

🧭 **归纳**：

| 方式 | 擅长 | 局限 |
|---|---|---|
| **正则（grep/ripgrep）** | 已知文本（函数名/变量名/错误消息） | 只匹配字面，无法理解语义 |
| **Glob（文件名）** | 快速建立项目结构 | 不看内容 |
| **语义代码搜索** | "验证用户身份" → 找到 `check_credentials` | 需结构感知分块 + 混合检索 + reranker |
| **符号级（LSP 跳定义/查找引用）** | 区分同名符号的定义和调用 | 需 LSP 基础设施 |

**路线之争**：
- **Claude Code（终端型）**：刻意**不建嵌入索引**，纯靠 agentic grep + glob——省去索引陈旧/外发风险
- **Cursor（IDE 型）**：走嵌入索引路线——跨文件语义召回收益 > 基础设施代价

## Q5-8 文件编辑的五种方案对比

- 章节: ch006 §5.1.8
- 主题: 文件编辑

> 📖 **原文** (ch006 §5.1.8)： 图5-4 对比了五种文件编辑方案，展示人类语言表达与机器精确执行之间的根本张力。

🧭 **归纳**：

| 方案 | 做法 | 优势 | 劣势 | 当前采用 |
|---|---|---|---|---|
| **差异描述 + Apply Model** | 模型生成 diff/带省略骨架 → Apply Model 合并 | 主模型专注高层逻辑 | 合并环节脆弱 | Cursor 曾用，**现已弃用** |
| **旧字符串 → 新字符串** | 模型提供 old string + new string；框架字符串替换 | 可预测、透明 | 删大段需完整原始内容；字符偏差即失败 | **Claude Code / Codex / 当前 Cursor** |
| **行号定位** | "删第 X-Y 行，插入新内容" | 大段删除仅需首尾行号 | 编辑后行号变化，多次编辑需用初始行号 | — |
| **类 Vim 编辑命令** | 借鉴 Vim 命令体系 | 重组织代码高效 | 语法学习负担；一次多命令不友好 | 弱模型错误率高 |
| **首尾匹配** | 只给首尾几行，中间省略 | 大段删除 + 内容匹配可靠 | 需首尾组合在文件中唯一 | — |

**关键洞察**：Vim 是为人类"持续看状态、规划下一步简单操作"设计；**模型工作模式是"长时间思考 + 批量复杂操作"**——这就是为什么 Vim 式编辑方案对模型不友好。

## Q5-9 代码作为通用 Agent 的元能力：六大方向

- 章节: ch006 §5.2
- 主题: 代码元能力

🧭 **归纳**（代码作为元能力的六大方向，详见 §5.2.1-5.2.6）：
1. **代码作为思考工具**——形式化代码让思考高度严谨（`age > 18 and is_verified` 消除歧义）
2. **代码作为业务规则约束**——精确、可执行、自然语言做不到的自洽证明
3. **代码驱动的多媒体生成**——PPT/Word/PDF/数据可视化本质都是代码生成
4. **代码作为系统适配器**——动态生成解析逻辑适应数据格式变化
5. **代码作为生成式 UI**——HTML 交互式界面
6. **代码创造代码（Agent 自举）**——Agent 写新工具 / 新 Agent（呼应 Q1-3 模型即 Agent + Q5-1 Coding 是元能力）

➕ **补充**：从 Q5-1 "代码是元能力" 到这里的"代码创造代码"——形成自举闭环：Agent 不仅用代码解决任务，还写代码扩展自己。
