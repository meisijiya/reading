# 第六章 Agent 的评估

> 评估在 Harness 中扮演"验证"功能的核心角色。**评估的对象不是模型，而是模型 + Harness 的组合体**。本章从指标体系 → 评估环境 → 评估方法 → 评估驱动决策。

## Q6-1 为什么评估对象是"模型 + Harness 组合体"而不是单纯模型？

- 章节: ch007 §6.0
- 主题: 评估对象

> 📖 **原文** (ch007 §6.0)： 评估在 Harness 中扮演着"验证"功能的核心角色。一个关键认识是： **评估的对象不应只是模型，而应是模型与 Harness 的组合体** 。同一个模型在不同的 Harness 中可能表现差异悬殊…… 当 Agent 在评估中表现不佳时，改进方向可能不是换模型，而是优化 Harness 的某个组件（提示词、工具设计、反馈循环）…… **区分这两类问题的常见手段是模型替换实验（model swap）** ——固定 Harness，只更换更强/更弱的模型，观察分数变化幅度；如果换强模型分数不涨，说明瓶颈在 Harness；如果换弱模型分数大跌、分数随模型能力大幅波动，最直接的解读就是瓶颈在模型能力本身 …… **消融是关闭 Harness 的某个组件看整体性能如何变化，模型替换则是固定 Harness、只换模型** ——前者定位 Harness 内部哪个部件重要，后者区分瓶颈在模型还是在 Harness。

🧭 **归纳**：
- 评估对象 = Model + Harness，**不是单纯模型**
- **消融实验**：定位 Harness 内部哪个组件重要（关掉一个看分数）
- **模型替换实验**：定位瓶颈在模型还是在 Harness（固定 Harness 换模型）
- **首尾呼应**："评估的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进"

## Q6-2 Pass@k vs Pass^k 怎么用？技术奇观 vs 业务可靠性

- 章节: ch007 §6.2.1-6.2.2
- 主题: 指标体系

> 📖 **原文** (ch007 §6.2.1)： 当前许多模型和 Agent 仍处在一个可以称为 **"技术奇观"** 的阶段。这里的"奇观"是指展示在大量尝试、充足时间和人工筛选下能够达到的最高上限：只要其中一次成功，就足以证明"这件事原则上做得到"。这正是 **Pass@k** 的逻辑——在同一任务上运行 k 次，只要至少有一次通过，任务就算通过；如果输出是连续得分，则取最好的一次，记为 Best@k。对这类工程与科研探索，展示的通常不是"每次都做对"，而是把探索预算拉长后终于出现一条突破性轨迹。**对于科研发现、漏洞挖掘、开放式创作等任务，这种能力上限本身就很有价值：人类可以从 k 条候选轨迹中挑出那一条最好的。**

> 📖 **原文** (ch007 §6.2.2)： 真实业务通常更关心另一件事：在多次尝试中一次错都不能犯。我们把这个目标称为 **Pass^k**（可以读作 Pass consecutive k）：同一任务连续运行 k 次，要求每一次都通过，且不能触发安全、合规或幻觉等一票否决项。它回答的是"Agent 能否稳定可靠地交付"，而不是"能否偶尔创造奇迹"。例如单次成功率 p=0.6 时，k=5：Pass@5 = 1 − 0.4^5 ≈ 99.0%，看起来几乎总能"至少成功一次"；但 Pass^5 = 0.6^5 ≈ 7.8%，说明连续五次都不出错仍然很难。**前一个数字适合衡量探索时的能力天花板，后一个数字才接近支付、退款、权限变更、生产部署等场景的可靠性要求。**

🧭 **归纳**：

| 指标 | 公式 | 场景 |
|---|---|---|
| **Pass@k** | `1 - (1-p)^k` | 探索/科研/创作（能力上限） |
| **Pass^k** | `p^k` | 生产（连续可靠，一票否决） |

**示例**：p=0.6, k=5 → Pass@5 ≈ 99.0%（看起来很好），但 Pass^5 ≈ 7.8%（连续 5 次都对仍很难）。

➕ **补充**：报告必须写清 k 次尝试的口径（独立采样 vs 生产连续 k 个任务）；副作用操作不能"重试直到成功"，应在沙盒/可回滚环境采样，每次失败记入可靠性指标。

## Q6-3 过程指标怎么设计？黑盒到白盒

- 章节: ch007 §6.2.3
- 主题: 过程指标

🧭 **归纳**（五大过程指标）：

| 指标 | 衡量 |
|---|---|
| **行动合法率** | 工具调用有效性（不调不存在的工具、不越权） |
| **工具调用正确率** | 参数语义合理（搜索词准确、路径正确） |
| **路径效率** | 步数 + 冗余动作 + 回退次数（需与人类专家基线比） |
| **检索覆盖率** | 信息收集类任务是否充分探索 |
| **成本与延迟** | 请求数 + token 花费（输入/输出 + KV Cache）+ 墙钟时间分布 |

## Q6-4 评估为什么必须既看轨迹又看结果？

- 章节: ch007 §6.2.4
- 主题: 双重覆盖

> 📖 **原文** (ch007 §6.2.4)： 评测中容易忽视的一个区分是： **Agent 在执行过程中"说了什么、做了什么"（即第一章定义的轨迹，trajectory）和"系统最终变成了什么样"（最终结果，outcome）是两件事** 。Agent 说"订票已完成"是轨迹层面的信息，数据库里确实生成了一条订单才是结果层面的验证。只看轨迹会漏掉"说了但没做到"的情况，只看结果又可能看不出中间步骤走歪了 …… **因此两类评测都应覆盖，以避免系统性盲区** 。

🧭 **归纳**：
- **轨迹（trajectory）** = Agent 说了什么/做了什么；**结果（outcome）** = 系统最终变成什么样
- 两类都覆盖——只盯轨迹会漏"说了没做"；只盯结果看不出中间走歪
- **零容忍原则**：安全违规（删除数据/数据外泄/越权发送）一票否决，不因其他维度表现优秀豁免

## Q6-5 自动评估环境长什么样？两类范式

- 章节: ch007 §6.3
- 主题: 评估环境

> 📖 **原文** (ch007 §6.3.3)： 关键设计原则是 **渐进式信息透露（Progressive Information Disclosure）** ，这是人机交互型评估与传统基准测试（benchmark）的根本区别 …… **绝不能一开始就把模拟用户的所有信息暴露给 Agent** ，信息应按需、渐进地在对话中透露。

🧭 **归纳**：

**评估环境五要素**：数据集 / 环境状态 / 工具接口 / 评分标准 Rubric / 执行协议

**两类范式**：

| 范式 | 例子 | 关键设计 |
|---|---|---|
| **工具调用型** | Verifiers 框架（SingleTurnEnv / ToolEnv / StatefulToolEnv / SandboxEnv） | 基于可执行标准（测试通过/答案匹配），不依赖人类标注或模型评判 |
| **人机交互型** | τ-bench（航空客服）/ τ²-bench（双控环境 + 组合任务生成） | **渐进式信息透露** + LLM 扮演用户 + 模拟用户有"有限耐心" |

➕ **补充**：τ-bench 检查是**组件级多维度**（数据库状态 + 沟通信息）但**任务层二元奖励**——便于统计 Pass^k，代价是粒度损失。

## Q6-6 LLM-as-a-Judge 怎么用？评判者校准

- 章节: ch007 §6.2.5
- 主题: 评估方法

> 📖 **原文** (ch007 §6.2.5)： 即使自动评估在大多数情况下是可靠的，也需要定期人工抽检 …… **评判者校准** ：在放量使用 LLM 评判之前，先构建一个人工标注的金标集（如 100-200 个覆盖各任务类型和难度的案例），在其上测量评判模型 …… 与人类标注的一致率 …… 达到预设门槛（如 kappa 高于 0.7）后才将评判模型用于大规模评估 …… **没有这一步，LLM 评判的分数只是"另一个模型的意见"，而非人类判断的可靠代理** 。

🧭 **归纳**：

| 实践 | 关键点 |
|---|---|
| **人工抽检** | 覆盖不同任务类型 + 成功/失败 + 边界分数模糊案例 |
| **评判者校准** | 100-200 人工金标集 + 测 Cohen's kappa ≥ 0.7 + 每次模型/Rubric 更新重测 |
| **对抗式评审（Red Teaming）** | 主动构造：表面完美但含隐蔽错误 / 关键词堆砌蒙混 / 利用评判模型偏见 |
| **多评委机制** | 独立评分 + 加权平均/一致性检查；严重分歧标记人工审查 |

## Q6-7 评估驱动决策：从结果到行动

- 章节: ch007 §6.6, 6.9
- 主题: 决策

> 📖 **原文** (ch007 §6.9.4)： 这就是**持续迭代**真正的含义：一轮证据只支持与它规模相称的下一步。H1 失败，让我们不再继续堆提示词；H5 找到了正确方向，也暴露了成本问题；H5C 解决成本问题后，才获得扩大测试的资格。好的 Benchmark 报告不只给出一个分数，还应写清结论适用于哪里、哪些底线没有通过、下一轮要验证什么。**当新模型发布时，更新基线分数、识别新能力带来的新机会、关注成本和延迟变化。**

🧭 **归纳**（评估驱动决策闭环）：

```
评估 → 读懂 Benchmark → 形成假设 → 改进 Harness（提示词/工具/反馈） → 重测 → ...
                    ↓
              区分"模型能力不足"vs"Harness 设计缺陷"
                    ↓
              模型替换实验 + 消融实验
```

**评估驱动的模型选型**（§6.6）：
- 关键维度：能力/成本/延迟/安全/特定任务表现
- 不要只看公开 benchmark——新模型在公开榜上更好，**不意味着在你的任务上也更好**（regression 风险）

## Q6-8 生产级 Agent 的内部评估基础设施：双层特性开关 + AB

- 章节: ch007 §6.10
- 主题: 内部评估

> 📖 **原文** (ch007 §6.10)： 完善的评估体系使得"为未来的模型开发产品"成为可行策略——即使当前模型不足以支撑商用，也可以先完成产品开发并建立评估集，持续追踪新模型的表现，一旦达到门槛就立即上线。

🧭 **归纳**（生产级评估基础设施）：

| 组件 | 做法 |
|---|---|
| **消融基础设施** | 每次新特性可独立开关；用 AB 测试衡量真实贡献 |
| **AB 测试方法论** | 区分"机制"vs"目标"（A 实现了特性 X 但目标是 Y，B 不实现 X 看是否影响 Y） |
| **双层特性开关** | 用户层（产品功能）+ 内部层（实验）分离 |
| **提示词敏感性评估** | 同一意图多种表述 → 评估一致性 |
| **隐私感知的分析** | 评估基础设施遵守数据合规 |

➕ **补充**：Harness 与模型训练深度耦合——产品模式宽容（占位符修补缺失消息），训练模式严格（拒绝修复，污染训练数据）。
