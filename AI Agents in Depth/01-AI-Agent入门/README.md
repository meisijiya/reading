# 第一章 AI Agent 入门

> 本章建立 Agent 的概念地图：核心公式、三大组件、ReAct 循环、Harness 工程、编排模式与护栏。后续章节会逐项展开。

## Q1-1 现代 Agent 的核心公式是什么？三种理解层次怎么映射？

- 章节: ch002 §1.1
- 主题: 核心公式 `Agent = LLM + 上下文 + 工具`

> 📖 **原文** (ch002 §1.1)：现代 Agent 的最小工程实现可以用一个简洁的公式来表达： **Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具**。这里的加号表示工程组件的组合，而不是强化学习中的形式化定义；更重要的是，这个公式只描述 Agent 边界之内的实现， **不包含 Agent 与之交互的 Environment（环境）** 。

> 📖 **原文** (ch002 §1.1)：换一种更直观的说法： **Agent = 大脑 + 眼睛 + 手脚** 。大脑负责思考和决策，眼睛接收环境提供的观察，手脚将决策转化为作用于环境的行动。

> 📖 **原文** (ch002 §1.1)：对熟悉强化学习的读者，这三者也可以映射到 RL 的形式化语言。具体来说，LLM 对应 Policy（策略），上下文对应 Observation Space（观察空间），工具对应 Action Space（动作空间）。

🧭 **归纳**：核心公式同一对象的三种表述（工程层 / 直觉层 / 学术层）：

| 直觉 | 组件 | 学术概念 |
|---|---|---|
| 大脑 | LLM | 策略 Policy |
| 眼睛 | 上下文构造 | 观察与历史 |
| 手脚 | 工具与适配器 | 观察/行动接口 |

➕ **补充**：公式中"+ 工具"对应到 RL 是 Action Space，但只覆盖"接口"；工具背后的文件系统/数据库/用户仍属 Environment，访问它们不改变 Agent 边界。

## Q1-2 在底层模型固定时，提升 Agent 表现的最主要工程手段是什么？

- 章节: ch002 §1.1.1
- 主题: 观察空间与动作空间扩展

> 📖 **原文** (ch002 §1.1.1)： 因此， 在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间 。用本书的术语说，就是扩展上下文和工具。许多看似需要"更聪明模型"的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。

🧭 **归纳**：升级 Agent 不必换模型——重新设计上下文（接什么数据进观察）和工具（暴露什么操作）常常比换 LLM 收益更高。Manus 与 OpenClaw 的演进就是这两条空间的扩展史：虚拟浏览器扩观察、本地 Gateway 扩动作；OpenClaw 又把接口延伸到用户已经在用的 WhatsApp/Telegram/Google Drive/Notion。

## Q1-3 "模型即 Agent"（Model as Agent）范式是什么意思？和 Harness 是什么关系？

- 章节: ch002 §1.1.3.1
- 主题: 模型即 Agent 范式

> 📖 **原文** (ch002 §1.1.3.1)："模型即 Agent"（Model as Agent）这一新范式代表了 AI Agent 发展的最新方向。先进模型通过后训练（特别是强化学习）将工具调用能力内化为原生能力：何时调用工具、调哪个、传什么参数，都由模型自己决定，无需人工编排。但这并不意味着框架层变得不重要了。恰恰相反，模型越强大，围绕模型构建的 Harness 就越关键。

> 📖 **原文** (ch002 §1.1.3.1)：模型自主决策的空间越大，出错时的影响面也越大，因此需要更精细的约束、验证和纠正机制来确保可靠性。模型厂商的真正优势不是"让框架变薄"，而是能对模型与外围 Harness 进行协同优化，持续迭代。

> 📖 **原文** (ch002 §1.1.3.1)：本书的立场是： **方向认同，节奏务实** 。方向上，本书不怀疑模型会持续吃掉 Harness……但在节奏上，这个"吃"远比直觉慢：训练以月计，模型也无法一次内化真实业务中所有的约束与偏好，模型此刻的能力边界，就是 Harness 此刻的价值所在。

🧭 **归纳**：
- RL 训练让模型原生拥有"何时调、调哪个、传什么参数"的**决策能力**；
- 但**工具本身的执行**（web_search 的真实检索、code_runner 的沙盒）仍在模型外的框架/Harness 里完成；
- Harness 不是会被"吃掉"的对立面，而是模型"吃一层、Harness 卸一层"动态博弈中的兜底层；
- 可靠性场景下，模型自主空间越大 → Harness 约束要越精细。

## Q1-4 ReAct 循环具体怎么走？Agent 的"轨迹"是什么？

- 章节: ch002 §1.1.5
- 主题: ReAct 循环与轨迹

> 📖 **原文** (ch002 §1.1.5)：Agent 执行任务的核心模式叫做 ReAct（Reasoning + Acting）。虽然名字只体现了思考（Reasoning）和行动（Acting）两个词，但实际循环包含三个环节：模型先 **思考** 当前应该做什么，然后调用工具 **行动** ，再 **观察** 工具返回的结果并继续思考下一步。这个"想→做→看→想→做→看"的循环不断重复，直到任务完成。

> 📖 **原文** (ch002 §1.1.5)： 轨迹是 Agent 在执行任务过程中不断积累的消息历史——用户消息、模型回复（包括思考过程和工具调用）、工具执行结果。每一次调用 LLM 时，它接收的完整上下文由 静态前缀（系统提示词 + 工具定义）和 轨迹（动态消息历史）两部分组成 …… **Agent 的上下文 = 静态前缀 + 轨迹** 。

🧭 **归纳**：ReAct = Think → Act → Observe 三步循环。Agent 每次调 LLM 看到的上下文 = 静态前缀（系统提示词 + 工具定义）+ 轨迹（用户消息 + 模型回复 + 工具结果，动态增长）。理解 Agent 行为的钥匙是看完整轨迹，不是看单次响应。

## Q1-5 上下文的五个组件各有什么用？缺一会怎样？

- 章节: ch002 §1.1.4 + 实验 1-1
- 主题: 上下文五组件 + 消融实验

> 📖 **原文** (ch002 §1.1.4)：从 API 的视角看（详见第二章），每次调用 LLM 时的上下文由以下五个部分构成： **系统提示词、工具定义、用户消息、模型回复、工具执行结果** 。前两项（系统提示词 + 工具定义）是静态前缀，后三项（用户消息 + 模型回复 + 工具执行结果）是随交互不断增长的动态消息历史。

> 📖 **原文** (ch002 §1.1.4)——实验 1-1 结论： 工具定义 是 Agent 行动能力的基础，没有它，Agent 就无法识别和调用任何工具。 **工具执行结果** 是闭环控制的关键，缺失它会导致 Agent"盲目"执行，陷入无限循环。 **思考过程** 保留了 Agent 做出之前决策的原因，使思维流程更加连贯…… **历史消息** 则防止了冗余操作…… **上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策** 。

🧭 **归纳**（消融实验四组对照）：

| 缺哪一组件 | 后果 |
|---|---|
| 工具定义 | 完全丧失行动能力 |
| 工具执行结果 | 反复调同一工具，陷入死循环 |
| 思考过程（reasoning） | 前后决策互相矛盾 |
| 历史消息 | 失忆，从头重做、重复已完成步骤 |

➕ **补充**：系统提示词不参与消融（无它则连"基本身份"都没有，测试无意义）。"Agent 只能基于它看到的信息决策"——这一原则是后续上下文工程章的方法论根基。

## Q1-6 Harness 的五大功能是什么？它们的核心设计原则是什么？

- 章节: ch002 §1.2.2
- 主题: Harness 五大功能

> 📖 **原文** (ch002 §1.2.2)：Harness 是 Agent 边界内环绕模型的运行与治理层，负责构造上下文、暴露工具接口、维护循环和状态，并实施权限、验证与纠正 …… 本书将 Harness 的功能归纳为五项： **工具管理、上下文管理、循环与状态管理、权限与安全、验证与纠正** 。

🧭 **归纳**：Harness 的五大功能 = 工具 / 上下文 / 循环状态 / 权限安全 / 验证纠正。本质是 Agent 边界内的"运行 + 治理"双层。模型越强，Harness 的治理权重越大（呼应 Q1-3 "模型即 Agent" 范式）。

## Q1-7 工作流（Workflow）和自主 Agent 该怎么选？

- 章节: ch002 §1.2.5
- 主题: 编排模式：工作流 vs 自主

> 📖 **原文** (ch002 §1.2.5)： 在构建 LLM 应用时，应遵循"从简单到复杂"的原则：首先考虑单个 LLM 调用——如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统；当需要多步骤处理时，对于可以清晰分解为固定子任务的场景，考虑使用 **工作流** ；只有当需要动态决策和灵活的执行路径时，才使用 **自主 Agent** 。需要记住的是： **Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得** 。

🧭 **归纳**：工作流 ⇄ 自主 Agent 是同一条谱，自主性 ↑ ↔ 灵活性 ↑、可预测性 ↓。生产级系统往往混合用：核心合规/支付/部署用工作流硬约束，探索/研究/开放任务用自主 Agent。具体判断维度见模块 04。

## Q1-8 护栏（Guardrails）和安全（Safety）该在哪一层做？

- 章节: ch002 §1.2.6
- 主题: 护栏与安全性

> 📖 **原文** (ch002 §1.2.6)： **护栏** （Guardrails）有助于管理数据隐私风险（例如防止系统提示泄露）或声誉风险（例如确保模型行为与品牌形象一致）…… **可以将护栏理解为分层防御机制** 。单个护栏不太可能提供足够的保护，但将多个专门的护栏组合使用，就能构建出更有韧性的 Agent 系统。

🧭 **归纳**：护栏是 Harness "约束、验证与纠正"层面的核心实现手段——多个专门护栏组合成"分层防御"（details in 2/4/5）。单一护栏不充分；组合形成韧性。
