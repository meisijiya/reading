## 二、Foundation Model 内部决策（选模型时必看）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 训练数据三大隐患 | (1) Common Crawl 含假新闻；(2) 英语占 45.88% 致低资源语言差；(3) tokenization 让 Burmese 等慢 10× | §2.1 | 🧭归纳 |
| 低资源语言含义 | 在 Common Crawl 中占比 < 1% 的语言；GPT-4 在 Telugu 上/MMLU 比英语低一档 | §2.1 | 🧭归纳 |
| Transformer 为什么主导 | attention 解决 seq2seq 的两痛点：(a) 仅用 final hidden state；(b) RNN 串行处理 | §2.2 | 🧭归纳 |
| 推理两阶段 | Prefill（并行处理输入，compute-bound）+ Decode（逐 token 生成，memory bandwidth-bound） | §2.2, §9.1 | 🧭归纳 |
| Attention 的 Q/K/V | Query = 当前解码状态；Key = 历史 token 标签；Value = 历史 token 内容 | §2.2 | 🧭归纳 |
| Transformer 替代架构 | RWKV（RNN+并行训练）/ SSMs（S4/H3/Mamba 线性时间序列建模）/ Jamba（Transformer+Mamba 混合 MoE 52B/12B active） | §2.2 | 🧭归纳 |
| 模型规模三大信号 | (1) 参数数 = 学习容量代理；(2) 训练 token 数 = 学了多少代理；(3) FLOPs = 训练成本代理 | §2.3 | 🧭归纳 |
| MoE 为何"又大又快" | 8 个 expert 每 token 只激活 2 个（Mixtral 8x7B：46.7B 总参数 / 12.9B active） | §2.3 | 🧭归纳 |
| Chinchilla 缩放律 | 给定算力预算，训练 tokens ≈ 20 × 参数数（最经济）；模型大小与数据应等比例翻倍 | §2.3 | 🧭归纳 |
| Sparse 模型含义 | 大部分参数为 0；7B 模型 90% 稀疏等价 700M 非零参数 | §2.3 | 🧭归纳 |
| 后训练三类型 | (1) Self-supervised finetuning / continued pre-training（领域语料继续自监督预训练）；(2) Supervised finetuning / SFT（指令-响应对）；(3) Preference finetuning / RLHF（指令-胜出响应-失败响应三元组） | §2.4, §7.1 | 🧭归纳 |
| 长 context finetuning | 改架构（位置编码）+ 数据；新模型可能退化短序列性能 | §2.4, §7.1 | 🧭归纳 |
| 采样为何被低估 | 解释幻觉、重复、不一致；调温度/top-p/top-k 性价比最高 | §2.5 | 🧭归纳 |
| Structured outputs | 用 schema-guided generation 约束 JSON/YAML/regex；生产系统下游代码硬需求 | §2.5 | 🧭归纳 |

## 三、评估方法（没评估别开工）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 评估为何是 AI 工程瓶颈 | ①模型越强越难评；②开放性无 ground truth；③FM 黑盒；④benchmark 快速饱和；⑤评估边界扩展 | §3.1 | 🧭归纳 |
| Benchmark 饱和速度 | GLUE 1 年 → SuperGLUE；MMLU（2020）→ MMLU-Pro（2024） | §3.1 | 🧭归纳 |
| 评估驱动开发 (EDD) | 评估之于 AI = TDD 之于软件；"上线却不知好坏"比没上线更糟 | §4.0 | 🧭归纳 |
| 评估四桶 | domain-specific capability / generation capability / instruction-following capability / cost and latency | §4.1 | 🧭归纳 |
| Entropy 含义 | 平均每个 token 携带的信息量（bits）；越难预测的语言熵越高 | §3.2 | 🧭归纳 |
| Cross entropy 含义 | H(P, Q) = H(P) + D_KL(P || Q)；训练目的 = 让 Q 逼近 P | §3.2 | 🧭归纳 |
| Perplexity (PPL) 含义 | PPL = 2^H；模型预测下一个 token 的"分母数"（越低越好）；≥3 即极好 | §3.2 | 🧭归纳 |
| Perplexity 三大经验 | 结构化数据 PPL 低；vocab 大 PPL 高；context 长 PPL 低 | §3.2 | 🧭归纳 |
| Perplexity 与 Post-training | SFT/RLHF 后 PPL 通常上升（post-training 折叠熵）；PPL 不再单调反映能力 | §3.2 | 🧭归纳 |
| 数据污染检测 | 低 PPL = 文本大概率在训练集；用于 benchmark 污染检测 & 数据去重 | §3.2 | 🧭归纳 |
| Functional correctness | 跑测试用例验对错；代码 HumanEval pass@k / MBPP；text-to-SQL Spider/BIRD | §3.3 | 🧭归纳 |
| pass@k 含义 | k 个采样中任一通过所有测试 = pass；pass@1 ≤ pass@3 ≤ pass@10 | §3.3 | 🧭归纳 |
| Lexical similarity | BLEU/ROUGE/METEOR++/TER/CIDEr；基于 n-gram 重叠；翻译/摘要传统但少用 | §3.3 | 🧭归纳 |
| Semantic similarity | 用 embedding + cosine similarity；BERTScore / MoverScore；跨模态可用（CLIP） | §3.3 | 🧭归纳 |
| AI as Judge 行业现状 | LangChain 2023: 58% 生产评估用 AI 判官；G-Eval、GPTScore 自带 reasoning | §3.4 | 🧭归纳 |
| AI Judge 三大偏见 | 位置偏好、长度偏好、自我偏好（judge 偏好自己输出风格） | §3.4 | 🧭归纳 |
| Comparative eval | 让 AI 判官对两个输出排名；最成功案例 = Chatbot Arena Elo | §3.5 | 🧭归纳 |
| 事实一致性三大武器 | (1) Local factuality（NLI / DeBERTa-v3-base-mnli-fever-anli）；(2) Global factuality（SelfCheckGPT 多次采样自检 / SAFE + Google Search 拆句验证 / TruthfulQA 817 题）；(3) 用例化 AI 判官 | §4.1 | 🧭归纳 |
| SelfCheckGPT 工作原理 | 假设"多次输出互不一致 = 原输出幻觉"；生成 N 个新响应测一致性；昂贵（多次 API） | §4.1 | 🧭归纳 |
| SAFE 工作原理 | (1) AI 拆 output 为单句；(2) 改写为自包含；(3) Google API 事实查询；(4) AI 判定一致性 | §4.1 | 🧭归纳 |
| Safety 六大类 | 不当语言、有害建议、仇恨、暴力、刻板、政治/宗教偏见 | §4.1 | 🧭归纳 |
| 指令遵循两大基准 | IFEval（25 类可自动校验：关键词/长度/JSON 等）/ INFOBench（内容/语言/风格约束，需 yes/no 判官） | §4.1 | 🧭归纳 |
| MCQ 局限 | 75% lm-evaluation-harness 任务是 MCQ；但"判别好坏"≠"生成好坏"——MCQ 测知识与推理，对生成无能为力 | §4.1 | 🧭归纳 |
| Model Selection 四步法 | (1) 硬属性（license/数据/大小/隐私）过滤 → (2) 公公开 benchmark 排序 → (3) 自家 pipeline 实跑 → (4) 生产监控+反馈循环 | §4.2 | 🧭归纳 |
| Hard vs Soft 属性 | Hard = 不可改（license / 训练数据 / 隐私）；Soft = 可改（accuracy / 延迟） | §4.2 | 🧭归纳 |
| Build vs Buy 决策 | API 便宜但有数据外送风险；自托管贵但可控；二者非二选一（API on top of open source 是新中间态） | §4.2 | 🧭归纳 |
| Eval Pipeline 三步 | (1) 评估每个组件；(2) 写评估指南（什么算"好"）；(3) 定义评估方法与数据 | §4.3 | 🧭归纳 |

## 四、Prompt 与 RAG（成本最低的两板斧）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| Prompt 工程能解决啥 | 不改权重就能引导行为；新信息通过 in-context learning 实时注入（持续学习） | §5.0, §5.2 | 🧭归纳 |
| Prompt 三段式 | 任务描述 + 示例 + 任务；可拆 system prompt / user prompt | §5.1 | 🧭归纳 |
| System prompt 为何更有效 | (a) 位置效应（模型对开头结尾的指令理解更好）；(b) OpenAI《Instruction Hierarchy》训练优先级 | §5.3 | 🧭归纳 |
| Chat Template 铁律 | 用错模板 = 沉默的灾难；Llama 2/3 模板不同；务必 print final prompt 校验 | §5.3 | 🧭归纳 |
| Context Length 真实瓶颈 | 5 年内从 1K → 2M（2000 倍）；但模型对中段注意力差（needle in haystack），长 ≠ 好用 | §5.3 | 🧭归纳 |
| In-context learning | 模型从 prompt 示例学新行为，不动权重；GPT-3 时代 few-shot 显著好于 zero-shot，GPT-4 时代差距缩小 | §5.2 | 🧭归纳 |
| Prompt 七大最佳实践 | (1) clear instructions；(2) sufficient context；(3) decompose；(4) time to think (CoT)；(5) iterate & version；(6) tools；(7) organize & version | §5.4 | 🧭归纳 |
| CoT 两种用法 | (a) "think step by step" / "explain your decision"（零样本 CoT）；(b) 给示例（one-shot CoT） | §5.4 | 🧭归纳 |
| Self-critique | 让模型检查自己的输出；CoT 的近亲；增加中间步 | §5.4 | 🧭归纳 |
| Prompt decomposition 四大利 | (a) Monitoring 中间输出；(b) Debugging 隔离坏步；(c) Parallelization 并行独立步；(d) Effort 写简单 prompt 更易；缺点 = 用户感知延迟 ↑ | §5.4 | 🧭归纳 |
| Prompt 工具 | DSPy（自动 prompt 优化）/ OpenPrompt / Promptbreeder（进化策略）/ Guidance / Outlines / Instructor（结构化输出） | §5.5 | 🧭归纳 |
| Prompt 工具两大风险 | (a) 隐藏 API call 可能把账单打爆；(b) 默认模板常有 typo；建议先手写不用工具 | §5.5 | 🧭归纳 |
| Prompt 攻击三类 | (1) Prompt extraction（反向工程 system prompt）；(2) Jailbreaking / prompt injection（让模型做坏事）；(3) Information extraction（泄露 context 中的隐私） | §5.6 | 🧭归纳 |
| RAG 为何不会死 | (a) 数据只增不减，长 context 总不够；(b) 模型对中段注意力差；(c) 节省 token 费用与延迟 | §6.0 | 🧭归纳 |
| Context construction 比喻 | = foundation model 的 feature engineering；给模型所需信息以处理输入 | §6.0 | 🧭归纳 |
| RAG 架构 | retriever（indexing + querying）+ generator；retriever 质量决定系统上限 | §6.1 | 🧭归纳 |
| Term-based 检索 | TF-IDF / Elasticsearch / BM25（Best Matching 第 25 代，强 baseline）；稀疏向量，词匹配 | §6.2 | 🧭归纳 |
| Embedding-based 检索 | 语义检索；可微调但易丢关键词；ANN 算法（FAISS / ScaNN / Annoy / Hnswlib）做近似最近邻 | §6.2 | 🧭归纳 |
| Hybrid search | term + embedding 组合；可串行（粗排→精排）或并行（RRF reciprocal rank fusion 融合排名） | §6.2 | 🧭归纳 |
| RAG 优化四大武器 | (1) Chunking（字符/词/句子/段落/递归分块 + token 分块 + 重叠）；(2) Reranking（粗排→精排，或按时间重排）；(3) Query rewriting（LLM 改写歧义 query）；(4) Contextual retrieval（Anthropic 给 chunk 附 50-100 tokens 上下文） | §6.3 | 🧭归纳 |
| Chunk size 经验 | 越小越多 → 召回广但易丢上下文；越大越少 → 召回窄但保完整；无万能值，需实验 | §6.3 | 🧭归纳 |
| 多模态 RAG | retriever 返回文本+图像（CLIP 等多模态 embedding）；表格数据走 text-to-SQL（语义解析+SQL 执行+生成） | §6.4 | 🧭归纳 |
| Agent = | FM + 工具（web 搜索/代码解释器/计算器/APIs）+ 规划（ReAct / Plan-and-Execute）+ 反思 | §6.4 | 🧭归纳 |
| Agent 四大失败模式 | (1) 工具用错；(2) 不该用工具时用；(3) 规划死循环；(4) 目标不可达 | §6.4 | 🧭归纳 |
| Agent 三种 memory | short-term（单对话内）/ long-term（跨对话）/ episodic（特定事件） | §6.5 | 🧭归纳 |
| RAG 评估原则 | 组件级 + 端到端双评；retriever 单独评（context precision/recall），最终落到"系统能否产生好答案" | §6.6 | 🧭归纳 |

## 五、微调与数据（成本陡升的两板斧）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| AI 工程实验次序 | 先 Prompt → 加 RAG → 还不行再 Finetuning；50-100 例微调通常就能看到改进，小数据无效大数据也基本无效 | §5.0, §7.2 | 🧭归纳 |
| Finetuning 三类 | (1) Continued pre-training（领域语料继续自监督预训练）；(2) SFT（指令-响应对）；(3) Preference finetuning / RLHF（指令-胜-败三元组） | §2.4, §7.1 | 🧭归纳 |
| 何时微调 | 输出格式不对 / 行为不符预期 / 不循指令 / 领域术语；JSON/YAML 输出是经典场景 | §7.2 | 🧭归纳 |
| 何时不微调 | (a) 任务型微调会损伤其他任务能力（catastrophic forgetting）；(b) 高质量标注数据贵且慢；(c) 需 ML 训练知识；(d) 需维护基础设施；(e) 数据飞轮跑得比微调更快 | §7.2 | 🧭归纳 |
| Finetuning vs RAG 一句话 | **Finetuning is for form, RAG is for facts** | §7.3 | 🧭归纳 |
| RAG + 微调可叠加 | Ovadia 2024 显示 43% 情况下 RAG+微调 > 单 RAG；二者非互斥 | §7.3 | 🧭归纳 |
| 训练内存四件套 | weights + activations + gradients + optimizer states；Adam 每 trainable param 多 3 value（grad + 2 opt state） | §7.4 | 🧭归纳 |
| 推理内存公式 | Inference memory = N × M × 1.2（N=params, M=bytes/param，1.2 = 权重 + 激活 + KV cache 经验值） | §7.4 | 🧭归纳 |
| 训练内存公式 | Training memory = weights + activations + gradients + optimizer states | §7.4 | 🧭归纳 |
| 数值格式铁三角 | FP32（4B/param，训练默认）/ FP16（2B/param，推理常用）/ BF16（2B/param，range 更宽精度更窄，TPU 优化）/ INT8 + INT4（量化） | §7.5 | 🧭归纳 |
| BF16 vs FP16 | 同 2 字节；BF16 range 宽、精度窄（大模型推理）；FP16 精度高、range 窄（小数据训练） | §7.5 | 🧭归纳 |
| 量化是减少内存最便宜银弹 | PTQ（post-training quantization）最常见；QLoRA = 4-bit 量化基础 + LoRA 微调 | §7.5, §7.6 | 🧭归纳 |
| PEFT 含义 | Parameter-efficient finetuning；只训一小部分参数（其他冻结），大幅减少训练显存 | §7.6 | 🧭归纳 |
| LoRA 工作原理 | 注入 trainable 低秩分解矩阵到 transformer 层；原始权重冻结 | §7.6 | 🧭归纳 |
| 模型合并 | 合并多个微调模型权重（线性平均 / SLERP 球面线性插值 / task arithmetic）；低成本"取各家之长" | §7.7 | 🧭归纳 |
| 1-bit LLM 萌芽 | BitNet b1.58 用 1.58 bit/param，性能比肩 16-bit Llama 2（≤3.9B） | §7.5 | 🧭归纳 |
| 数据决定模型上限 | "最好 ML 团队 + 无限算力，没数据训不出好模型" | §8.0 | 🧭归纳 |
| Data-centric AI vs Model-centric | 近年从"同数据集谁家模型好"转向"同模型谁家数据好"（DataComp / DataPerf） | §8.0 | 🧭归纳 |
| 数据三黄金 | quality / coverage / quantity；烹饪比喻：食材新鲜度 / 配料齐全 / 份量 | §8.1 | 🧭归纳 |
| Quality 六特性 | relevant + aligned + consistent + correctly formatted + unique + compliant | §8.1 | 🧭归纳 |
| LIMA 数据少而精 | 1,000 条精选 prompt-response 训 65B Llama，在 43% 案例上不输 GPT-4 | §8.1 | 🧭归纳 |
| Yi 10K > 数十万噪音 | 10K 精心构造指令 > 数十万噪音指令 | §8.1 | 🧭归纳 |
| Data flywheel 含义 | 应用产生用户数据 → 反馈回流训练 → 模型变好 → 用户更多 → 更多数据；大厂核心壁垒 | §8.2 | 🧭归纳 |
| 数据量经验法则 | 50-100 例起步看是否有效；finetuning technique + task complexity + base model performance 决定需要量 | §8.1 | 🧭归纳 |
| Ossification 含义 | 预训练可"冻结"模型权重，使其对微调数据适应性差；小模型比大模型更易 ossification | §8.1 | 🧭归纳 |
| 数据处理四步 | (1) Inspect（人工抽样看）；(2) Deduplicate（去重防偏见+污染）；(3) Clean/Filter（去低质）；(4) Format（统一 schema、用模型 tokenizer 切分） | §8.4 | 🧭归纳 |
| 标注指南的真相 | LinkedIn 说标注指南是 AI 工程流水线最难的部分；很多人放弃精标寄希望"模型自己悟"——风险大 | §8.2 | 🧭归纳 |
| Data augmentation vs synthesis | augmentation 从真实数据衍生（图像翻转）；synthesis 从无到有生成 | §8.3 | 🧭归纳 |
| Model Distillation | 小模型学大模型输出 logits/probabilities/text；可让 7B 模型逼近 65B | §8.3 | 🧭归纳 |
| AI 生成数据的隐忧 | 继承 base model 偏见 + 放大系统错误；解 = 与人类数据混合（人类数据作 quality anchor） | §8.3 | 🧭归纳 |

## 六、推理优化与生产架构

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 推理两阶段优化总开关 | Prefill（并行输入，compute-bound）+ Decode（逐 token 生成，memory bandwidth-bound）；生产常拆到不同机器 | §9.1 | 🧭归纳 |
| Online vs Batch API | Online 延迟优先；Batch 成本优先（OpenAI/Gemini 半价但分钟-小时级）；适合 batch：合成数据、定时报表、新客户 onboarding、模型迁移、推荐刷新、知识库重建 | §9.1 | 🧭归纳 |
| TTFT 含义 | Time to first token（prefill 阶段时间）；用户等待首字时常感知为"卡不卡" | §9.2 | 🧭归纳 |
| TPOT 含义 | Time per output token（decode 阶段每字时间）；120ms/字 ≈ 8 token/秒足够人眼阅读 | §9.2 | 🧭归纳 |
| Throughput vs Goodput | Throughput = 输出 token/秒；Goodput = 满足 SLO 的 RPS；盯着 high utilization 没意义 | §9.2 | 🧭归纳 |
| MFU / MBU | Model FLOP/s Utilization / Model Bandwidth Utilization；比 NVIDIA 官方 GPU utilization 更准 | §9.2 | 🧭归纳 |
| 推理占成本多大 | 高达 90%（vs 训练）——专用 inference chip（AWS Inferentia / Apple Neural Engine / MTIA / Edge TPU / Jetson）涌现 | §9.3 | 🧭归纳 |
| 模型优化四件套 | Quantization / Distillation / Pruning / Architecture Search | §9.4 | 🧭归纳 |
| 服务优化五大金刚 | (1) Batching（GPU 利用率 ↑，延迟 ↑）；(2) KV Cache（decode 时 K/V 缓存，每 token 从 O(n²) 降到 O(n)）；(3) Prompt Cache（重复 prompt 段跨请求复用）；(4) Speculative Decoding（小模型草拟→大模型 verify，一次出多 token）；(5) Continuous Batching（slot 空出来立即填新请求） | §9.5 | 🧭归纳 |
| KV Cache 工作原理 | 预计算 K/V 向量，decode 时复用，每 token 从 O(n²) 降到 O(n) | §9.5 | 🧭归纳 |
| Speculative Decoding | 小模型先生成 k 个候选 token；大模型一次 forward pass 判 OK 否；可一次出多 token，错了 fallback 大模型 | §9.5 | 🧭归纳 |
| Continuous Batching | slot 空出来立即填新请求，告别"凑满 batch 等最慢那个"；大幅提升 GPU 利用率 | §9.5 | 🧭归纳 |
| 架构五步走 | Step 1 Enhance Context（RAG/tool use）→ Step 2 Guardrails（input/output）→ Step 3 Router + Gateway → Step 4 Cache（exact/semantic）→ Step 5 Agent Patterns（loop/parallel/write actions） | §10.0 | 🧭归纳 |
| PII 保护三策略 | (1) 检测敏感数据（ID/电话/银行账号/人脸/内部关键词）；(2) Mask + placeholder 屏蔽（如 [PHONE NUMBER]）；(3) Reverse PII map 响应侧解掩 | §10.2 | 🧭归纳 |
| Guardrail 失败兜底 | 简单 retry（empty/格式错时重试）+ 并行取优响应 + 转人工（特定短语触发 / sentiment 分析触发 / turn 数阈值触发） | §10.2 | 🧭归纳 |
| Guardrail 开箱工具 | Meta Purple Llama / NVIDIA NeMo Guardrails / Azure PyRIT / Azure AI content filters / Perspective API / OpenAI content moderation API | §10.2 | 🧭归纳 |
| Router 工作机制 | Intent classifier（GPT-2/BERT/Llama 7B 等小模型）预测意图 → 分流到不同模型/agent/FAQ/人工；防 out-of-scope 省 API call | §10.3 | 🧭归纳 |
| Gateway 核心功能 | 统一接口 + access control + cost cap + fallback policy + load balancing；Portkey / MLflow / TrueFoundry / Kong 开箱即用 | §10.3 | 🧭归纳 |
| Exact vs Semantic Cache | Exact 强一致但命中率低；Semantic 命中率高但易引入数据泄露 + 阈值难调；personal/time-sensitive query 别 cache | §10.4 | 🧭归纳 |
| Semantic Cache 数据泄露 | user X 问"return policy for electronics" → 系统返回含 X 会员信息 → cache → user Y 问同一问题 → 拿到 X 的信息 | §10.4 | 🧭归纳 |
| Write Actions 风险 | Agent 调用外部工具改环境（发邮件/下单/转账）= 能力 ↑ 但风险 ↑ | §10.5 | 🧭归纳 |
| 监控三件套 | MTTD (mean time to detection) + MTTR (mean time to response) + CFR (change failure rate) | §10.6 | 🧭归纳 |
| 评估 ↔ 监控必须互通 | 评估指标是监控指标子集；监控发现的坏 case 反馈到评估 | §10.6 | 🧭归纳 |
| User Feedback 两类 | explicit（thumbs up/down、评分）vs implicit（重新生成、复制回答、放弃对话）；implicit 多但难解 | §10.7 | 🧭归纳 |
| Orchestration 框架 | LangChain / LlamaIndex / Haystack；管理多组件协同 + 数据流 + 状态；加复杂度，需要时再上 | §10.7 | 🧭归纳 |

## 八、AI 工程的"不要做"清单

| 反模式 | 为何不行 | 章节锚点 |
|---|---|---|
| 只懂 Prompt 工程 | "The problem is when prompt engineering is the only thing people know" | §5.0 |
| 用公共 benchmark 替代自家 eval | 公共 benchmark 快速饱和 + 不知自己任务的失败模式 | §3.1 |
| 不做评估就上线 | 上线却不知好坏比没上线更糟（撤不下来、浪费维护费） | §4.0 |
| 上线后立即全量部署 | CFR 高说明监控不够；先灰度再放大 | §10.6 |
| 用 Word 替代 Context 不解 | 模型对长 context 中段注意力差，长 ≠ 好用 | §5.3 |
| Long-context 可以取代 RAG | 数据只增不减；模型中段注意力差；省 token 费与延迟 | §6.0 |
| 用错 Chat template | 沉默的灾难（模型会做"合理"的事，但完全错） | §5.3 |
| Prompt 工具默认设置就上线 | 隐藏 API call 可能把账单打爆；默认模板常有 typo | §5.5 |
| Prompt 不版本管理 | 多人多版本，调试地狱；用 prompt catalog 集中版本化 | §5.4, §5.7 |
| 不分信息/行为问题就上微调 | 信息问题 → RAG；行为问题 → 微调；混了浪费资源 | §7.3 |
| 任务型微调想不影响其他任务 | catastrophic forgetting；多任务数据混合微调或用 MoE | §7.2 |
| 把所有数据都 cache | personal/time-sensitive query 不能 cache；PII 跨用户共享风险 | §10.4 |
| 用 Semantic Cache 但无阈值 | 易把 user X 的信息返回给 user Y | §10.4 |
| Agent 调外部工具前没 Guardrails | 一次 prompt injection 可能执行 SQL 拖库 / 发垃圾邮件 / 乱扣款 | §5.6, §10.2 |
| 评估与监控脱节 | 评估指标不映射监控指标 = 开发环境 100 分 / 生产 0 分 | §10.6 |
| 用 OSS 训练数据未查 license | 即便 dataset license 允许商用，原始数据可能不允许 | §8.2 |
