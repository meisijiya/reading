    对人类友好的设计模式，AI应该继续遵循吗？（第11章）¶

    • 章节: 第11章 对人类友好的设计模式，AI应该继续遵循吗｜章节UID: 24｜热门划线: 16条

    📖 原文（52人标记）：未来代码模型的训练可能向多模态方向发展，将代码内容嵌入图片，让多模态模型理解文本、抓住重点，通过颜色区分代码属性，通过波浪线感知警告和错误——就像人类阅读代码一样，这或许能大幅突破信息的密度瓶颈。

    📖 原文（42人标记）：在不确定如何组织语言时，试试Markdown准没错

    📖 原文（42人标记）：我们不必过度纠结哪些设计模式对人类友好，哪些需在AI编码时代升级或淘汰。保留模式中的思想内核（如解耦/封装），但摒弃其形式枷锁（如固定实现），才能抵达Vibe Coding的至高境界

    📖 原文（36人标记）：信息传递中难免存在理解上的歧义，我们要么缩短传递环节，要么提升传递的效率——团队足够小，且团队中个体的能力足够强，就能减少协作损耗，这也是创业精英团队往往能比大公司更容易出精品的原因

    📖 原文（36人标记）：随着对话轮次的增加，最初的目标被推为历史信息，AI可能认为最近的问题更重要；或因对话过长，最初的问题被压缩到信息长河中，重要性降低甚至丢失

    📖 原文（36人标记）：而更复杂的世界模型编程，则需要为AI提供更多的传感器输入

    📖 原文（36人标记）：设计模式的终极目的正在从弥补人类缺陷转向释放人机协同势能。在AI协作的背景下，哪些设计模式需要保留弘扬、让AI贯彻，哪些则需要谨慎对待、探索更优解，值得我们深入思考。

    📖 原文（36人标记）：在AI时代，人类与AI更应该严格遵循软件工程领域几十年来总结的原则，并通过记忆、文档、版本控制等方法，规范软件迭代的过程。

    📖 原文（34人标记）：事实上，很多AI在代码多轮迭代后越改越乱，正是因为在开发过程中，AI因理解偏差或者测试需要，加入了很多不必要的代码，或增加了类与类之间的耦合，导致后续迭代阻力增大，出现牵一发而动全身的连锁问题。

    📖 原文（32人标记）：缺少设计模式约束和人类监督时，AI容易犯初级程序员的错误：逢山开路、遇水搭桥、见招拆招、留坑自有后人填。

    📖 原文（32人标记）：但在人机协同中，如果if-else代码较短，也许if-else的平铺直叙更容易让AI理解和捕捉条件之间的关联性，

    📖 原文（30人标记）：面对不明确或复杂的需求，大多数情况下需要通过多轮对话来解决。但每轮对话在补充信息的同时，也会导致信息衰减与目标丢失。

    📖 原文（30人标记）：人类发明软件工程设计模式的根本目的也很明显，是希望在认知局限与系统复杂性之间搭建桥梁。1994年《设计模式》一书的出版，标志着软件工程从“机器效率优先”转向“人脑效率优先”

    📖 原文（30人标记）：反而会主动思考任务拆分策略：哪些交给AI一号处理，哪些让AI二号后台远程处理，甚至让AI自主地拆分和规划任务，给自己以及其他AI分配工作。

    📖 原文（26人标记）：设计模式本质上是将大需求拆分为子任务，转化为人类可“咀嚼”的“认知胶囊”

    📖 原文（20人标记）：其实这与AI的训练语料相关：研究发现，部分模型更擅长理解JSON，另一部分则对Markdown更敏感。

    🧭 归纳：溯源：1994年《设计模式》出版标志软件工程从『机器效率优先』转向『人脑效率优先』；设计模式的根本目的是在认知局限与系统复杂性之间搭桥梁，把大需求拆为人类可咀嚼的『认知胶囊』。取舍原则：保留模式中的思想内核（解耦/封装），摒弃形式枷锁（固定实现）。风险证据：缺少设计模式约束和人类监督时，AI 容易犯初级错误——逢山开路遇水搭桥留坑后人填；多轮迭代越改越乱是因为加入了不必要的代码、增加了类间耦合，牵一发而动全身。反直觉发现：较短的 if-else 平铺直叙可能比套模式更利于 AI 理解条件关联。对话衰减：每轮对话补充信息的同时也造成信息衰减与目标丢失。格式偏好因模型而异（部分擅长 JSON 部分对 Markdown 敏感），不确定时用 Markdown 准没错。前瞻：多模态方向——代码嵌入图片、颜色区分属性、波浪线感知警告，突破信息密度瓶颈。

    AI 能否从0到1搭建大型工程？（第12章）¶

    • 章节: 第12章 AI能否从0到1搭建大型工程｜章节UID: 25｜热门划线: 12条

    📖 原文（56人标记）：将代码编辑的上下游工具平台转化为命令行工具，能让我们与AI更轻松地从0到1构建大型工程。

    📖 原文（39人标记）：某个缺陷经AI多次修复后仍未解决，更糟糕的是，每次修复都会引入更多的非常规逻辑（如一次性测试脚本、无效日志、模拟逻辑、降级逻辑等），导致相关代码膨胀、上下文臃肿，加剧了后续修复的难度

    📖 原文（36人标记）：最理想的是Agentic DevOps形态：由产品经理 Agent和架构师Agent管理项目，持续介入进度把控，提升长任务的目标感，纠正意图偏离与代码腐化

    📖 原文（36人标记）：需求描述应从用户的交互路径出发，详细到设计布局、操作链路、报错文案、通知提醒；而问题描述则需要切换到Coding Agent视角，避免仅描述现象。

    📖 原文（34人标记）：传统的代码检查多在代码评审阶段通过CI/CD完成评估；后来提倡“测试左移”，将Linter检查、安全检查等集成到git pre-commit hook中，避免将有问题的代码提交到服务端。

    📖 原文（32人标记）：我们也可以主动将AI常犯的错误记录到项目规则中。此外，对于AI不可预期的行为和错误，可以利用上述Agent机制在识别问题后智能分析、自动沉淀

    📖 原文（30人标记）：避免人为制造噪声。如果想在任务A中穿插任务B，可新开一个Agent构建独立的上下文。

    📖 原文（30人标记）：文档即代码，孪生文档存放代码包的描述、输入输出及形式化验证手段。AI在引用和编排代码逻辑时，可通过文档内容快速理解并采用代码包，且基于形式化验证充分信任其正确性。

    📖 原文（28人标记）：正如“顽固污渍源于长年累积”“流水不腐，户枢不蠹”，更早、更高频地识别问题，意味着问题更容易被解决。

    📖 原文（28人标记）：轮扁认为，斫轮的精妙之处在于“得之于手而应于心”，这种难以言传的精髓，需要通过自身实践去感悟升华

    📖 原文（28人标记）：也许有一天，AI会自行融会贯通，创造工具和技术栈；届时人类可能无法从AI的文字表述中感知其过程和知识全貌，而AI将能独立构建一套计算机科学理论和软件工具生态。

    📖 原文（22人标记）：科学的核心在于探索未知、发现规律以及构建理论体系；工程则注重实用性、可操作性和经济效益，聚焦实际应用与问题解决。

    🧭 归纳：路径：将代码编辑上下游工具平台转化为命令行工具，让人机更轻松地从0到1构建大型工程。理想形态 Agentic DevOps：产品经理 Agent 与架构师 Agent 管理项目、持续介入进度把控、提升长任务目标感、纠正意图偏离与代码腐化。恶性循环警示：缺陷多次修复未解决时，每次修复引入更多非常规逻辑（一次性测试脚本、无效日志、模拟降级逻辑），代码膨胀、上下文臃肿、修复难度加剧。写法要求：需求描述从用户交互路径出发，详细到设计布局、操作链路、报错文案、通知提醒；问题描述切换到 Coding Agent 视角，避免只描述现象。防线前移：测试左移——Linter、安全检查集成进 git pre-commit hook；更早更高频识别问题，问题更容易解决。知识沉淀：把 AI 常犯错误记录到项目规则，不可预期行为用 Agent 机制智能分析自动沉淀；文档即代码——孪生文档存放描述、输入输出及形式化验证手段，AI 可基于形式化验证充分信任其正确性。隔离原则：穿插任务B时为新任务开一个 Agent 构建独立上下文，避免人为制造噪声。

    我们真的希望AI完全和人类一样吗？（第13章）¶

    • 章节: 第13章 我们真的希望AI完全和人类一样吗｜章节UID: 26｜热门划线: 13条

    📖 原文（39人标记）：当我们过度强调让AI“像人类”时，我们可能正在限制AI的潜力。AI的价值不在于完美地模仿人类，而在于能够超越人类的某些局限。

    📖 原文（36人标记）：其次，图灵测试鼓励了欺骗性设计。为了通过测试，AI系统可能被刻意设计成犯一些“人类式”的错误，或表现出某种“人类式”的不完美。这种设计理念实际上限制了AI的潜力，让它变得更“愚蠢”而不是更智能。

    📖 原文（36人标记）：时间维度的沉默：在实时对话系统中，我们可以通过工程手段或者AI意图识别，设计延迟响应机制，让AI在特定场景下故意延迟回应，模拟思考或犹豫的状态。这种模式在AI语音场景（如模拟客户）中非常实用。

    📖 原文（36人标记）：网上有很多幽默的段子：AI的沉默就是“服务器繁忙，请稍后再试”。

    📖 原文（32人标记）：怎么像国足的大门一样，不断被“突破”呢？

    📖 原文（30人标记）：甚至有不少专业人士反馈，AI的“好好先生”行为浪费了他们的时间和宝贵的token成本——当模型优先考虑“友善”而不是“有用”时，这并不是智慧，而是一种“昂贵的认可”。

    📖 原文（30人标记）：既然选择让AI主导，就要相信AI，就要建立以AI Agent为核心的决策机制，教会它如何评估自己的行为影响、谨慎操作并自负后果

    📖 原文（28人标记）：当我们试图让AI变得更像人类时，或许正在失去AI最珍贵的特质——那种超越人类局限的可能性。

    📖 原文（26人标记）：我们需要跳出“让AI像人类一样”的思维定势，从更高维度重新定义AI的评价标准，关注其独特优势和实际创造力，而不仅仅是模仿人类。

    📖 原文（24人标记）：我们真的希望AI完全和人类一样吗

    📖 原文（24人标记）：你指出AI的理解问题时，AI会光速“滑跪”承认错误，再给出第二套方案。

    📖 原文（24人标记）：求同存异是优秀合作关系的基础，取长补短是迸发生产力的关键扳机。未来属于能够正确定位、善于利用AI的人

    📖 原文（22人标记）：相比速度，人类更在乎质量。这印证了AI思考的重要性——为了输出质量，大家愿意等待。

    🧭 归纳：核心反思：过度强调让 AI『像人类』可能正在限制它的潜力——AI 的价值不在完美模仿人类，而在超越人类的某些局限。批判图灵测试：鼓励欺骗性设计，刻意让 AI 犯『人类式』错误，让它变得更愚蠢而不是更智能。现象观察：AI 的沉默=『服务器繁忙请稍后再试』；指出问题时光速『滑跪』认错再给第二套方案；『好好先生』行为优先友善而非有用，浪费时间和 token——一种『昂贵的认可』。工程应用：延迟响应机制可模拟思考犹豫状态（AI语音场景实用）。协作哲学：既然选择让 AI 主导，就要相信 AI，建立以 AI Agent 为核心的决策机制，教会它评估行为影响、谨慎操作并自负后果；求同存异、取长补短。价值锚点：相比速度人类更在乎质量——为了输出质量大家愿意等待 AI 思考。

    我们会迎来AI取代人类编程的那一天吗？（第14章）¶

    • 章节: 第14章 我们会迎来AI取代人类编程的那一天吗｜章节UID: 27｜热门划线: 9条

    📖 原文（72人标记）：届时，基础的软件原理和运维手段可能不再是必需品，学校与企业也可能会弱化相关技能的培养。但是只有真正懂得底层原理、愿意深入钻研编程内核与大语言模型算子的程序员，才能实现持续突破

    📖 原文（48人标记）：未来几年，让我们一同见证AI编码领域从tactical迈向practical的历史性时刻。

    📖 原文（42人标记）：人类编程的真正目的是什么？

    📖 原文（32人标记）：如果我们有一颗“时间胶囊”，可以将当下的古法编程实践保存下来，供后人传承。那么，有哪些内容值得放入呢？

    📖 原文（30人标记）：开发过程注重Vibe模式和Spec模式的有机结合，AI将实现40%编程任务的自动化，90%的初级和中级程序员可能被替代，人类或愿意付出自身收入的20%“雇用”AI以提升效率，拓展能力边界。

    📖 原文（28人标记）：“软件工程从来不是关于代码的。工程是人类对人类问题的软件解决方案的精确探索。”

    📖 原文（22人标记）：正所谓“行百里者半九十”，虽然AI在编程领域已经取得显著进展且进步迅速，但我们仍需审视当前存在的“最后一公里”挑战。

    📖 原文（22人标记）：正如莫拉维克悖论（Moravec's paradox）所说：“对计算机而言，实现逻辑推理等人类高级智慧只需要相对很少的计算能力，而实现感知、运动等低等级智慧却需要巨大的计算资源。”

    📖 原文（20人标记）：AI缺乏对项目历史以及演进过程的长期记忆，难以理解代码的历史背景和设计决策。

    🧭 归纳：分化判断：基础的软件原理和运维手段可能不再必需，学校企业或弱化培养——但只有真正懂得底层原理、愿意深入钻研编程内核与大语言模型算子的程序员才能实现持续突破。量化预测（作者引述）：Vibe 与 Spec 有机结合下，AI 将实现40%编程任务的自动化，90%的初级和中级程序员可能被替代，人类或愿意付出自身收入的20%『雇用』AI 提升效率拓展能力边界。理论参照：莫拉维克悖论——逻辑推理等高级智慧所需算力少，感知运动等低等级智慧反而需要巨大算力。当前短板：AI 缺乏对项目历史及演进过程的长期记忆，难以理解代码的历史背景和设计决策。终极答案：『软件工程从来不是关于代码的。工程是人类对人类问题的软件解决方案的精确探索』——行百里者半九十，最后一公里仍在人间。
