## 一、场景 → 方案速查

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 判断「要不要拆微服务」 | 性能不是目的（云时代算力近无限）；真驱动力=异构需求/人才制约/甲方要求/快速变化业务/历史包袱；且须满足四前提（组织接受康威定律、有架构专家、自动化以自治为目标、复杂性已成主要矛盾） | §16.1–§16.2 | 🧭归纳 |
| 定微服务粒度 | 下界=独立（发布/部署/运行/测试）+内聚+完备；上界=2 Pizza Team 一个研发周期的需求范围；沟通成本 n×(n−1)/2，分治降为 O(N log N) | §16.3 | 🧭归纳 |
| 远程调用选 RPC 还是 REST | RPC=面向过程（表示数据/传递数据/表示方法三问题，现代框架只能「对象/性能/简洁」三选一）；REST=面向资源（六原则，RMM 0–3 级）；追求极限性能或事务一致性选 RPC 风格，面向公网开放接口选 REST | §2.1–§2.2 | 🧭归纳 |
| 本地事务为什么可靠 | ARIES：WAL（先写日志后写数据）+ Undo/Redo；崩溃恢复 Analysis→Redo→Undo 三步；隔离性靠锁+隔离级别，MVCC 读不阻塞写 | §3.1 | 🧭归纳 |
| 跨服务数据一致怎么选 | 可靠事件队列（最简单，最终一致，消息带事务 ID 幂等）→ TCC（要隔离性，业务侵入大）→ SAGA（长流程，补偿反向操作）；XA/2PC 仅限同进程多库，有协调者单点风险 | §3.2–§3.4 | 🧭归纳 |
| 注册中心选 AP 还是 CP | Eureka=AP（异步复制，牺牲一致性换可用）；Consul/ZooKeeper/etcd=CP（Raft/ZAB 多数写入）；判据=分区后本地能否继续提供正确服务 | §7.1 | 🧭归纳 |
| 服务雪崩怎么办 | 容错三模式：断路器（CLOSED/OPEN/HALF-OPEN，故障率达标即跳闸）+舱壁隔离（线程池/信号量隔离故障服务）+重试（仅瞬时故障+仅幂等+超时/次数双终止 ≤5 次）；七种策略按语义选：Failover/Failfast/Failsafe/Failsilent/Failback/Forking/Broadcast | §8.1 | 🧭归纳 |
| 接口被突发流量打垮 | 四类限流：计数器（临界突刺 60+60=120）→滑动窗口→漏桶（恒定速率，削平突发）→令牌桶（可预存额度应对突发）；分布式限流把令牌货币化，本地扣减勿每次远端统计 | §8.2 | 🧭归纳 |
| 内部服务互信怎么做 | 摒弃边界安全拥抱零信任：身份只来源于证书而非 IP，mTLS 双向认证；Istio PeerAuthentication STRICT/Permissive 逐个迁移，授权用 AuthorizationPolicy（from/to/when） | §9.1–§9.2 | 🧭归纳 |
| 出了问题看不到现场 | 可观测性三支柱一起上：Logging（MDC 带 TraceID→Filebeat→Kafka 削峰→Grok 结构化→ES 冷热分层）+ Tracing（Trace/Span，边车收集最透明）+ Metrics（Prometheus Pull+TSDB+告警） | §10.1–§10.3 | 🧭归纳 |
| 理解容器到底是什么 | chroot(1979) 文件隔离→Namespace(2002) 访问隔离→cgroups(2006) 资源配额→LXC 封装系统→Docker(2013) 封装应用→Kubernetes(2014) 封装集群；Pod=补足「进程组」概念的容器组 | §11.1–§11.2 | 🧭归纳 |
| K8s 应用打包方式怎么选 | Kustomize（YAML Base/Overlay/Patch，无 DSL）→ Helm（Chart+Release，模拟 apt）→ Operator（CRD+自定义控制器，有状态运维）→ OAM（开发/运维/平台关注点分离） | §11.3 | 🧭归纳 |
| Pod 存储怎么持久化 | Docker Bind/Volume/tmpfs 三挂载；K8s PV/PVC 一对一独占易浪费 → StorageClass 动态分配；存储类型：块存储（低延迟 RWO）/文件存储 NFS/EFS（可共享，容器首选）/对象存储 S3（便宜，CDN 备份归档） | §13.1–§13.2 | 🧭归纳 |
| Pod 被莫名杀掉排查 | 先看 QoS 等级：Guaranteed（limits=requests）>Burstable>BestEffort（最先被驱逐）；驱逐阈值默认 memory<100Mi 等；requests 给调度器、limits 给 cgroups 的双轨制是根因 | §14.1–§14.3 | 🧭归纳 |
| 要不要上服务网格 | 通信五阶段演进终态：sidecar 代理（iptables 流量劫持）+控制平面（xDS 分发配置）把熔断/认证/监控下沉基础设施，应用零改造；代价=每跳多两代理、运维复杂度（Istio 1.5 都因此回归单体 istiod） | §15.1–§15.2 | 🧭归纳 |
| 架构腐化了怎么办 | 腐化只能延缓无法根治；唯一有效办法=演进式设计——像「换房子」不像「造房子」，持续小步演进而非一次性重写 | §16.4.2 | 🧭归纳 |

## 二、关键数字与概念

| 数字 / 概念 | 含义 | 章节锚点 |
|---|---|---|
| **八大分布式谬误** | 网络可靠/延迟为零/带宽无限/网络安全/拓扑不变/管理员唯一/传输成本零/网络同质——透明 RPC 必须为其埋单 | §2.1 |
| **CAP** | P 是网络天然属性不可舍弃，实际只在 AP 与 CP 之间选；Gilbert & Lynch 2002 年证明成定理 | §3.4 |
| **Quorum 过半机制** | 过半节点接受即生效，容忍 <1/2 节点失联；Basic Paxos 两阶段（准备+批准） | §6.1 |
| **Safety vs Liveness** | 协定性=坏事一定不发生；终止性=好事终将发生；Basic Paxos 并发交替提议会活锁（随机超时规避），Multi Paxos 选主化解 | §6.1–§6.2 |
| **反熵 vs 传谣** | Gossip 两种传播模式：反熵全量同步（开销大）、传谣只传变更（冗余小）；不一致窗口与消息冗余不可兼得 | §6.3 |
| **断路器跳闸线** | 10s 内 ≥20 请求且故障率 ≥50% 才 OPEN；HALF-OPEN 试探恢复；熔断≠降级（降级是熔断后兜底逻辑） | §8.1 |
| **重试放大 256 倍** | Zuul×Feign×Ribbon 各重试 4 次 = 4⁴=256 次调用——重试必须全局设预算 | §8.1 |
| **令牌桶 vs 漏桶** | 漏桶恒定出水平滑流量但难应变速率突变；令牌桶放牌速率可调、能预存余量应对突发 | §8.2 |
| **VXLAN** | IANA 分配 UDP 4789 端口；24 位 VNI≈1677 万网络；额外 50 字节封装头；只要三层可达即可部署 | §12.1 |
| **CNM vs CNI** | Docker libnetwork(2015.05) vs K8s CNI(2015.07)，五年战争 CNI 完胜（K8s/OpenShift/Mesos/CF 全支持） | §12.2 |
| **CSI 2704 行 vs FlexVolume 155 行** | 存储扩展规范完善度对比；K8s 1.14 起把 In-Tree 驱动迁出为 Out-of-Tree CSI 实现 | §13.2 |
| **CPU 可压缩 / 内存不可压缩** | CPU 不足只饥饿不杀（1 Core=1000m）；内存不足 OOM 直接杀容器——这是驱逐机制的根源 | §14.1 |
| **QoS 三档默认阈值** | Guaranteed（limits=requests）/ Burstable / BestEffort；kubelet 默认驱逐线 memory.available<100Mi、nodefs<10%、imagefs<15% | §14.2–§14.3 |
| **xDS 协议族** | Envoy 把转发行为抽象为 Listener(LDS)/Cluster(CDS+EDS)/Router(RDS)，数据面配置的事实标准 | §15.1 |
| **邓巴数 150** | 人际社交上界（5 知己/15 伙伴/35 朋友/150 说得上话）——微服务团队规模的人类学依据 | §16.3 |

## 三、技术选型对照

| 决策点 | 对照项 | 结论 | 章节锚点 |
|---|---|---|---|
| 强制缓存 vs 协商缓存 | Expires/Cache-Control ↔ Last-Modified/ETag | 有把握定时效用强制（Cache-Control 优先于 Expires）；没把握用协商（ETag 一致性最强但有哈希开销） | §4.1 |
| HTTP/2 vs HTTP/3(QUIC) | TCP 多路复用 ↔ UDP 重造可靠传输 | HTTP/2 解决队首阻塞但受制于 TCP；QUIC 面向移动设备，连接标识符支持网络切换不断连 | §4.3 |
| 负载均衡层级 | 二/三层（DR/IP-Tunnel）↔ 四层（LVS）↔ 七层（Nginx/网关） | 四层性能高功能弱，七层功能强性能弱；主流组合=四层做入口+七层做路由过滤 | §4.5, §7.2 |
| Cookie-Session vs JWT | 服务端有状态 ↔ 客户端自包含 | Session 安全性好但扩容需共享状态；JWT 无状态利扩展但**默认明文只防篡改不防泄漏**、无法主动失效 | §5.3 |
| 密码存储 | MD5/SHA ↔ 加盐慢哈希 | 必须 BCrypt/PBKDF2/scrypt 等慢哈希+随机盐，用成本参数对抗算力增长 | §5.4 |
| OAuth2 四模式 | 授权码/隐式/密码/客户端 | Web 应用=授权码模式（两次重定向最严谨）；纯前端=隐式（禁 Refresh Token）；可信第一方=密码；纯机器间=客户端凭证 | §5.2 |
| 容器 LB：客户端 vs 边车代理 | 进程内 Ribbon ↔ Sidecar Envoy | 客户端 LB 零网络开销但绑语言；边车对应用透明、统一治理，是服务网格方向 | §7.3 |
| 追踪数据收集 | 日志法 ↔ 服务法 ↔ 边车法 | Sleuth 日志侵入低但不精确；Java Agent 探针精确但耗资源；Envoy 边车最理想但只见调用不见方法级 | §10.2 |
| Prometheus 采集 | Pull ↔ Push | Pull 主流（健康状态自带）；Push Gateway 只兜短生命周期任务/NAT 场景 | §10.3 |
