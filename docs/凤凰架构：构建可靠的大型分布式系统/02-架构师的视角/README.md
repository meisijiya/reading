> 📖 **原文**（§4.1.1）：HTTP的强制缓存对一致性问题的处理策略就如它的名字一样，十分直接：假设在某个时点到来以前，譬如收到响应后的10分钟内，资源的内容和状态一定不会被改变，因此客户端可以无须经过任何请求，在该时点前一直持有和使用该资源的本地缓存副本。

> 📖 **原文**（§4.1.1）：Cache-Control是HTTP/1.1协议中定义的强制缓存Header，它的语义比Expires丰富了很多，如果Cache-Control和Expires同时存在，并且语义存在冲突（譬如Expires与max-age/s-maxage冲突）的话，规定必须以Cache-Control为准。

> 📖 **原文**（§4.1.2）：强制缓存是基于时效性的，但无论是人还是服务器，其实多数情况下并没有什么把握去承诺某项资源多久不会发生变化。另外一种基于变化检测的缓存机制，在一致性上会有比强制缓存更好的表现，但需要一次变化检测的交互开销，性能上就会略差一些，这种基于检测的缓存机制，通常被称为“协商缓存”。

> 📖 **原文**（§4.2）：无论是使用浏览器抑或是在程序代码中访问某个网址域名，譬如以www.icyfenix.com.cn为例，如果没有缓存的话，都会先经过DNS服务器的解析翻译，找到域名对应的IP地址才能开始通信，这项操作是操作系统自动完成的，一般不需要用户程序介入。

> 📖 **原文**（§4.3.1）：有了多路复用的支持，HTTP/2就可以对每个域名只维持一个TCP连接（One Connection Per Origin）并以任意顺序传输任意数量的资源了，这样既减轻了服务器的连接压力，也不需要开发者去考虑域名分片这种事情来突破浏览器对每个域名最多6个的连接数限制。

> 🧭 **归纳**：①**透明多级分流**：用户请求流经客户端缓存→DNS→CDN→网关/负载均衡→服务端缓存→DB；6 级共同实现"分布广阔/意识不到"；原则是减少单点 + 奥卡姆剃刀（不是每系统都要追求高并发）。②**客户端缓存**：强制缓存（Expires 绝对时间受本地时钟干扰，HTTP/1.1 的 Cache-Control 用 max-age/s-maxage/public/private/no-cache/no-store/no-transform 替代）vs 协商缓存（Last-Modified/If-Modified-Since 秒级粒度，ETag/If-None-Match 一致性最强但每次哈希开销，Vary Header 处理 Accept*/Content-* 多版本）。③**DNS**：递归查询从根→cn→com.cn→...→权威服务器；A/AAAA/CNAME 多条记录可做智能线路（按地区/ISP）；HTTPDNS/DoH 绕过本地 DNS 避免劫持。④**传输链路**：YSlow-23 中雪碧图/合并/内联/域名分片都是为了对抗 HTTP over TCP 的矛盾（HTTP 短小 vs TCP 长连接）；HTTP/2 多路复用（Frame+Stream ID）解决队首阻塞，单域名单 TCP 连接；HTTP/1.1 用 Chunked Transfer Encoding 解即时压缩 vs 持久连接冲突；QUIC（HTTP/3）以 UDP 为底自带可靠传输，移动网络切换靠连接标识符复用。⑤**CDN**：通过 CNAME 链 + 智能 DNS 把用户路由到最近边缘节点；分发方式 Push 主动推送（双十一预热）/Pull 被动回源；CDN 还能做协议升级、安全防御、HSTS、状态缓存、QoS。⑥**负载均衡**：4 层（数据链路层改 MAC=DSR/三角传输、网络层改 IP=IP Tunnel/NAT）vs 7 层（反向代理，明文 HTTP 解析后转发；可做 SYN Flood 过滤、降级熔断）；策略有轮询/权重轮询/随机/一致性哈希/响应速度/最少连接；软件 LVS 内核态性能最高，Nginx/HAProxy 用户态功能强。⑦**服务端缓存**：四大属性=吞吐量（OPS）+命中率+扩展功能+分布式；淘汰策略 FIFO→LRU→LFU→TinyLFU（Count-Min Sketch + 滑动时间窗）→W-TinyLFU（Window Cache LRU + Main Cache 分段 LFU）；分布式缓存分复制式（JBossCache，写入代价 O(n²)，已淘汰）与集中式（Redis，AP 式，跨语言但序列化成）；多级缓存=进程内一级 + 分布式二级，变更以分布式为准。⑧**缓存四大风险**：穿透（不存在数据每次回源→缓存空值或布隆过滤器）、击穿（热点过期并发打 DB→加锁或代码管理）、雪崩（大批同 TTL 同时过期→随机 TTL + 多级缓存 + 集群）、污染（更新时序导致不一致→Cache Aside 模式：写数据源→失效缓存，下次回填）。

> 📖 **原文**（§5.2.1）：RBAC模型在业界中有多种说法，其中以美国George Mason大学信息安全技术实验室提出的RBAC96模型最具系统性，得到了普遍的认可。为了避免对每一个用户设定权限，RBAC将权限从用户身上剥离，改为绑定到“角色”（Role）上，将权限控制变为对“角色拥有操作哪些资源的许可”这个逻辑表达式的值是否为真的求解过程。

> 📖 **原文**（§5.2.2）：OAuth 2给出了多种解决办法，这些办法的共同特征是以令牌（Token）代替用户密码作为授权的凭证。有了令牌之后，哪怕令牌被泄漏，也不会导致密码的泄漏；令牌上可以设定访问资源的范围以及时效性；每个应用都持有独立的令牌，任何一个失效都不会波及其他。

> 📖 **原文**（§5.3.1）：Cookie-Session方案在本章的主题“安全性”上其实是有一定先天优势的：状态信息都存储于服务端，只要依靠客户端的同源策略和HTTPS的传输层安全，保证Cookie中的键值不被窃取而出现被冒认身份的情况，就能完全规避掉信息在传输过程中被泄漏和篡改的风险。

> 📖 **原文**（§5.3.2）：请特别注意是明文，JWT只解决篡改的问题，并不解决泄漏的问题，因此令牌默认是不加密的。

> 📖 **原文**（§5.4.3）：慢哈希函数是指执行时间可以调节的哈希函数，通常是以控制调用次数来实现的。BCrypt算法就是一种典型的慢哈希函数，它做哈希计算时接受盐值Salt和执行成本Cost两个参数③。

> 📖 **原文**（§5.5.2）：CA作为受信任的第三方，承担公钥体系中公钥的合法性检验的责任。可是，这里和现实世界仍然有一些区别，在现实世界你去找公安局，其办公大楼不大可能是剧场布景冒认的；而在网络世界，在假设所有网络传输都有可能被截获冒认的前提下，“去CA中心进行认证”本身也是一种网络操作

> 📖 **原文**（§5.5.3）：2018年，最新的TLS 1.3（RFC 8446）发布，比起前面版本相对温和的升级，TLS 1.3做出了一些激烈的改动，修改了从1.0起一直没有大变化的两轮四次（2-RTT）握手，首次连接仅需一轮（1-RTT）握手即可完成，在连接复用支持时，甚至将TLS 1.2原本的1-RTT下降到0-RTT，显著提升了访问速度。

> 📖 **原文**（§5.6）：上述的讨论大概不会有统一、正确的结论，但是在Java里确实有验证的标准做法，笔者提倡的做法是把校验行为从分层中剥离出来，不是在哪一层做，而是在Bean上做，即Java Bean Validation。

> 🧭 **归纳**：①**安全的 6 个面**：认证（你是谁）、授权（你能干什么）、凭证（你如何证明）、保密（敏感数据不泄漏）、传输（不被窃听篡改冒充）、验证（输入数据合乎规则）。②**认证 = 3 层 × 多方案**：通信信道（SSL/TLS 证书）、协议（HTTP Basic/Digest/Bearer/HOBA）、内容（Web 表单，2019 W3C WebAuthn 用生物识别/物理密钥取代密码，FIDO 联盟制定）；Java 体系 JAAS（代码+用户双层太复杂失败）→ Spring Security（hasRole/hasAuthority，角色自动带 ROLE_ 前缀）。③**授权 = RBAC + OAuth 2**：RBAC96（George Mason 大学）= User-Role-Permission-Session-Resource-Operation，"许可"解耦操作与资源多对多；RBAC-1 角色继承、RBAC-2 互斥（会计 vs 出纳）+ 基数约束；垂直权限（功能）易抽象，水平权限（数据）难通用。OAuth 2（RFC 6749）= 第三方授权，4 种模式：授权码（严谨，ClientID+ClientSecret，两次重定向）、隐式（纯前端，Fragment 传 Token，禁 Refresh Token）、密码（用户明文给第三方，仅限高度可信，Fenix's Bookstore 用）、客户端（无资源所有者，服务间调用，如订单清理定时服务）。④**凭证 = Cookie-Session vs JWT**：服务端有状态（CAP 不可兼得：亲和式/复制式/集中式）vs 客户端无状态（JWT 三段：Header 签名算法+Payload Base64URL 明文+Signature HMAC-SHA256 或非对称 RSA-SHA256）；JWT 7 个推荐 Claim（iss/exp/sub/aud/nbf/iat/jti）；JWT 缺点：难主动失效（要黑名单→退化成有状态）、易重放（信道层解决）、携带数据有限（Header 受 Tomcat 8KB/Nginx 4KB 限制）、客户端存储难。⑤**保密**：6 级保密强度（摘要→加盐哈希→动态盐值→动态令牌→HTTPS→U盾/双因素/物理隔离），唯一绝对安全是一次性密码（香农证明）；客户端加密无意义（中间人攻击可劫持整个服务）但服务端加密有意义（防拖库）；密码存储流程：客户端 MD5+固定盐 → 客户端 BCrypt（慢哈希 Cost=10，210 次）→ 服务端 SecureRandom 生成 36 字节 server_salt → SHA256(client_hash + server_salt) 存库；验证流程同加密流程再比对。⑥**传输安全层**：密码学三件套 = 摘要（哈希不可逆，MD5/SHA 雪崩效应）、对称加密（AES，性能高但密钥分发难）、非对称加密（RSA/ECC，公钥加密+私钥签名，解决蛋鸡悖论）；现实用混合加密（非对称传对称密钥，对称加密数据）；数字证书 X.509 走 PKI/CA 链，浏览器预置根证书打破"鸡生蛋"循环；TLS 1.2 四次握手（Client Hello→Server Hello→Client Finished→Server Finished）协商协议版本+随机数+密码学套件+证书+PreMasterSecret；TLS 1.3 仅需 1-RTT（甚至 0-RTT 连接复用）。⑦**验证**：Java Bean Validation（JSR 303→349→380），把校验从分层剥离挂在 Bean 上；内置注解（@NotNull/@Pattern/@Email/@Size 等）做格式校验，自定义注解（@UniqueAccount/@AuthenticatedAccount/@NotConflictAccount）做业务校验；不带业务的注解放类定义内自动运行，带业务的注解放外面按需触发（避免重复执行副作用）；分组校验应对"新增/修改/删除"差异。
