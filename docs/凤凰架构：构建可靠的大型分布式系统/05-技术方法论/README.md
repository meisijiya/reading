## §16 第16章 向微服务迈进

> 📖 **原文**（§16.1）：有人会说微服务是信息系统发展的必然阶段，为了应对日益庞大的压力，获得更好的性能，自然会演进至能够扩缩自如的微服务架构。

> 📖 **原文**（§16.1）：微服务最主要的目的是对系统进行有效拆分，实现物理层面的隔离，微服务的核心价值就是拆分之后的系统能够让局部的单个服务有可能实现敏捷地卸载、部署、开发、升级，而局部的持续更迭，是系统整体具备Phoenix特性的必要条件。

> 📖 **原文**（§16.2）：康威定律尝试使用社会学的方法去解释软件研发中的问题，其核心观点是“沟通决定设计”（Communication Dictate Design）

> 📖 **原文**（§16.2）：笔者在1.4节中曾写到“作为一个普通的服务开发人员，作为一个螺丝钉式的程序员，微服务架构是友善的。可是，微服务对架构者是满满的恶意，对架构能力要求已提升到史无前例的程度”。

> 📖 **原文**（§16.2）：微服务自动化的最终目的是构筑可持续的生态系统。

> 📖 **原文**（§16.3）：微服务粒度的下界是它至少应满足独立——能够独立发布、独立部署、独立运行与独立测试，内聚——强相关的功能与数据在同一个服务中处理，完备——一个服务包含至少一项业务实体与对应的完整操作。

> 📖 **原文**（§16.3）：微服务粒度的上界是一个2 Pizza Team能够在一个研发周期内完成的全部需求范围。

> 📖 **原文**（§16.4.1）：我们可以进一步量化地推导出前文已经使用过的一个结论：软件规模小时微服务的复杂度高于单体系统，规模大时则相反。

> 📖 **原文**（§16.4.1）：假如只能用一个词来形容微服务解决问题的核心思想，笔者给的答案就是“分治”，这既是微服务的基本特征，也是微服务应对复杂性的手段。

> 📖 **原文**（§16.4.2）：架构腐化只能延缓，无法避免。

> 📖 **原文**（§16.4.2）：治理架构腐化唯一有效的办法是演进式的设计，这点与生物族群的延续也很像，流水不腐，户枢不蠹。

> 🧭 **归纳**：第16章是"避坑"指南，关键词：①**驱动力** = 异构能力需求 / 人才制约 / 甲方商业要求 / 快速变化业务 / 历史包袱沉重系统——性能**不是**主要目的（云时代硬件近乎无限，分拆不会凭空产生性能）。②**四个前提**：a) 决策者接受康威定律并同步调整组织（架构是社交活动，涉及利益再分配）；b) 团队里有撑得起主干的架构 / 运维专家（Kubernetes/Istio/Spring Cloud 也不能替代人）；c) 自动化与监控度量以**自治**为目标——警惕"套娃悖论"（监控本身也要被监控）和自动化异化为"恶龙"；d) 复杂性已成为制约生产力的主要矛盾（已在图16-2生产力曲线交叉点之后）。③**粒度上下界**：下界 = **独立**（独立发布/部署/运行/测试）+ **内聚**（强相关功能 + 数据同处）+ **完备**（≥1 个完整业务实体）；上界 = **2 Pizza Team**（6~12 人）一个研发周期内的全部需求。沟通成本 n×(n–1)/2 ≈ O(N²) → 分治降为 O(N log N)；邓巴数 150 = 人际社交上界。④**治理双视角**：静态 = "正确执行"，复杂度 = O(kN) + O(N²)（单体）/ O(kN) + O(N log N)（微服务）——高次项差异决定大规模时微服务占优；动态 = "持续保持"，**架构腐化只能延缓、不能根治**，唯一解药是**演进式设计**（"换房子"而非"造房子"）。一句话：微服务 = 用**分治**控制**沟通成本**，但**认知负荷**更重——本质是把人的协作成本从 O(N²) 降到 O(N log N)，用规模换治理。
