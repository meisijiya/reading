## 模块一 基础与建模（§1–§4）

### §1 第1章 追根问底微服务

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 评估是否采用微服务 | 微服务不是目标，先想清楚目标，再问"有没有更简单的方法" | §3.1 | 🧭归纳 |
| 初创公司 / 5 人以下小团队 | 不推荐微服务（"微服务税"耗资源，单体更划算） | §1.7.1 | 🧭归纳 |
| 100 人规模协作 / SaaS 全天候 | 适合微服务（独立发布 + 可扩展） | §1.7.2 | 🧭归纳 |
| 客户自部署型产品（Windows 安装包） | 不适合微服务（运维复杂度压在用户身上） | §1.7.1 | 🧭归纳 |
| 业务变更常跨越 UI/后端/数据库三层 | 按业务能力垂直切分（端到端切片），而非技术分层 | §1.2.2 / §1.2.6 | 🧭归纳 |
| 多个团队争用同一段代码（交付争用） | 微服务可沿业务边界划所有权，但仍非银弹 | §1 / §1.3.4 | 🧭归纳 |
| 评估"微服务应该多大" | 不要纠结大小，关注"你能管理多少个微服务"和"边界是否稳定" | §1.2.4 | 🧭归纳 |
| 准备上微服务的新架构 | 日志聚合是采用微服务的先决条件 | §1.4.1 | 🧭归纳 |
| 3 个微服务就考虑上 Kubernetes | 等管理部署开始令人头疼时再考虑；先让别人托管 | §1.4.2 | 🧭归纳 |
| 想用微服务解决 ACID 跨服务事务 | 微服务不提供；放弃分布式事务，走 Saga/最终一致性 | §1.6.9 | 🧭归纳 |
| 想要降本 | 微服务短期成本更高，是增加利润的方法但不一定降低成本 | §1.6.3 | 🧭归纳 |

| 数字 | 含义 | 锚点 |

### §2 第2章 微服务建模

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 划分微服务边界不确定怎么开始 | 围绕业务领域建模（DDD 默认起点），但要混合其他方法 | §2.7 | 🧭归纳 |
| 多个微服务需要被同时修改才能上新功能 | 内聚不够——把"一起变化的代码"放一起 | §2.2.2 | 🧭归纳 |
| 一个微服务依赖多个下游微服务 | 警惕"逻辑过于集中"；领域耦合仍要保持最低限度 | §2.3.1 | 🧭归纳 |
| 上下游之间传递数据仅为下下游所需 | 隐藏需求（让中介服务收集数据）或透明传递 | §2.3.2 | 🧭归纳 |
| 多个微服务共享同一数据库 | 公共耦合，通常不可接受；明确禁止，除非只读静态数据 | §2.3.3 | 🧭归纳 |
| 外部服务直接读写本服务数据库 | 内容耦合（病态耦合）；立即改为请求接口 | §2.3.4 | 🧭归纳 |
| 订单状态机被多服务共同修改 | 由单个微服务集中管理状态转换，拒绝非法转换 | §2.3.3 | 🧭归纳 |
| 微服务看起来只是数据库 CRUD 包装器 | 表明低内聚——本应在此管理的数据逻辑被分散到上游 | §2.3.3 | 🧭归纳 |
| 初期微服务数量 | 以"完整的限界上下文"为粒度起步（由粗到细），不要追求细粒度 | §2.4.4 | 🧭归纳 |
| 跨服务聚合关系如何建模 | 用 URI 或伪 URI（如 `soundcloud:tracks:123`），让引用显式 | §2.4.2 | 🧭归纳 |
| 团队对领域理解不一致 | 跑事件风暴（Alberto Brandolini），技术与非技术干系人共创 | §2.4.5 | 🧭归纳 |
| PCI / GDPR 合规要求缩小审计范围 | 按数据隔离划分服务（PaymentCo 把信用卡数据隔离到深色区域） | §2.6.2 | 🧭归纳 |

**§2 关键数字**

| 数字/口诀 | 含义 | 锚点 |
|---|---|---|
| 高内聚低耦合的结构是稳定的 | 康斯坦丁定律（Endres/Rombach 真正出处） | §2.2.4 |
| "一起变化的代码应该组织在一起" | 内聚的最简明定义（出处不详） | §2.2.2 |
| 一个聚合只由一个微服务管理 | 反过来不行：微服务可管多聚合，但聚合不能被多服务瓜分 | §2.4.2 / §2.4.4 |
| 1971 / 1976 / 2003 | Parnas 信息隐藏提出年 / Yourdon-Constantine Structured Design / Endres-Rombach A Handbook of Software and Systems Engineering | §2.2.1 / §2.3 |

### §3 第3章 拆分大单体

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 想从单体切换到微服务但还没目标 | 先想清楚目标；"微服务不是目标" | §3.1 | 🧭归纳 |
| 拆分大型单体 | 增量、小步、可回滚；"大爆炸式重写只有一次大爆炸" | §3.2 | 🧭归纳 |
| 选第一个拆分对象 | 易实现 + 有端到端价值的"速赢"对象；最简单的都做不成就别做 | §3.4 | 🧭归纳 |
| 已确定第一个微服务，先拆代码还是数据 | 通常先拆代码（短期收益大）；不确定数据库可拆就先拆数据库做可行性证明 | §3.5.1 / §3.5.2 | 🧭归纳 |
| 想无侵入替换单体功能 | 绞杀者模式（HTTP 代理拦截路由，单体无感知） | §3.6.1 | 🧭归纳 |
| 关键业务功能不敢一刀切 | 并行运行模式：新旧实现同时跑，对比结果 | §3.6.2 | 🧭归纳 |
| 需要在新旧实现间动态切换 | 功能开关（在代理层实现，可灰度） | §3.6.3 | 🧭归纳 |
| 拆分后跨表 JOIN 变慢 | 关联从数据库移到应用层，多一次网络调用；用批量/缓存缓解 | §3.7.1 | 🧭归纳 |
| 跨库外键约束丢失 | 用软删除或数据复制兜底 | §3.7.2 | 🧭归纳 |
| 想用分布式事务保持 ACID | 放弃分布式事务，新书明确说它"无法提供小范围数据库事务的保障"；改用 Saga | §3.7.3 | 🧭归纳 |
| 跨微服务生成报表 | 专设报表数据库，由各服务推送"最少必要数据"，表结构可与源不同 | §3.7.5 | 🧭归纳 |
| 团队是领域新手时拆分 | 慎重——Snap CI 教训：过早拆分会被迫合并回单体 | §3.3 | 🧭归纳 |
| 识别代码热点 | 用 CodeScene 等静态分析工具识别频繁变更部分 | §3.4 | 🧭归纳 |
| 单体和微服务"共存"是不是混乱 | 不是——现实系统本来就杂乱；目标是持续演进而非整洁 | §3.3 | 🧭归纳 |

**§3 关键数字**

| 数字 | 含义 | 锚点 |
|---|---|---|
| 10% / 90% | 微服务迁移的常见组合：瓶颈 10% 转微服务，剩余 90% 留单体 | §3.3 |
| 1 年 | Snap CI 团队合并回单体后，再次拆分成功的间隔时长 | §3.3 |
| "3 件套" | 迁移模式：绞杀者 + 并行运行 + 功能开关 | §3.6 |

### §4 第4章 微服务间通信模式

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 在同步 vs 异步、HTTP vs Kafka 之间纠结 | 先定"请求-响应 vs 事件驱动"，再定"同步 vs 异步" | §4.3 | 🧭归纳 |
| 后续逻辑依赖当前调用的结果 | 请求-响应（同步或异步均可） | §4.7.2 | 🧭归纳 |
| 想让多个下游自行决定怎么响应 | 事件驱动（默认推荐；事件发布方不知道消费者是谁） | §4.8 / §4.8.3 | 🧭归纳 |
| 要跟老系统/大型机/海量数据集成 | 共用数据（文件/数据库）；用轮询或事件通知触发 | §4.6 / §4.6.4 | 🧭归纳 |
| 调用链 ≥ 4 个微服务且全同步 | 重排流程（去掉关键路径）或转异步，否则一环故障=全部失败 | §4.4.3 | 🧭归纳 |
| 多个独立 API 调用要串行等结果 | 并行调用；总耗时 = 最慢那个 | §4.7.1 | 🧭归纳 |
| 用 async/await 但仍在阻塞 | 术语陷阱：执行模型仍是同步阻塞，按模型而非关键字判断 | §4.5.2 | 🧭归纳 |
| 共享数据库被当作通信手段 | 严禁；公共耦合（§2.3.3）的实例化 | §4.6 / §2.3.3 | 🧭归纳 |
| 异步队列里偶有消息让消费者崩溃 | 设最大重试次数 + 死信队列 + 监控 UI（"消息诊所"） | §4.9 | 🧭归纳 |
| 跨进程调用 | 必须实现超时和重试；监控带关联 ID 才能跨进程追踪 | §4.7.1 / §4.9 | 🧭归纳 |
| 事件内容只放 ID 还是放完整数据 | 默认放完整数据（信息隐藏原则）；判断准则"愿意通过 API 共享的就能放进事件" | §4.8.2 | 🧭归纳 |
| 担心事件过大 | Kafka 1 MB / RabbitMQ 512 MB 单消息上限；PII 拆分两种事件 | §4.8.2 | 🧭归纳 |
| 微服务实现层要避免的 | "不要让中间件包含越来越多的智能，而要让微服务保持智能" | §4.8.1 | 🧭归纳 |
| 团队首次引入事件驱动 | 警惕复杂度提升；监控、死信队列、关联 ID 不可省 | §4.9 | 🧭归纳 |

**§4 关键数字**

| 数字 | 含义 | 锚点 |
|---|---|---|
| 几毫秒 | 数据中心内网络通信数据包来回传输耗时 | §4.1.1 |
| 1000 次 | 进程内合理 / 进程间不合理 的 API 调用阈值 | §4.1.1 |
| 5 种故障 | Tanenbaum 分布式故障分类：崩溃/遗漏/时效/响应/恶性 | §4.1.3 |
| 1 MB / 512 MB / 2 GB | Kafka 默认消息上限 / RabbitMQ 当前上限 / RabbitMQ 历史上限 | §4.8.2 |
| 2006 | Fowler 提出"灾难性故障转移"概念时的银行定价 bug 年份 | §4.9 |
| 4–5 个微服务 → 1 环挂 = 全部失败 | MusicCorp 案例：订单→支付→防欺诈→客户 | §4.4.3 |

## 模块二 集成与工作流（§5–§6）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 跨服务同步调用、要最大化互操作和缓存 | REST 仍是默认选择 | §5.2.2 | 🧭归纳 |
| 内部微服务同步调用、要可控的强类型契约 | gRPC（HTTP/2 + 协议缓冲区）首选 | §5.2.1 | 🧭归纳 |
| 移动端/聚合多个下游、读多写少 | GraphQL 做外部聚合层，读 GraphQL / 写 REST | §5.2.3 | 🧭归纳 |
| 异步广播、事件流、需要重放与持久化 | Kafka（按主题持久化，分区内有序） | §5.2.4 | 🧭归纳 |
| 异步点对点 + 消息确认 + 严格路由 | RabbitMQ / ActiveMQ（队列 = 单消费者组 = 负载均衡） | §5.2.4 | 🧭归纳 |
| 接口需要长期向后兼容 | 扩展式更改 + 兼容消费者（Postel 定律：严输出宽输入） | §5.6.1, §5.6.2 | 🧭归纳 |
| 必须做破坏性变更但要保持独立部署 | 扩展-收缩模式：同一进程同时暴露新旧接口（首选） | §5.7.3 | 🧭归纳 |
| 怀疑结构性破坏 | 模式比较工具：Protolock / json-schema-diff / openapi-diff | §5.6.5 | 🧭归纳 |
| 怀疑语义性破坏 | Pact 消费者驱动的契约测试 | §5.6.5 | 🧭归纳 |
| 跨服务共享代码 | 接受同一库的多个版本共存；客户端库要分"通用 SDK + 业务客户端"两层 | §5.8 | 🧭归纳 |
| 服务发现，单实例/简单场景 | DNS 直连主机；多实例经负载均衡器 | §5.9.1 | 🧭归纳 |
| 服务发现，动态环境 | Consul（HTTP 接口 + SRV 记录 + 健康检查 + consul-template） | §5.9.2 | 🧭归纳 |
| 服务发现，已经上了 K8s | 用 K8s 内置（pod 元数据匹配），不必单独再起 Consul | §5.9.2 | 🧭归纳 |
| 南北向流量（GUI/外部访问） | API 网关；但禁止在网关层做调用聚合/协议重写 | §5.10.1 | 🧭归纳 |
| 东西向流量（多语言、≥5 微服务） | 服务网格（Envoy 系）；<5 微服务不值得上 | §5.10.2 | 🧭归纳 |
| 跨微服务状态变更 | 先在本地 ACID 事务处理；整体原子性天然丢失 | §6.1.2 | 🧭归纳 |
| 跨微服务要"全部成功或全部失败" | 作者明确反对 2PC/分布式事务，改用 Saga | §6.3 | 🧭归纳 |
| 业务流程涉及多个服务 | Saga = 子事务 + 补偿；放弃全局原子性换得短锁 | §6.4 | 🧭归纳 |
| Saga 回滚失败步骤 | 触发"补偿事务"（语义回滚，非 DB 回滚：邮件发了就是发了） | §6.4.1 | 🧭归纳 |
| 简化回滚设计 | 把最可能失败的步骤前置，尽早终止流程 | §6.4.1 | 🧭归纳 |
| Saga 选编排式还是协同式 | 单团队负责全 Saga → 编排；跨团队 → 协同 | §6.4.2 | 🧭归纳 |
| 协同式 Saga 追踪进度 | 必须用关联 ID（Correlation ID）贯穿所有事件 | §6.4.2 | 🧭归纳 |

### §5 关键数字

- **服务端最小集群规模**：ZooKeeper 至少 3 个节点（§5.9.2）
- **服务网格起步阈值**：作者明确"只有 5 个微服务"不值得上（§5.10.2）
- **Kafka 同集群已知最大规模**：同一集群上 5 万多个生产者和消费者（一家大型科技公司案例，§5.2.4）
- **缓存 TTL 风险**：JVM 默认缓存 DNS 记录，TTL 内旧 IP 仍生效（§5.9.1）
- **2PC 限制**：仅用于"非常短暂的操作"——锁时间 = 操作时间（§5.2）
- **破坏性变更过渡期**：作者举的极端例子是给消费者 1 年的弃用期（§5.7.7）

### §6 关键数字

- **ACID 四个属性**：原子性 / 一致性 / 隔离性 / 持久性（§6.1.1）
- **2PC 两个阶段**：投票阶段 + 提交阶段（§6.2）
- **Saga 历史**：Hector Garcia-Molina 和 Kenneth Salem 1987 年提出（§6.4）；嵌套扩展 1991 年 Data Engineering 论文
- **Spanner 代价**：依赖卫星原子钟 + 极昂贵的数据中心（§6.3）
- **MongoDB 多文档 ACID**：4.0 起支持（§6.1.1）
- **混合风格心法**：编排式偏请求-响应，协同式偏事件（§6.4.2）

## 模块三 构建、部署与测试（§7–§9）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 判断团队是否真在做 CI | Humble 三问：每天向主干提交？有验证代码行为的测试？构建破坏时禁止其他提交且修复是首要任务？三条不满足就只是"用了 CI 工具" | §7.1 | 🧭归纳 |
| 选分支策略 | 基于主干开发 + 功能开关；短期分支（<1 天）、活跃分支 <3 个是高绩效常态；GitFlow 长生命周期分支只适合"不可信"开源贡献者场景 | §7.2 | 🧭归纳 |
| 构建制品怎么管 | 只构建一次 + 环境无关：早期一次构建镜像存仓库，CI→预发布→生产复用同一 build-123；环境相关配置全部从制品剥离 | §7.3 | 🧭归纳 |
| 代码库组织怎么选 | 单巨型库最差（一行改动全量构建）；一服务一库所有权清晰但跨服务改动多次提交；monorepo 原子提交但需 Bazel 类工具 + CODEOWNERS；超 20 人组织倾向多代码库 | §7.4 | 🧭归纳 |
| 一台主机跑多个服务行不行 | 不行：坚持隔离执行，一主机一服务（容器已足够好）；Gilt 反面案例——单实例服务压垮整个主机 | §8.1–§8.2 | 🧭归纳 |
| 部署平台怎么选 | 没坏别修、尽可能放弃控制权（PaaS/FaaS 优先）、容器化是性价比折中；Few 微服务+Few 开发时 K8s 过度复杂，先 minikube/MicroK8s 试用再决策 | §8.4–§8.5 | 🧭归纳 |
| FaaS 拆分粒度 | 可"一微服务一函数"或"一聚合一函数"（DDD 聚合对应多函数共享数据库）；不要拆到每个状态转换——一致性管理难度跳升而价值微薄 | §8.6 | 🧭归纳 |
| 怎么做到不停机发布 | 把部署和发布分开：功能开关→蓝绿部署→金丝雀放量→并行运行（GitHub Scientist 比较新旧实现）；部署频次↑+变更失败率↓在高绩效组织反复证实 | §8.7 | 🧭归纳 |
| 测试金字塔比例怎么定 | 单元:服务:端到端每层多一个数量级（作者亲历 4000:1000:60 已嫌多）；反模式"测试甜筒"必须用更小更快测试替换 | §9.1–§9.2 | 🧭归纳 |
| stub 还是 mock | stub 只回响应、mock 还验证调用次数/参数而易脆——作者倾向少用 mock；本地桩可用 mountebank 多协议打桩 | §9.3 | 🧭归纳 |
| 端到端测试越积越多怎么办 | 承认其脆弱性（任意故障即红、"偏差正常化"、作者亲历完整回归 6 周）；用消费者驱动契约（CDC/Pact）替代跨团队端到端，端到端只留少而精的冒烟/金丝雀当最后安全网 | §9.4–§9.5 | 🧭归纳 |
| 谁来写测试 | 专业测试团队会让开发远离测试代码、反馈变长；最佳是扇入+按服务所有权拆分（Emily Bache 模式） | §9.4 | 🧭归纳 |
| 生产环境还要测什么 | 部署完成≠发布：冒烟测试（部署后发布前）+金丝雀+虚拟用户注入；MTBF vs MTTR 权衡——更快回滚+更好监控往往优于堆更多预发布测试 | §9.7 | 🧭归纳 |

- 完整回归曾跑 6 周（端到端失控的代价）——§9.4

## 模块四 可观测性与安全（§10–§11）

| 场景 | 方案 | 章节锚点 | 三级标记 |

| 团队首次上微服务 | 部署前先把日志聚合工具跑起来；关联 ID 同步在第一跳生成、整链透传到日志固定列 | §10.6.1 | 🧭归纳 |

| 语义监控 + 模拟业务 | 不用低层指标告警，改用业务级陈述（新客户可注册/高峰销售/订单配送）；模拟业务跑端到端测试子集 | §10.6.6–10.6.7 | 🧭归纳 |
| 微服务可观测性工具评估 | 选大众化/易集成（支持 OpenTelemetry）/提供上下文（时效+相关+关系+程度）/秒级实时 | §10.8 | 🧭归纳 |
| 安全意识定位 | 系统安全 = 最薄弱环节决定；不要只加固前门而忘了后门 | §11.1 | 🧭归纳 |
| 安全控制分层 | 三类同时用：预防（凭证/加密/认证）/检测（防火墙/IDS）/响应（备份+沟通计划） | §11.1.2 | 🧭归纳 |
| 凭证管理 | Vault / Kubernetes secrets 集中管理；轮换越频越好（AWS API 限时密钥可缩到 1 小时）；git-secrets 拦截提交 | §11.3.1 | 🧭归纳 |
| 依赖漏洞防护 | Snyk / GitHub 代码扫描集成 CI，链接到有漏洞库即阻断构建 | §11.3.2 | 🧭归纳 |
| 备份有效性 | 必须用生产备份实际恢复一次构建测试数据（避免"薛定谔的备份"）；备份存独立账户/独立区域 | §11.3.3 | 🧭归纳 |

| 服务间认证 | 微服务零信任环境用双向 TLS（mTLS）；服务网格是主流落地手段；公网场景客户端身份验证通常不如用户身份重要 | §11.5.1, §11.6.1 | 🧭归纳 |
| 静态数据保护 | 不自创加密；用加盐哈希存密码；密钥与数据分库存储；Datensparsamkeit = 适度收集 | §11.5.2 | 🧭归纳 |

| 鉴权架构 | 网关做粗粒度（SSO 登录握手 + 填充标头/发 JWT），下游微服务做细粒度；细粒度用粗粒度角色（按组织运作方式建模），不堆"金额阈值式"碎角色 | §11.6.4–11.6.5 | 🧭归纳 |
| 跨服务委托人传递 | 用 JWT：JSON 负载（公共声明 exp/groups/sub） + 3 段编码（标头.负载.签名）；公钥从 Vault 取 | §11.6.9 | 🧭归纳 |

## 模块五 弹性与扩展（§12–§13）

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 系统进入微服务，先做什么 | 先建日志聚合；核心路径服务部署多副本+多可用区（AWS 单 AZ 不保可用性） | §12.2, §12.6 | 🧭归纳 |
| 跨功能需求怎么定 | 写 SLO：响应时间用百分位（如 200 并发下 90% 在 2 秒内）+ 历史停机时长衡量可用性 + 数据按类定保留期 | §12.3 | 🧭归纳 |
| 同步调用下游总被拖死 | 设超时（外部调用 100% 配默认超时）+ 给整个操作留时间预算并透传给下游 | §12.5.1 | 🧭归纳 |
| 下游时不时 503/504 | 重试：仅瞬时错误（503/504 不重试 404）+ 重试前等一会 + 超时×重试≤总预算 | §12.5.2 | 🧭归纳 |
| 单个下游慢拖垮所有调用 | 舱壁：每个下游独立连接池/线程池（最关键的一道防线），从根上防资源耗尽 | §12.5.3 | 🧭归纳 |
| 下游已病入膏肓还在被打 | 断路器：阈值后快速失败；半开探活，恢复则闭合；同步链路首选快速失败别排队 | §12.5.4 | 🧭归纳 |
| 不知下游故障或发布时 | 断路器手开手闭写进自动化部署脚本（发布期免疫），配合舱壁 + 超时三件套 | §12.5.4 | 🧭归纳 |
| 重试/重发安全前提 | 幂等：业务事件带唯一 ID；HTTP 的 GET/PUT 自身规范幂等，但实现必须真幂等 | §12.5.8 | 🧭归纳 |
| 数据选 AP 还是 CP | 库存/推荐接受 5 分钟陈旧 → AP；银行余额/订单不能陈旧 → CP；同一微服务不同功能可分选 | §12.7.4, §12.7.5 | 🧭归纳 |
| 想自己实现 CP 一致性存储 | 强烈反对；用 Consul/ZooKeeper/etcd 等成熟实现；不要自造加密也不要自造分布式一致性 | §12.7.2 | 🧭归纳 |
| 系统假设的真实性检验 | 混沌工程：Chaos Monkey/Gorilla/Latency Monkey + 演练日 DiRT + Chaos Toolkit/Gremlin；运行 ≠ 变弹性，只检验假设 | §12.8 | 🧭归纳 |
| 故障发生后怎么办 | 无指责复盘（blameless post-mortem）；找个人责备只会掩盖系统问题、失去学习机会 | §12.9 | 🧭归纳 |
| 选扩展起点 | 纵向扩容（买大机器）→横向复制（多副本+LB）→数据分区 →功能拆分；先易后难 | §13.1 | 🧭归纳 |
| 单体写竞争扩展 | 先纵向扩容（关系数据库快速扩写首选）+ 公有云按小时租机器 | §13.1.1 | 🧭归纳 |
| 单体读重 | 横向复制加读副本，主写从读，由微服务内部路由，对消费者透明 | §13.1.2 | 🧭归纳 |
| 需要扩展+健壮性双重 | 数据分区 + 横向复制组合（每分区多副本）；单分区失效只丢该分区请求 | §13.1.3 | 🧭归纳 |
| 选分区键 | 唯一 ID 而非姓氏/地理；负载分布均匀 + 抗姓名变化；改分区方案代价极高（曾见主库离线 3 天） | §13.1.3 | 🧭归纳 |
| 不知道怎么拆 | 提取一个微服务出来独立扩展就是功能拆分；按业务能力而非技术能力；先易后难 | §13.1.4 | 🧭归纳 |
| 4 维可叠加 | 沿一维扩展常解锁其他维（先功能拆出订单→副本数→按地理分区），按需组合 | §13.2 | 🧭归纳 |
| 缓存优化起步 | 0 是理想数量；只在确实需要时才加；越少越能推断新鲜度 | §13.4.6 | 🧭归纳 |
| 缓存放在哪 | 客户端（最快、可降级，但多副本不一致）/ 服务端（一致性最好，但省不掉网络一跳）/ 请求缓存（性能最强但极特化） | §13.4.4 | 🧭归纳 |
| 缓存失效选哪招 | TTL（最简单但会返回过期数据 4 分 59 秒）/ ETag 带条件 GET（省资源再生）/ 通知失效（最优雅，需心跳健康监测）/ 透写（仅服务端可行）/ 回写（微服务下少用，缓存失则数据失） | §13.4.5 | 🧭归纳 |
| 缓存提升健壮性 | 过期数据保留待更新而非自动清除；本质是选 AP | §13.4.3 | 🧭归纳 |
| 嵌套缓存的新鲜度 | TTL 1+1=2 分钟过期；嵌套越深越难推断，避免过度缓存 | §13.4.6 | 🧭归纳 |
| 自动扩展启动顺序 | 先对故障用自动扩展（"至少 5 实例"），再对负载用；缩要谨慎，多留容量 | §13.5 | 🧭归纳 |
| 响应式扩缩缓冲 | 扩 10 分钟但只提前几分钟知道 → 预留额外容量；用负载测试验证自动扩展规则 | §13.5 | 🧭归纳 |
| 是否要重新架构 | 成功的代价不是失败；不要在新项目启动时大规模预构建应对"可能永不到的负载" | §13.6 | 🧭归纳 |

### 关键数字

- **AdvertCorp 案例：每实例 40 并发 → 5 分钟内峰值 800 并发 → 系统崩溃**；下游服务仅服务 <5% 用户却拖垮全站（§12.5）
- **广告 HTTP 请求初始超时 30 秒 → 实际正常 <1 秒 → 调到 1 秒**；目标 4~6 秒呈现页面，最差 ≈2 秒（§12.5.1）
- **重试超时×次数：500 ms × 3 次 + 间隔 1 秒 = 最多 3.5 秒**；超过总预算则不再重试（§12.5.2）
- **HTTP 4 大错误码**：404 不重试；503 Service Unavailable / 504 Gateway Timeout 可重试（§12.5.2）
- **AWS 单可用区：单月 99.95% 正常运行时间** → 工作负载必须分布在该区域内多个可用区（§12.6）
- **AWS 单 EC2 实例无正常运行时间保证** → 多实例必要；同可用区也救不了，可用区失效应有跨可用区副本（§12.6）
- **响应时间 SLO 示例**：200 并发连接下 90% 响应时间 2 秒（§12.3）
- **AWS u-24tb1.metal 实例内存 24 TB**（极端内存型示例，§13.1.1）
- **数据分区失效影响**：4 分区均匀分布 → 1 个分区失效 = 25% 请求失败（§13.1.3）
- **分区方案改造成本**：曾见客户为改主库分区方案使生产系统离线 3 天（§13.1.3）
- **Kafka 分区消息大小默认上限 1 MB**（来自第 4 章，作为对比：分区方案的中间件基础，§13.1.3）
- **HTTP 缓存控制两大报头**：Cache-Control（TTL）+ Expires（到期时间戳）（§13.4.5）
- **缓存嵌套放大效应**：每层 TTL 1 分钟 → 实际陈旧度最高 2 分钟（§13.4.6）
- **响应式扩展 vs 通知时间差**：仅提前几分钟通知但扩需 10 分钟 → 必须预留额外容量（§13.5）
- **"至少 5 实例"打地鼠陷阱**：删除实例时若忘关规则，实例自动重启 → 死循环；自动扩展规则要做操作演练（§13.5）
- **CAP 铁律**：分布式下 CA 不存在；AP 与 CP 的取舍取决于"分区后是否还能提供正确服务"（§12.7.3–§12.7.4）
- **CAP 灵活性**：Cassandra 允许单次调用做不同 CAP 取舍；同一微服务内不同功能可分别选 AP/CP（§12.7.5）
- **混沌工程原典定义**："通过对系统进行实验来增强系统在生产环境中经受动荡条件的能力的学科"（混沌工程原理网站，§12.8）
- **Netflix Simian Army**：Chaos Monkey（随机关机器）+ Chaos Gorilla（关整个可用区）+ Latency Monkey（模拟网络变慢）（§12.8.2）
- **广告系统 HTTP 缓存灾难**：Expires: Never + 改条件跳过缓存头改写 → 改 URL 才能让用户重抓（§13.4.8）

| 跨团队学习 | **实践社区（CoP）**——每周几小时研讨/分享 | §15.8.1 | 🧭归纳 |
| 业务流团队自助 | 平台团队——构建让"正确做法最简单"的工具 | §15.8.2 | 🧭归纳 |
| 平台采纳策略 | **铺好的路（Paved Road）**——可选用而非强制；OKR 跟踪采纳率 | §15.8.2 | 🧭归纳 |
| 共享微服务被多团队改 | 拆分 / 跨域变更特别团队 / **内部开源** / 可插拔框架 / 库贡献 | §15.9–15.11 | 🧭归纳 |
| 内部开源机制 | 核心提交者 + 受信任/不受信任提交者；先在成熟服务上开放 | §15.10.1, 15.10.2 | 🧭归纳 |
| 跨地域团队 | 成员尽量同地 / 同近时区；沟通粗粒度接口匹配代码所有权 | §15.14 | 🧭归纳 |
| 业务线边界（REA 模式） | 业务线内自由通信；**业务线之间强制异步批处理** | §15.13 | 🧭归纳 |

### §16 演进式架构师 — 愿景、原则与治理

| 场景 | 方案 | 章节锚点 | 三级标记 |
|---|---|---|---|
| 架构师定位 | **城市规划师 ≠ 建筑师**——定义区域，不指定区域内部 | §16.4 | 🧭归纳 |
| 架构关注范围 | "**关注盒子之间发生的事情，而对盒子内部置之不理**" | §16.5 | 🧭归纳 |
| 区域（边界）定义 | 区域 = 微服务/团队边界；区域内允许技术栈/数据存储差异 | §16.5 | 🧭归纳 |
| 与团队相处频率 | **4 团队每 4 周花半天**；最好与团队结对编码 | §16.7 | 🧭归纳 |
| 架构愿景 | 在系统级有简明技术愿景；同时考虑系统、用户、构建者 | §16.1, 16.16 | 🧭归纳 |
| 治理本质 | "评估干系人需求/优先排序决策/按方向监测绩效"——集体活动 | §16.13 | 🧭归纳 |
| 原则 vs 实践 vs 约束 | 原则 ≤10 条（可变化）/ 实践（技术、常变）/ 约束（几乎不变） | §16.8.2, 16.8.3 | 🧭归纳 |
| 跨语言实践 | 不同语言团队可有不同实践，但要共享一套原则 | §16.8.4 | 🧭归纳 |
| 架构演进验证 | 用**适应度函数**持续监测（性能/耦合/周期时间等） | §16.9 | 🧭归纳 |
| 与团队决策分歧 | **默认同意团队**——只在"鸭子池塘"级风险上否决 | §16.10 | 🧭归纳 |
| 微服务"一等公民"标准 | 可监控性 / 接口（少量标准化）/ 架构安全性（断路器、状态码规范） | §16.12 | 🧭归纳 |
| 微服务模板选择 | 警惕"中央框架怪兽"；模板**可选**，提供内部开源贡献通道 | §16.13.2 | 🧭归纳 |
| 异常处理 | 记录异常日志；**累积到一定程度就该改原则** | §16.15 | 🧭归纳 |
| 大型组织治理（康卡斯特范式） | 仿 IETF 设**内部架构协会**——开放标准机构式集体决策 | §16.6 | 🧭归纳 |
| 演进式架构师 6 项核心职责 | **愿景 + 同理心 + 协作 + 适应性 + 自治性 + 治理** | §16.16 | 🧭归纳 |
