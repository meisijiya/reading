## 第8章 多智能体协作

Claude Code最被低估的能力不是写代码有多快，而是它可以同时运行多个智能体。学会并行工作之后，你的工作模式将从“一个人配一个AI”变成“一个人指挥一个AI团队”。

写这本书的时候，我同时打开了6个Claude Code智能体。这6个智能体并行运行了大约6小时，就完成了初稿。如果串行执行，至少需要一周。

但这并不是没有代价的。6个智能体意味着6份独立的上下文，词元消耗量是单智能体的6倍；而且6个智能体的写作风格不完全一致，后期还需要进行统一审校。因此，并行不是越多越好，而是要判断：任务拆开后能不能独立做？合并成本高不高？

### 8.1 一个人为什么要开那么多窗口

Boris日常是这样工作的：本地开启5个Claude Code实例（每个实例对应一个独立的git checkout工作目录，互不干扰），云端再打开5～10个Claude网页会话，每个会话执行不同的任务，包括写新功能、修复bug、写测试、做重构、进行代码审查等，同时进行。

我一开始觉得这也太夸张了。直到自己尝试之后才理解，这不是炫技，而是Boris给团队的第一个使用技巧：**并****行****做****更****多****工****作****。**

原因很直接：Claude Code的工作模式是“你给任务→Claude Code执行几分钟→你评估结果→你再给下一个任务”，中间有大量等待时间。若只打开一个智能体，大部分时间你在等Claude Code干活。若打开5个智能体，你在评估第一个结果的同时，其他4个智能体还在运行，等待时间几乎为零。

并行工作的关键前提是：**每****个****智****能****体****需****要****在****独****立****的****代****码****环****境****中****运****行****，**否则它们会互相覆盖文件，发生冲突。这就是worktree要解决的问题。

### 8.2 worktree：并行运行的基础设施

worktree允许你从同一个仓库创建多个工作目录，每个工作目录在不同的分支上，文件系统完全隔离。Claude Code原生支持worktree：

# 启动一个在独立worktree中运行的Claude session

claude --worktree

# 在tmux会话中启动（可以后台运行）

claude --worktree --tmux

每次运行claude --worktree,Claude Code就会自动创建一个新的worktree，切到一个新分支，然后在那个隔离的环境中工作。完成后，你可以把分支合并回主分支。

但当你同时启动多个worktree时，很快会遇到一个新问题：多个智能体同时运行，你该如何在它们之间切换和管理？此时就用到tmux了。在Claude Code中，可以通过添加--tmux参数来启用这个能力，智能体会在一个tmux窗口中启动，你可以用快捷键在不同智能体之间切换。Boris设置了shell别名来快速跳转：

# ～/.zshrc中添加

alias za="tmux select-window -t claude:0"

alias zb="tmux select-window -t claude:1"

alias zc="tmux select-window -t claude:2"

za表示跳到第一个智能体，zb表示跳到第二个智能体，以此类推。如果你使用Desktop App，在界面中选中worktree复选框即可，不需要手动配置tmux。

### 8.3 subagent：给主智能体叫个帮手

并行智能体适合处理互不相关的独立任务。但有时你要的不是打开一个新窗口，而是在当前任务中调一个“专家”来处理特定环节，比如让一个安全审查专家评估你刚写的认证代码。这就是subagent做的事情。

在．claude/agents/目录下放入一个．md文件，就定义了一个subagent：

.claude/agents/

├──security-reviewer.md　　　 #安全审查专家

├──code-simplifier.md　　　　 #代码精简专家

├──verify-app.md　　　　　　#应用验证专家

└──code-architect.md　　　　　#架构设计专家

每个智能体文件可以设置自定义名称、工具集权限、权限模式，甚至指定使用的模型。比如“安全审查”智能体可以配置为只有读权限（不能改代码），并指定使用推理能力更强的模型。

subagent最重要的特性不是“专业分工”，而是**独****立****上****下****文****。**

每个subagent都运行在自己的上下文窗口中，不占用主智能体的上下文空间。当主智能体的对话已经很长，上下文快满的时候，可以调用一个subagent来处理子任务，相当于开辟了一个新的“思考空间”，不会挤压主智能体的上下文空间。

你甚至可以在提示词中加上“use subagents”，让Claude Code主动判断什么时候该把子任务分配给subagent，从而投入更多计算资源来完成复杂任务。

**核****心****建****议**

实用的subagent组合示例：security-reviewer（每次涉及认证、权限、数据存储时自动调用）+ verify-app（修改完成后自动启动应用并验证功能是否正常）。这两个subagent覆盖了“代码写得对不对”和“应用能否正常运行”两个最常见的验证需求。

### 8.4 Agent Teams：让智能体自己协调

worktree允许你手动管理多个并行智能体，subagent可以为主智能体调用专家。Agent Teams则更进一步：多个智能体可以互相通信、协调分工。

Agent Teams于2026年2月正式发布，目前是Claude Code最强大的协作模式。它的核心理念很简单：不是由用户协调多个智能体，而是让智能体自己协调。我之前写过一篇实测文章——与3个AI队友在45分钟内完成红白机游戏厅的开发，就是利用了这个功能。

**1****.****W****r****i****t****e****r****/****R****e****v****i****e****w****e****r****模****式**

最经典的用法是一个智能体写代码，另一个智能体审代码。

(1) Writer智能体写代码：负责实现功能，按照需求写代码并运行测试。

(2) Reviewer智能体审代码：评估Writer智能体的输出，指出问题并给出改进建议。

(3) Writer智能体根据反馈修改：收到评估意见后改进代码，形成迭代循环。

两个智能体在这种模式下写出的代码比单个智能体写出的代码好很多，原因和人类团队的协作类似：写代码的人容易陷入自己的思路，而审代码的人能从不同角度发现问题，两个智能体互相监督，可以显著提升产出质量。

**2****．****测****试****驱****动****模****式**

另一种高效的模式是一个智能体写测试，另一个智能体写实现。写测试的智能体先根据需求定义“什么是正确行为”，写实现的智能体再根据定义要求编写代码。这就是AI版的TDD（test driven development，测试驱动的开发）。

Agent Teams会自动共享任务状态和消息，你不需要在智能体之间手动复制和粘贴信息。系统中有一个team lead（团队负责人）角色负责协调分工和进度。

**3****.****C****o****o****r****d****i****n****a****t****o****r****模****式****：****分****阶****段****协****调**

Agent Teams内部其实有一套更精细的协调机制。对于复杂任务，系统会自动分4个阶段执行：先让多个worker并行调查代码库（Research，即调研），然后由coordinator综合结果并生成规格说明（Synthesis，即综合），接着worker按规格说明进行精准修改（Implementation，即实施），最后由coordinator验证结果（Verification，即验证）。你不需要手动配置这个流程，Agent Teams会根据任务复杂度自动判断是否执行完整的流程。

### 8.5 Fan-out批处理：人海战术的AI版

前面讲的都是多个智能体配合做一件事，还有另一类问题：**同****一****个****操****作****需****要****在****大****量****文****件****上****重****复****执****行****。**这种场景更适合采用Fan-out （扇出）模式。

Fan-out的核心思路是：把一个操作复制成多个独立任务，同时执行。

**1****．****非****交****互****模****式**

Claude Code支持非交互模式，可以用-p参数传入提示词，适合在脚本中调用：

# 非交互模式执行单个任务

claude -p "把这个文件从JavaScript迁移到TypeScript"

配合shell循环，你可以批量处理：

# 批量迁移一批文件

for file in $(cat files-to-migrate.txt); do

claude -p "Migrate $file from JS to TS" \

--allowedTools "Edit,Bash(git commit *)" &

done

注意&，这让每个Claude Code智能体在后台并行运行。如果有50个文件要迁移，50个智能体同时运行，可能几分钟就能完成原本需要一整天才能完成的工作。

**2****.****/****b****a****t****c****h****命****令**

如果你不想自己写shell脚本，Claude Code提供了/batch命令来简化这个过程。

(1) 交互式规划。告诉Claude Code你想做什么（如“把所有React类组件迁移到函数组件”）,Claude Code会分析项目，列出所有需要处理的文件。

(2) 确认执行。你评估计划，确认后Claude Code启动数十个智能体并行执行。

(3) 汇总结果。所有智能体完成任务后，Claude Code汇总成功或失败情况，你只需要处理少数失败的任务。

这种模式特别适合大规模重构、代码迁移、批量修复等场景。一个人加Claude Code，往往可以完成一个工程团队一周才能完成的迁移工作。

### 8.6 不需要一直盯着计算机

Claude Code支持远程控制和异步执行，你不用一直守着终端。

### 8.6.1 远程控制

远程控制功能打破了物理工位的束缚，让你能够通过移动端或其他设备，随时随地接入正在运行的开发环境。

**R****e****m****o****t****e****C****o****n****t****r****o****l****。**你可以通过该功能生成一个链接，在手机上打开这个链接，就能远程创建和管理本地的Claude Code智能体。这个功能适合在通勤途中启动任务、出门前让Claude Code先运行起来等场景。Boris提到，他早上会用iPhone通过Claude移动端启动会话，之后在桌面端继续操作。

**C****l****a****u****d****e****C****o****d****e****o****n****W****e****b****。**如果开发环境在云端或者你只是想在浏览器中使用，可以直接在浏览器中运行网页版Claude Code，不需要安装本地环境。

### 8.6.2 异步执行

**1****.****/****s****c****h****e****d****u****l****e****：****云****端****定****时****任****务**

# 设定一个云端定时任务

/schedule "Check for outdated dependencies and create PRs"

/schedule用于设定定时触发的任务，在云端执行。即使关闭计算机，任务也会按时执行。这适合日常维护类工作，如依赖更新、安全扫描、日报生成等。

**2****.****/****l****o****o****p****：****本****地****长****时****间****运****行**

有些任务需要长时间运行（如监控CI状态、执行CI测试等）。/loop可以让Claude Code在本地无人值守运行，最长可达3天。你去做别的事，Claude Code会在后台持续运行。

**异****步****工****作****的****心****智****转****变**

传统开发是同步的：写代码、运行测试、等待结果，全都串行执行。而在异步模式下，你可以在晚上睡觉前启动一批任务，早上醒来后再评估结果。AI就像“夜班团队”：白天你定方向、做决策，晚上它们执行。

### 8.7 Anthropic团队如何使用Claude Code

Anthropic曾发布“How Anthropic Teams Use Claude Code”报告，记录了其内部各团队如何使用Claude Code。这里选取几个有代表性的案例进行简单介绍。

**数****据****基****础****设****施****团****队****：**用Claude Code调试Kubernetes集群。当Pod出现问题时，让Claude Code读取日志、分析错误栈、定位根因并给出修复建议。过去需要高级工程师花很长时间排查的问题，Claude Code几分钟就能给出解决方案。

**安****全****工****程****团****队****：**用Claude Code追踪复杂的控制流。安全审计需要跟踪一个请求从入口到数据库的完整路径，手动执行极其耗时。现在Claude Code可以自动追踪并生成调用链路图。

**营****销****团****队****：**用Claude Code生成广告变体。一场活动通常需要几十个版本的文案和素材组合，过去设计师和文案要花好几天迭代。现在由Claude Code批量生成，营销人员只需进行选择和微调。

**法****务****团****队****：**这是最令人意外的案例。一位律师用Claude Code搭建了一个电话树系统（来电后自动路由到对应的法律顾问）。这位律师不是工程师，也不会写代码，但从零搭建了这个系统并上线。这个案例让我意识到，Claude Code的受众已经不再局限于工程师。

### 8.8 多智能体写作经验总结

**从****两****个****智****能****体****开****始****。**不要一开始就同时开启10个智能体，先习惯在两个智能体之间切换：一个负责主任务，另一个进行辅助（如写测试、进行代码审查）。等觉得游刃有余了，再逐渐增加智能体数量。

**为****每****个****智****能****体****设****定****明****确****的****角****色****。**不要让智能体什么都做，应进行明确分工：有的负责前端，有的负责后端，有的专门做测试。角色越清晰，你管理起来越轻松。

**用****G****i****t****分****支****进****行****隔****离****。**每个智能体在自己的分支上工作，通过PR合并。千万不要让多个智能体操作同一个分支，否则会产生严重冲突。

**定****期****查****看****。**并行不等于完全不管。建议每隔15～20分钟查看各个智能体的进度，及时纠偏。

**核****心****建****议**

Boris的总结我很认同：把并行工作想象成管理一个远程团队。你不需要盯着每个人写每一行代码，但你要清楚每个人在做什么、进度如何、有没有卡住。你的工作从写代码变成了做项目管理。
