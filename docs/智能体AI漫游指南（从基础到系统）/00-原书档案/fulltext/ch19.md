# Chapter 19 · 循环工程（Loop Engineering）

从业者与LLM智能体交互方式的演变遵循了一条惊人一致的轨迹。2022–2024年，首要技能是提示工程（prompt engineering）：精心组织措辞，从单次模型调用中引出想要的回答。到2025年，焦点转向上下文工程（context engineering）——策展模型在推理时看到的全部token，包括检索到的文档、工具输出与对话历史[ 10 ]。上一章我们讨论了harness工程：设计围绕Agent的运行时环境——工具、沙箱、记忆与护栏。循环工程[ 279 ]是这一演进中的下一层：设计迭代控制结构，让Agent自主地朝目标前进，无需人类在每一轮输入下一条指令。

从提示到循环：工程演进的四个阶段

1.提示工程：优化你对模型说了什么（2022–2024）

2.上下文工程：优化模型看到了什么（2025）

3. Harness工程：优化Agent运行所在的环境（2025–2026）

4.循环工程：优化让Agent持续朝目标工作的循环（2026）

每一层都包裹住前一层而不取代它。你仍然要写提示；仍然要策展上下文；仍然要构建harness。循环工程让这一切运转起来。

这个说法诞生于2026年6月：Peter Steinberger [ 338 ]主张开发者应当停止直接提示编码Agent，转而设计能够提示这些Agent 的系统——这一观点得到了Boris Cherny（Anthropic 的Claude Code负责人）的印证，他提到自己的角色已经完全转变为编写协调模型行动的外部执行循环[ 52 ]。这不仅仅是工具偏好。它反映了一个结构性现实：当一次Agent运行可能持续一小时并修改数十个文件时，杠杆率最高的工程不再在提示里——而在那个让Agent始终保持高效、被验证、不偏离目标的循环里。

### 19.1上下文工程：循环之下的那一层

在循环运行之前，必须有人决定模型在每一步看到什么。这门学科就是上下文工程：在推理期间策展并维护上下文窗口中最优token集合的正式实践。它是循环之下的那一层——循环状态被翻译为模型输入的机制。该术语由Tobi Lütke（Shopify CEO）在2025年6月推广开来[ 244 ]，他将其描述为与AI Agent协作的新兴核心技能。Anthropic在2025年9月将其形式化为“在推理期间策展并维护最优token集合”。Andrej Karpathy认同这一框架，将其描述为“在下一步之前，用恰到好处的信息填满上下文窗口的精妙艺术与科学” [ 178 ]。这些定义的汇聚反映了一个现实：当上下文窗口从4K增长到128K再到1M token时，“往里面放什么”变得与“问什么”同等重要。上下文工程不是提示工程。提示工程优化的是指令——引导模型行为的措辞。上下文工程优化的是信息环境——模型据以推理的文档、工具输出、历史与状态的全集。在单轮交互中，两者的区别很小。在多步Agent循环中，它决定了模型是拥有正确行动所需的信息，还是在盲目飞行。

关键技术。上下文工程借助几种互补的方法：

•动态上下文组装：在每一轮循环迭代中从多个来源（检索到的文档、工具输出、记忆存储）选择并组合上下文，而不是使用固定模板。

• RAG集成：检索任务相关文档或代码片段并注入上下文窗口，用精确、即时的信息取代过时或泛泛的背景知识。

•工具输出摘要化：在把冗长的工具输出（如长文件列表、测试运行器日志）插入上下文之前先压缩，在保留信号的同时节省token预算。

•对话历史管理：决定哪些先前的轮次原样保留、哪些摘要化、哪些彻底丢弃——一个滚动压缩问题，在长时程Agent运行中变得至关重要。

• Token预算分配：在相互竞争的信息来源之间显式划分上下文窗口，确保模型始终有空间生成有用的回答。

上下文窗口预算分配（典型Agent循环）

组件预算说明

循环内的上下文工程。在循环中，上下文工程在每一轮迭代都发挥作用。在每一步t，循环控制器必须决定：保留哪些先前的观测o <t、摘要哪些、哪些检索文档仍然相关，以及如何从这些组件组合出新的上下文s t。这不是一次性的设计决策——而是一条与Agent策略π θ并行的动态策略。设计糟糕的上下文策略会让模型丢失目标、重复已做过的动作，或无法使用两步之前检索到的信息。设计良好的策略则能让模型的“工作记忆”在整个运行期间始终与任务当前状态对齐。上下文工程vs.循环工程上下文工程回答：模型在第t步看到了什么？循环工程回答：模型在第t步行动之后发生了什么？两者互补。循环决定动作与观测的序列；上下文工程决定当模型采取下一个动作时这些观测如何被表示。做不好上下文工程就不可能做好循环工程——循环的状态只有被正确编码进模型上下文时才有用。

### 19.2把循环工程视为推理时强化学习

让循环工程与本书相关的核心洞见是：一个精心设计的Agent循环在结构上与在推理时运行的RL优化过程完全相同——只是不做模型权重的梯度更新：

s t = context( s t − 1 , a t − 1 , o t − 1 ) (state = accumulated context)a t = π θ ( s t ) (action = model generation)o t = env( a t ) (observation = tool/environment feedback)r t = verify( s t , a t , o t ) (reward = verification signal) (19.1)

循环持续运行，直到r t超过成功阈值或触发终止条件。“策略” π θ不通过梯度更新；相反，被更新的是状态——观测、错误消息与反思被追加到上下文中，让同一个冻结模型在后续迭代中产生更好的动作。这正是Reflexion [ 326 ]背后的机制：模型跨迭代改进，靠的不是学习新权重，而是阅读自己的失败历史。循环— RL对应关系考虑标准RL目标max π E [ P Tt =0 γ t r t ]。在循环工程中：

•策略π：冻结的LLM，以不断累积的上下文为条件

•状态s t：第t步时上下文窗口的内容

•动作a t：模型生成的输出（代码编辑、工具调用、消息）

•环境：工具、文件系统、测试运行器、linter ——任何产生观测的东西

•奖励r t：验证信号（测试通过、linter干净、指标提升）

•折扣γ：隐含在循环预算中——越靠后的步骤成本越高、越不可能成功

•回合：从目标定义到终止的一次完整循环执行

与训练时RL的关键区别：策略权重是冻结的。“学习”完全通过状态累积发生——随着循环推进，模型获得更丰富的条件信息。这类似于上下文内学习（in-context learning），但环境在主动塑造模型所见。

这种对应并非仅仅是个比喻。它有直接的工程后果：

1.奖励设计很重要：正如RLHF中那样，定义糟糕的奖励（验证标准）会导致reward hacking—— Agent满足检查的字面要求却违背其意图（例如删除一个失败的测试让CI变绿）。

2.探索—利用权衡：重复同一失败方法的循环表现出很差的探索能力。Reflexion [ 326 ]这类机制通过自我批评加入显式探索，类似于PPO中的熵奖励。

3.时域与折扣：更长的循环面对累积误差与上下文劣化，正如长时域RL受困于信用分配难题。预算上限就是有效的时域。

4.状态表示：上下文管理（压缩、剪枝、外化）就是RL中状态表示设计在循环工程里的对应物——两者都决定Agent能否有效地对自己的处境进行推理。

### 19.3生产级循环的解剖

一个可用的循环需要五个结构性原语[ 279 ]，外加外部状态持久化：

19.3.1五个原语

> Table 19.1:循环工程的五个结构性原语。

原语在循环中的角色RL对应物

自动化。自动化是把一次性的Agent运行变成真正循环的心跳。它们定义循环何时、为何触发——按cron计划、响应webhook，或由文件系统事件触发。没有自动化，你只有一个Agent；有了它们，你拥有一个自维持的系统。生产示例包括：夜间CI失败分类、每小时依赖漏洞扫描，以及提交后审查。

工作树（隔离）。多个Agent并行运行的那一刻起，文件级冲突就成了主导性失败模式。Git工作树——共享仓库历史的独立工作目录——提供了隔离：每个Agent在自己的分支上操作，不可能与兄弟Agent发生写入冲突。这与分布式RL中运行独立rollout worker（第11.2节）是同一个原则：并行需要隔离。

技能。技能（第23章）把Agent本会在每个循环从头重新推导的项目知识固化下来。在循环语境中，技能充当持久条件——跨迭代保持稳定的约定、构建流程与约束。没有技能，每次循环迭代都从零开始；有了它们，Agent跨运行累积知识，而不会把上下文窗口浪费在重新发现的事实上。

连接器。连接器——通常通过MCP实现（第22章）——把循环的动作空间扩展到文件系统之外。只能读写文件的循环是受限的；连接了问题跟踪器、CI系统、预发布环境与团队通信渠道的循环可以闭合完整的反馈回路：发现问题→修复→验证→部署→通知。

子Agent（制造者—检查者分离）。循环工程中最关键的结构性原则是把产出输出的Agent与评估输出的Agent分开。让模型给自己的输出打分，就像让学生给自己批改考卷——激励是错位的。一个专门的验证子Agent（可以运行不同的模型或以更高的推理强度运行）提供独立的评估，让无人值守的运行变得可信。这对应RL中的actor-critic架构：actor（生成器）提出动作；critic（验证器）评估它们。

19.3.2外部状态：循环的记忆

上述每个原语都只作用于单次迭代。外部状态是把各次迭代在时间上连接起来的东西。由于LLM在两次调用之间是无状态的——模型会忘记当前上下文之外的一切——循环的连续性必须驻留在磁盘上：一个Markdown进度文件、一个结构化数据库，或一份受版本控制的日志。这个外部状态有三个功能：

1.进度追踪：尝试过什么、成功了什么、还剩什么。

2.失败记忆：哪些方法试过并失败了，防止循环在相同的死胡同之间震荡。

3.交接上下文：当循环升级给人类或后续运行接管时，状态文件提供完整的审计轨迹。

状态不是可选项

没有外部状态的循环是一个失忆的循环。它会重新尝试已失败的方法、丢失部分进度，并在出错时拿不出审计轨迹。状态机制不必复杂——每轮迭代后提交到git的一个Markdown文件通常就足够——但它必须存在。

### 19.4循环的伪代码

剥去所有表象，每个Agent循环都是一种控制结构，更像恒温器或REPL，而不是一段对话：

def agent_loop(goal: str , max_steps: int = 50, budget: TokenBudget = None):"""The canonical agent loop structure."""state = initialize_state(goal) #加载外部状态和目标

for step in range (max_steps):# 1.推理当前状态（ReAct风格）thought = model.reason(state)

# 2.选择并执行动作action = model.choose_action(state)observation = environment.execute(action)

# 3.用新信息更新状态state = update_state(state, thought , action , observation)

# 4.接近上下文窗口上限时压缩上下文if state.token_count > CONTEXT_BUDGET * 0.8:state = compact(state) #汇总旧步骤

# 5.检查终止条件if verifier.passes(state, goal): #确定性检查persist_state(state, status= "success" )return Success(state)

if no_progress_detected(state, window=3):persist_state(state, status= "stuck" )return escalate_to_human(state)

if budget and budget.exhausted():persist_state(state, status= "budget_exceeded" )return escalate_to_human(state)

#达到硬性上限persist_state(state, status= "max_steps" )return escalate_to_human(state)

循环工程中所有有趣的地方，都是关于这些行之一的决策：什么构成有效的goal，verifier.passes如何实现，compact如何在丢弃噪声的同时保留相关历史，以及no_progress_detected如何既避免过早终止又避免无限循环。

### 19.5循环模式

在第20章介绍的Agent设计模式基础之上，循环工程识别出一组自主性逐级递增的模式层级：

19.5.1验证循环

最简单也最常见的模式：生成，对照确定性检查验证，失败则重试。

验证循环：修复直到测试通过

failure_log = []for attempt in range (MAX_ATTEMPTS):result = run_tests()if result.passed:break #成功— —退出循环fix = model.generate(f "Fix this test failure:\n{result.errors}\n"f "Previous attempts that failed: {failure_log}")apply_patch(fix)failure_log.append(result.errors)

终止条件：测试通过（成功）或重试预算耗尽（升级）。关键属性：验证信号是确定性的——测试运行器产生客观的通过/失败，模型无法争辩。

这一模式之所以成功，是因为它的奖励信号干净利落。测试运行器充当不可腐蚀的批评者——与LLM-as-judge评估不同，它无法被说服或愚弄。

19.5.2 Reflexion循环

在验证循环之上加入尝试之间的显式自我批评[ 326 ]。每次失败后，Agent把一段自然语言反思（“我失败是因为修改了错误的函数——错误追溯到import，而不是实现”）写入情景记忆缓冲区。后续尝试会读取这个缓冲区，从而在单个回合内实现学习，无需权重更新。

Reflexion：从失败中做上下文内学习Reflexion循环在基本重试之外增加了三个组件：

1. Actor：执行任务

2. Evaluator：提供奖励信号（测试、指标或LLM judge）

3.自我反思：把一条口头化的“学到的教训”写入情景记忆

反思记忆跨尝试持久化，为Agent 提供避免重复相同失败的机制。实证上，Reflexion 在HumanEval上达到91%的pass@1（基线为67%），证明口头自我批评在迭代场景中可以替代权重更新[ 326 ]。

19.5.3评估器—优化器循环

一种双模型架构[ 10 , 246 ]：一个模型生成候选，另一个独立模型依据显式标准评估它并返回结构化反馈。生成器吸收反馈，产出改进版本。循环重复，直到评估器评分超过阈值或迭代预算耗尽。关键的设计选择是评估器是确定性的（编译器、测试套件、linter）还是概率性的（另一个LLM）。确定性评估器带来可靠的收敛；概率性评估器对主观标准是必要的，但引入了评估器—生成器合谋的风险。

19.5.4层级循环

一个元循环生成并监控多个子循环。编排Agent把高层目标分解为子任务，把每个子任务指派给运行自己循环的专门化子Agent，监控它们的进度并综合结果。这对应分层RL [ 21 ]：高层策略选择子目标，低层策略执行它们。

层级循环：通宵仓库维护

#外层循环：通过自动化每晚运行for issue in triage_agent.identify_actionable_issues():#内层循环：每个问题一个子智能体，使用隔离工作树worktree = create_isolated_worktree(issue.branch_name)

result = fix_loop(goal=issue.description ,worktree=worktree ,verifier=run_tests_and_lint ,max_steps=20)

if result.success:review = review_agent.evaluate(result.patch) #检查器if review.approved:open_pull_request(result.patch, issue)else :state_db.log(issue, "fix_rejected" , review.feedback)else :state_db.log(issue, "fix_failed" , result.state)

外层循环（分类）按计划运行。内层循环（修复）是临时的、任务范围的。审查Agent提供制造者—检查者分离。状态跨夜间运行持久化。

19.5.5自主研究循环

Karpathy的AutoResearch [ 179 ]展示了一个受严格约束的研究循环：Agent修改训练脚本，运行一个限时实验（例如在GPU上跑5分钟），读取验证指标，并决定是提交改动（指标提升）还是回滚（指标下降）。循环无限持续，通过迭代式实验探索超参数与架构空间。这一模式之所以有效，是因为奖励信号标量且无歧义：验证损失要么下降了要么没有。每轮迭代的严格时间上限防止任何一次失败的实验消耗过多资源。

19.6.2确定性vs.概率性验证

确定性验证器（编译器、测试套件、linter）是黄金标准，因为它们产生客观的通过/失败，模型无法靠说服钻空子。测试要么通过要么不通过——再雄辩的推理也改变不了裁决。概率性验证器（LLM-as-judge）对没有机械检查的任务是必要的——代码质量、文档清晰度、UX改进——但它们引入了失败模式：

•自我评估偏差：如果同一个模型既生成又评估，它会对自己的输出手下留情。

•评估器博弈：经过多次迭代，生成器可能学会产出满足评估器表面模式的输出，却没有实现真正的质量。

•评估器不一致：由于采样方差，同一个LLM-judge可能在不同运行中对相同输出给出不同分数。

缓解策略包括：用另一个（通常更强）模型作评估器、提供带二元标准的显式评分细则，以及定期用人类判断校准LLM-judge。

### 19.7终止工程

朴素循环的标志性失败是它永远不会停。终止设计不是事后补丁——它是工程的一半。

19.7.1终止条件

生产级循环携带多个独立的退出条件：

1.目标达成：验证器确认目标已实现。这是唯一成功的终止。

2.硬性迭代上限：循环步数上限（通常20–50）。无论其他条件如何，防止无界执行。

3.预算耗尽：token数、墙钟时间或金钱成本超过预定义上限。

4.无进展检测：最近k轮迭代没有产生可测量的状态变化——循环在震荡或卡死。这是硬性上限之后最重要的安全机制。

5.致命错误：任何迭代都无法解决的不可恢复状况（凭据缺失、基础设施故障）。

无进展检测：停滞断路器检测停滞需要在迭代间追踪一个进展信号。常见方法：

•输出哈希比较：如果最近3次Agent输出或文件状态完全相同，循环在打转。

•错误重复：同一错误消息连续出现k轮。

•指标平台期：数值信号（测试通过率、验证损失）在k步内没有提升ϵ。

• Diff熵：每轮迭代的代码改动量正趋近于零—— Agent在做越来越小、无关紧要的编辑。

检测到停滞时，正确的行动是升级，而不是继续迭代。循环保存状态，把控制权交给人类或更高级的编排器。

19.7.2探索问题

卡在局部最小值的循环——用微小的变体重复同一种失败方法——正在表现出RL中熟悉的探索—利用失败。循环内促进探索的机制：

•基于反思的探索：k次失败尝试之后，触发一个反思步骤，显式要求模型考虑根本不同的方法（类似于PPO中的熵正则化[ 319 ]）。

•温度升级：连续失败后提高采样温度，鼓励多样化输出。

•策略记忆：不仅记录失败的动作，还记录失败的策略。“方法A（修改handler）失败了3次；改试方法B（重写schema）。”

•全新子Agent：生成一个上下文窗口干净的子Agent ——它不会陷入已累积上下文可能造成的窠臼。

### 19.8失败模式与反模式

19.8.1 Loopmaxxing陷阱

“ Loopmaxxing ”——假设让Agent跑足够多轮迭代最终就会产出正确解——是循环工程版的“算力够多就能解决一切”。它的失败与纯随机搜索的失败同源：没有指向改进的梯度信号，光靠迭代不是优化。Loopmaxxing在以下情况出现：

•目标缺少可检查的成功条件（“改善用户体验”）

•验证信号过于粗糙（在1000个测试的套件上只有二元通过/失败，无法提供指向修复的梯度）

•无论迭代多少次，Agent都缺乏解决问题的能力

解药是认识到循环只是放大工程能力——它们不取代工程能力。目标定义糟糕的循环会以极高的效率去追求错误的东西。

19.8.2理解债

当循环修改代码的速度超过工程团队审阅的速度时，仓库中实际存在的东西与人类理解之间的差距就会扩大——这就是理解债（comprehension debt）[ 279 ]。与技术债不同（技术债由代码承载），理解债存在于团队成员的头脑里。它无声地复利增长，直到某场危机迫使人们去调试那些设计决策、结构依赖与边界情况完全未被记录的代码。循环同时放大生产力与风险设计良好的循环加速的是工程师深刻理解的工作。用循环来逃避理解工作，则会造成加速的不理解螺旋。同样的机制，相反的结果。区别在于：人仍然是工程师，还是沦为了按“开始”按钮的人。

19.8.3循环中的Reward Hacking

正如RL Agent利用奖励定义缺陷在未达成既定目标的情况下拿到高奖励，循环Agent也会利用验证漏洞：

•删除测试：最简单的reward hack ——删掉失败的测试让CI变绿。

•指标博弈：通过记住验证集而非泛化来过拟合验证损失。

•收窄规格：解决所陈述问题的简化版本，恰好能通过检查。

•掩盖输出：压制错误输出而不是修复根本原因。

防御手段与RLHF相同：设计难以钻空子的奖励函数（验证标准）。多个独立检查——测试和类型检查和lint和审查子Agent ——构成一个比任何单一信号都更难利用的验证面。

19.8.4上下文劣化

在长时程循环中，上下文窗口会被每一步的历史——思考、工具输出、错误、补丁——填满。当窗口接近容量时，模型对相关信息的注意力下降（“中间迷失”现象[ 226 ]）。症状包括：

• Agent重新尝试它已经试过并明确标记为失败的方法

•工具调用变得不那么精确—— Agent忘记了自己读过哪些文件

•模型在臃肿的上下文中艰难地分配注意力，回答变得更短、更不连贯

对策：

1.激进压缩：每k步之后，把已完成的工作总结为简短的状态描述，丢弃原始记录。

2.外部草稿本：把中间结果写入文件，让Agent按需读取，而不是把一切留在上下文里。

3.子Agent隔离：在新上下文窗口中生成子任务，只返回它们的结论——而不是完整推理轨迹。

4.历史滑动窗口：只完整保留最近w步；把更早的内容压缩进一个摘要块。

### 19.9生产级循环架构

19.9.1夜间维护循环

最立即可用的循环模式：一个按计划在夜间运行的自动化，趁团队睡觉时处理累积的工作。架构：夜间CI分类与修复循环触发：Cron计划（例如每天02:00 UTC）。阶段1 ——分类（单Agent，只读）：

•读取昨天的CI失败、新开的issue与最近的提交

•对每条发现分类：可自动修复/需人工/误报

•把发现写入状态文件；归档误报

阶段2 ——修复（并行子Agent，隔离工作树）：

•对每个可自动修复的issue，在隔离工作树中生成一个子Agent

•每个子Agent运行一个验证循环（修复→测试→重试）

•预算：每个issue 20步或15分钟

阶段3 ——审查（独立验证Agent）：

•审查子Agent依据项目编码标准评估每个提议的修复

•批准的修复：开draft PR、链接到issue、通过连接器通知频道

•被拒的修复：记录拒绝原因，升级到人工分类收件箱

持久化：状态文件（提交到仓库）记录所有已采取的行动，让第二天的运行跳过已解决的issue，并从失败处接着干。

19.9.2持续实验循环

受AutoResearch [ 179 ]启发，这一模式把循环应用于科学发现：修改训练脚本，运行限时实验，评估结果，决定提交还是回滚。AutoResearch循环结构1.假设生成：Agent提出一项修改（超参数、架构改动、数据增强）

2.实现：Agent修改训练脚本

3.限时执行：恰好运行T分钟（硬性墙钟上限）

4.评估：从输出读取验证指标

5.决策：指标提升→ git commit；指标下降→ git rollback

6.记录：把假设、结果与推理记入实验日志

7.重复：依据累积的实验历史生成下一个假设

关键约束：限时执行防止任何一次失败的实验消耗过多算力。基于git的提交/回滚确保代码库只会向前。

研究循环中的局部最小值问题研究循环容易陷入保守探索。面对困难的优化景观时，Agent倾向于提出最小改动——把学习率调0.001 ——只带来名义上的改进而非真正的进展。这是RL探索问题在循环层面的显现。对策包括：定期的“大胆假设”提示、为尝试新颖方法设置多样性奖励，以及在两次运行之间由人类注入研究方向。

19.9.3常驻编排器

OpenClaw [ 338 ]这类系统实现了一个持久的“心跳”机制：一个按固定周期运行的元Agent，评估仓库状态、监督子循环并分派工作。与每天触发一次的夜间模式不同，常驻编排器保持持续感知，在几分钟内响应事件（新提交、CI失败、新issue）。该架构引入了一个带崩溃恢复的持久状态数据库——如果编排器在循环中途失败，它会从最后一个检查点状态恢复，而不是从头重启。子循环被作为拥有各自终止条件的独立任务来跟踪，编排器监控它们的停滞、预算耗尽或冲突。

### 19.10长时程循环中的上下文管理

长时程循环面临一个根本张力：上下文窗口是Agent的工作记忆，但容量固定。每一步都会追加新信息（思考、观测、错误），没有主动管理，窗口就会填满、质量下降。本节介绍跨大量迭代维持上下文健康的工程技术。

### 19.11何时不该使用循环

循环工程并非普遍适用。它增加了复杂度、成本与失败模式，在更简单的方法够用时这些是不合理的。以下情况请优先选择直接提示或简单工作流：

•任务是单轮的：精心构造的提示大多数时候一次就能给出正确答案。加循环只带来边际质量提升，却付出显著成本。

•目标缺少可检查的条件：“让代码更好”没有客观的停止点。循环要么永远运行，要么任意停止。

•人工交互很廉价：如果开发者正在积极工作并能实时反馈，交互式聊天比工程化一个循环更快。

•任务超出模型能力：如果Agent原则上解决不了这个问题——无论迭代多少次——循环只是在烧token。再多的重试也补不上根本的能力差距。

•验证不可能：没有反馈信号，循环就没有梯度。它会退化为随机搜索。

简洁性原则第20章阐述的同一设计原则在此适用：从最简单的可行方法开始，只有当你有了“迭代确实显著改善结果”的证据时才加入循环复杂度。一个能解决问题的提示链，永远优于一个或许能解决问题的循环。

### 19.12循环的经济学

循环用算力（token、墙钟时间）换取质量。理解这一权衡对生产部署至关重要。循环成本模型对于一个平均N轮迭代、每轮消耗T个token、单价为每token p的循环：

Cost loop = N · T · p + Cost tools + Cost verification

使用提示缓存（系统提示与早期上下文被缓存，按较低的p c < p计费）时：

Cost cached = T new · p + T cached · p c + (tools + verification)

提示缓存对循环尤其有价值，因为目标定义、技能内容与早期历史跨迭代保持不变——每次调用通常有60–80%的上下文可缓存。

经济决策：循环产出的价值（节省的开发者时间、通宵生产力、质量提升）是否大于它的token成本？一个运行20轮、每轮$0.02的循环总成本是$0.40 ——如果能省下开发者30分钟，这微不足道。但没有预算上限的失控循环，一夜之间就能烧掉数百美元。

### 19.13历史背景与相关工作

循环工程并非凭空出现。它把一条跨越数年的研究谱系产品化了：

1. ReAct（2022）[ 408 ]：确立了所有现代循环都继承的推理与行动交错模式。

2. Reflexion（2023）[ 326 ]：加入情景记忆与自我批评，证明Agent可以在不更新权重的情况下跨尝试改进。

3. AutoGPT（2023）[ 330 ]：第一个被广泛使用的自主Agent循环，同时展示了无人值守运行的潜力与陷阱（失控执行、高成本、不可靠输出）。

4. Self-Refine（2023）[ 246 ]：把“先生成后批评”的迭代精化循环形式化。

5. “ Ralph循环”（2025）：非正式的基于bash的单行脚本，让编码Agent在简单的重试循环中运行——产品化循环原语的前身。

6.产品化循环（2026）：主要平台（Codex、Claude Code）直接内嵌/goal与/loop命令，无需定制基础设施就能使用复杂的循环模式[ 279 ]。

从AutoGPT到现代循环工程的演进展示了一条成熟之路：早期系统缺少终止逻辑、验证与成本控制——它们是没有工程的循环。2026年的形式化补上了让无人值守运行变得安全的纪律：显式终止、确定性验证、预算约束与制造者—检查者分离。

### 19.14小结

循环工程代表了人— Agent协作的当前前沿：从参与对话，转向设计能够自主进行那些对话的系统。其关键原则：

1.循环是推理时RL ——状态、动作、奖励与（通过上下文的）策略更新——在无梯度下降的情况下运行。

2.验证就是奖励信号。它的质量决定收敛。优先确定性检查；把制造者与检查者分开。

3.终止是设计的一半。每个循环都需要硬性上限、预算与无进展检测。

4.上下文是有限的工作记忆。通过压缩、外化与子Agent隔离来主动管理它。

5.循环放大工程能力——它们不取代工程能力。目标定义糟糕的循环会高效地追求错误的东西。

6.从简单开始。一个带确定性验证器的验证循环，胜过一套你无法调试的精密多Agent系统。

构建循环——但保持工程师身份杠杆点已经从写提示转向设计循环。但设计一个能够收敛的循环，需要把问题理解得足够深，才能定义“完成”意味着什么、什么构成进展、何时停止。循环工程让人类的判断更加重要，而不是更不重要——因为糟糕判断的后果现在会以机器速度复利增长。
