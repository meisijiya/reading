# 第五章 Coding Agent 与通用 Agent

> 前面几章分别交付了上下文工程和工具设计，本章把它们组合起来：为什么"Coding Agent + 文件系统"是通用 Agent 的内核，怎么围绕它搭建 Harness，以及代码作为"元能力"如何延伸到思考、规则、多媒体、界面乃至 Agent 自身。

## Q5-1 一个基础 Coding Agent 需要哪七个核心工具？

- 章节: ch06 §5.1.1　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 七个核心工具

> 📖 **原文** (ch06 §5.1.1)：**代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力**。在当前 SOTA 模型的加持下，具备基本 coding 能力并不需要复杂的架构。

> 📖 **原文** (ch06 §5.1.1)：为了支持这五类操作，一个基础的 Coding Agent 只需配备以下七个核心工具：

> 📖 **原文** (ch06 §5.1.1)：1. **Code Interpreter（代码解释器）**：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码在其中运行即使出错也不会影响宿主机），安全执行 Python 代码

> 📖 **原文** (ch06 §5.1.1)：5. **编辑文件工具**：对现有文件进行局部修改，是代码维护和迭代的核心操作

> 📖 **原文** (ch06 §5.1.1)：6. **搜索文件名工具（Glob）**：通过模式匹配快速定位文件系统中的目标文件，例如用 `**/*.py` 找出项目中所有 Python 文件

> 📖 **原文** (ch06 §5.1.1)：7. **搜索文件内容工具（Grep）**：在文件内容中搜索特定的文本模式，例如搜索所有调用了某个函数的代码行

> 📖 **原文** (ch06 §5.1.1)：这七个工具构成了一个完整但极简的工具箱，几乎任何 Agent 系统都可以低成本地集成。

> 📖 **原文** (ch06 §5.1.1)：注意，这个工具集是 Coding Agent 特有的基础配置，不同于第四章按调用方向和作用性质划分的五类通用工具分类（感知/执行/协作/事件触发/用户沟通）。七个核心工具主要覆盖了感知和执行两类。协作、事件触发、用户沟通这三类需求仍需要其他工具，但它们不是 Coding Agent 的核心。

🧭 **归纳**：以"整理仓库中所有遗留的 TODO 注释"这类任务反推，需要五类操作（浏览目录、读代码、改文件、跑命令、找模式），对应七个工具：

| # | 工具 | 对应操作 |
|---|---|---|
| 1 | Code Interpreter | 跑代码、算、画图 |
| 2 | Bash Shell | 运行测试、处理特殊格式 |
| 3 | 读文件 | 读代码、配置、文档、日志 |
| 4 | 写文件 | 新建或完全重写 |
| 5 | 编辑文件 | 局部修改（代码维护的核心操作） |
| 6 | Glob | 按文件名模式定位 |
| 7 | Grep | 按内容模式定位 |

注意这套工具箱是 Coding Agent 专用配置，与第四章的五类通用工具分类不是同一套切法：七个工具主要落在"感知 + 执行"，协作、事件触发、用户沟通仍需另外补齐。

## Q5-2 为什么说 Coding Agent + 文件系统是通用 Agent 的核心？边界在哪？

- 章节: ch06 §5.1.2　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 通用Agent架构范式与边界

> 📖 **原文** (ch06 §5.1.2)：以 Manus 为代表的通用 Agent 产品，将 Deep Research（深度调研）、Computer Use（电脑操控）和 Coding（代码生成）三大能力融合在一个系统中，凸显了一个已经被多类实践反复验证的洞察：**Coding Agent 加上文件系统，是开放任务型通用 Agent 最核心的技术基础**。

> 📖 **原文** (ch06 §5.1.2)：为什么 Coding Agent 是核心而非其他两种？因为几乎所有高效的内容生成最终都要落到代码上。PPT 本质上是 OOXML（Office Open XML，微软推出的办公文档开放标准）格式的代码，Word 文档和 PDF 报告可通过代码生成，数据分析和可视化由 Python 脚本完成

> 📖 **原文** (ch06 §5.1.2)：整个过程中，文件系统是信息流转的枢纽——记忆从文件读取，产物写入文件，经验也保存为文件。

> 📖 **原文** (ch06 §5.1.2)：**适用边界：哪些 Agent 以 Coding 为核心架构**。“Coding Agent 是通用 Agent 的核心” 这一判断主要适用于**以开放任务为目标**的通用 Agent——深度调研、内容生成、数据处理这类任务边界不确定、产物形态多样的场景。在这些场景中，无法预先枚举所有需要的工具，代码生成作为元能力提供了动态扩展能力边界的最经济路径，因此它是架构的核心。

> 📖 **原文** (ch06 §5.1.2)：而另一类 Agent——例如垂直领域的客服 Agent——任务空间相对封闭，核心架构围绕固定的业务流程、领域工具和对话策略构建，代码在其中更多是工具箱里的一件工具而非架构中枢。但即便在后者，coding 也是重要的基础能力：精确计算、数据处理、规则校验都离不开它。这正与前一节 “Coding 是 Agent 的基础能力” 的论断呼应：是否以 Coding 为核心架构因场景而异，但具备 coding 能力是所有 Agent 的共同底线。

🧭 **归纳**：这套判断的两条适用边界：

- **以 Coding 为架构核心**：开放任务型（深度调研、内容生成、数据处理）——任务边界不确定、产物形态多样，无法预先枚举工具，代码是动态扩展能力边界最经济的路径。
- **以 Coding 为基础能力（但不作为架构中枢）**：垂直封闭型（客服 Agent）——架构围绕固定业务流程、领域工具和对话策略。

结论是分层的：是否以 Coding 为核心架构因场景而异，但具备 coding 能力是所有 Agent 的共同底线。

➕ **补充**：书中给出的执行流示例（读 `MEMORY.md` → 查 API 用法 → 下载数据 → 写 Python 脚本 → 生成 `report.pdf` → 回写记忆）说明文件系统承担了三种角色：记忆载体、产物落盘处、经验沉淀地。

## Q5-3 推荐的工程化流程有哪些阶段？项目指令文件起什么作用？

- 章节: ch06 §5.1.3　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 流程阶段与项目指令文件

> 📖 **原文** (ch06 §5.1.3)：下面描述的是一套**推荐的工程化流程**，它把软件工程的最佳实践投射到 Agent 身上，勾勒的是理想形态。现实中的 Coding Agent（如 Claude Code、OpenClaw）更多按反应式的迭代循环工作，会**按需裁剪**这套流程——简单任务会跳过设计文档、不会每一步都阻塞等待用户批准，只有当任务复杂、影响面大时才会完整走完各阶段。

> 📖 **原文** (ch06 §5.1.3)：Coding Agent 的工作始于对项目的系统性理解。当 Agent 首次接触一个代码仓库时，首要任务不是马上动手改代码，而是先建立对整个项目的认知框架。

> 📖 **原文** (ch06 §5.1.3)：如果关键文档缺失，Agent 不应在盲目状态下开始工作，而应主动承担文档化的责任——通过系统性地阅读代码库，识别主要模块、核心抽象、组件间依赖关系，生成包含架构概览、目录结构、测试运行指南的初始文档。这份文档既为 Agent 后续工作提供蓝图，也为其他开发者提供了入口点。

> 📖 **原文** (ch06 §5.1.3)：项目文档化如今有了一种 Agent 专用的形态：**项目指令文件**。CLAUDE.md、AGENTS.md、.cursorrules 等文件已成为业界事实标准——它们在每次会话开始时被自动注入上下文，相当于项目级的系统提示词。与面向人类读者的 README 不同，指令文件承载的是面向 Agent 的行为约定：构建与测试命令（“用 `pnpm test` 而不是 `npm test`”）、代码风格（“禁用 any 类型”）、明确的禁区（“不要改动 `migrations/` 目录”）。

> 📖 **原文** (ch06 §5.1.3)：在需求模糊的状态下就开始编码，往往导致大量返工。

> 📖 **原文** (ch06 §5.1.3)：把“测试通过”而非“代码写完”定义为完成标准

> 📖 **原文** (ch06 §5.1.3)：过时的文档比没有文档更糟糕，因为它会误导未来的开发者。

> 📖 **原文** (ch06 §5.1.3)：这套流程体现了软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化。

🧭 **归纳**：推荐的阶段顺序与每阶段的关键交付：

1. **项目文档化** — 先建立认知框架；文档缺失就主动生成。产物形态是项目指令文件（CLAUDE.md / AGENTS.md / .cursorrules）。
2. **任务理解与需求澄清** — 区分边界清晰的简单需求与模糊的复杂需求，后者先澄清再动手。
3. **编写设计文档** — 把抽象需求变成实现计划，同时为人类提供低成本介入点（审设计比审几百行代码容易）。
4. **代码实现与测试** — 测试驱动，"测试-修复"循环多轮迭代；完成标准是"测试通过"而非"代码写完"。
5. **代码审查** — 可读性、性能、安全、风格，可用 lint 或专门的审查子 Agent。
6. **文档同步与交付** — 架构层面的改动必须同步更新架构文档。

项目指令文件的三重价值：项目级系统提示词、KV Cache 友好的稳定前缀、"知识必须存在于代码库本身"原则的直接落地。

## Q5-4 为什么 Coding Agent 是成熟度最高的 Agent 类型？

- 章节: ch06 §5.1.4　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 四象限与四条Harness原则

> 📖 **原文** (ch06 §5.1.4)：可以用任务清晰度和验证自动化程度两个维度，将任务分成四种状态。目标明确且结果可自动验证，是最适合 Agent 发挥的区域；目标清楚但验收还得靠人盯，吞吐量的天花板就是人的审查速度；有自动化反馈但目标模糊，系统会高效地往错误方向跑；两者都缺，Agent 基本派不上用场。

> 📖 **原文** (ch06 §5.1.4)：代码编写天然处于这个象限的核心——测试套件提供明确的验收标准，Linter 和类型检查器提供即时的自动化验证，Git 提供完美的版本控制和回退能力。这就解释了为什么 Coding Agent 是当前所有 Agent 类型中成熟度最高的：不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness。

> 📖 **原文** (ch06 §5.1.4)：**约束优先于指导**：能用代码强制的规则就不要用文档建议。Linter 规则、类型约束、CI 检查的价值远超系统提示词中“请遵循…”式的指导——前者是“做不了”，后者只是“建议别做”。

> 📖 **原文** (ch06 §5.1.4)：**反馈越快越好，越结构化越好**：错误信息越详细、越接近错误发生的时刻，Agent 的纠正效率越高。

> 📖 **原文** (ch06 §5.1.4)：**回退要可靠**：Agent 在安全网内操作才能大胆试错。Git 分支、沙盒环境、快照机制确保任何错误都可逆。

> 📖 **原文** (ch06 §5.1.4)：**约束的另一层目的：防止过程性错误。** 验收基线管的是结果对不对，执行边界管的是**过程**——即使结果正确，用错误的方法达成也不行。

> 📖 **原文** (ch06 §5.1.4)：**工具编排：故障边界控制**。成熟的 Coding Agent 支持并行工具调用，Harness 视角下的独特问题是**故障如何传播**：一个工具失败时，哪些调用应当中止、哪些应当继续？

🧭 **归纳**：四象限（表5-1）与 Harness 的目标：

| | 结果可自动验证 | 结果需人工验证 |
|---|---|---|
| **目标明确** | 最佳区域：修复有测试用例的 bug | 吞吐量受限：代码重构需人工审查 |
| **目标模糊** | 高效地跑偏：用 linter 优化"代码质量" | 难以启动："让 UI 更好看" |

Harness 的目标就是把尽可能多的任务推向"目标明确 + 验证自动化"象限。四条可迁移原则：**约束优先于指导**、**验证要自动化**、**反馈越快越结构化越好**、**回退要可靠**。

另一条容易忽略的原则：执行边界管的是**过程**。即使结果正确，用错误方法达成也不行（删库重建"修好"了故障但数据没了）。因此要约束的是动作，而不仅是结果。

## Q5-5 生产级 Harness 会遇到哪些故障？怎么检测？

- 章节: ch06 §5.1.5　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 四层故障与检测模式

> 📖 **原文** (ch06 §5.1.5)：**故障分类学：四层故障。** 系统应对的第一步是分类。按故障发生的位置，可以分为四层：

> 📖 **原文** (ch06 §5.1.5)：**API 层**：限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断。这类故障与任务内容无关，是基础设施的噪声。

> 📖 **原文** (ch06 §5.1.5)：**工具层**：幻觉调用（调用了不存在的工具）、参数畸形（不符合工具的输入约束）、执行抛异常，以及最危险的一种——工具反复返回同一个错误，而模型不加改变地反复重试。

> 📖 **原文** (ch06 §5.1.5)：**上下文层**：上下文窗口溢出、压缩失败、轨迹结构损坏（如工具调用缺少配对的结果消息）。

> 📖 **原文** (ch06 §5.1.5)：**控制流层**：死循环（反复执行相同操作却毫无进展）与死亡螺旋（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应）。

> 📖 **原文** (ch06 §5.1.5)：**检测：先分类，再计数。** 捕获故障后的第一个判断不是“要不要重试”，而是“值不值得重试”。可重试的错误（限流、过载、网络抖动）重试才有意义；不可重试的错误（参数不合法、权限不足、工具不存在）原样重试多少次都是同样的结果，必须改变输入或策略。生产级 Harness 维护一张错误到恢复策略的映射表，而不是笼统地“出错就重试”。

> 📖 **原文** (ch06 §5.1.5)：单次错误之外，还要检测**模式**。一是重复调用指纹：对“工具名 + 参数”计算指纹，相同指纹反复出现就是无进展循环的明确信号——第一章消融实验中 Agent 反复调用同一工具，正是这种模式。

> 📖 **原文** (ch06 §5.1.5)：还有一类故障不表现为错误，需要专门的**活性与完整性监控**。流式连接最危险的失败模式不是断开（这会立即报错），而是静默卡死

🧭 **归纳**：四层故障与各自的检测手段：

| 层 | 典型故障 | 关键检测 |
|---|---|---|
| API 层 | 限流、过载、超时、连接中断、输出截断 | 可重试分类 + 错误到策略的映射表 |
| 工具层 | 幻觉调用、参数畸形、同一错误反复重试 | "工具名 + 参数"指纹去重 |
| 上下文层 | 窗口溢出、压缩失败、轨迹结构损坏 | 轨迹完整性校验，注入前自动补配对 |
| 控制流层 | 死循环、死亡螺旋 | 连续失败计数、无进展模式识别 |

不报错的故障最危险：流式连接的**静默卡死**（连接建立但数据流停止），SDK 超时往往只覆盖初始连接而非传输过程——需要独立的空闲看门狗。推广出的原则是：每个长连接都需要活性信号，而非仅依赖连接超时。

## Q5-6 恢复如何分级升级？什么时候必须终止？

- 章节: ch06 §5.1.5　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 恢复分级熔断与死亡螺旋

> 📖 **原文** (ch06 §5.1.5)：**恢复：分级升级，逐级透明。** 恢复手段按对用户透明的程度分级，能用低级别解决就不升级：

> 📖 **原文** (ch06 §5.1.5)：1. **静默重试**。可重试错误的默认动作。两个细节决定成败：指数退避叠加随机抖动，避免大量客户端同步重试造成二次拥塞，并尊重服务端返回的等待时长提示；区分前台与后台调用——主循环的请求失败要重试，标题生成、输入建议这类辅助性后台调用失败则直接放弃，否则后台重试会挤占主链路的配额，形成“重试放大”。

> 📖 **原文** (ch06 §5.1.5)：2. **降级与接续**。重试无效时，改变请求本身再试。以输出触顶（生成到一半被长度限制截断）为例：先静默提升输出上限重发，仍不够再在消息末尾追加元指令、让模型从断点接续生成。

> 📖 **原文** (ch06 §5.1.5)：3. **暴露给用户**。所有自动手段用尽后才呈现错误，并附上已经尝试过的恢复动作。

> 📖 **原文** (ch06 §5.1.5)：**终止：每条恢复路径都要有上限。** 恢复机制本身也可能失效，因此每条恢复路径都必须有明确的熔断上限：上下文压缩连续失败若干次就放弃压缩，权限分类连续失败就回退到人工询问，输出接续最多尝试固定轮数。阈值从哪来？答案是产线数据而非拍脑袋。

> 📖 **原文** (ch06 §5.1.5)：比单点熔断更隐蔽的是**死亡螺旋**：错误路径上触发的逻辑自身又调用 LLM，再次出错，连锁触发。

> 📖 **原文** (ch06 §5.1.5)：说得再本质些——**Agent 的可靠性不取决于它犯不犯错，而取决于每类错误是否都有对应的检测、恢复与终止路径**。

🧭 **归纳**：恢复三级（按对用户透明度递增）：

1. **静默重试** — 指数退避 + 随机抖动；区分前台与后台调用，避免"重试放大"挤占主链路配额。
2. **降级与接续** — 改请求本身：提升输出上限、从断点接续、降级到备用模型（需先剥离旧模型私有格式块）、回落到标准模式。
3. **暴露给用户** — 所有自动手段用尽后才呈现，并附上已尝试过的恢复动作。

终止的纪律：每条恢复路径都有熔断上限，阈值来自产线数据而非拍脑袋（书中给出的例子是"连续 3 次"，理由是绝大多数故障在此之前已恢复、继续重试基本无望）。死亡螺旋的防护靠两条：错误路径上禁用一切会再次调用模型的副作用逻辑，以及递归深度计数器。

➕ **补充**：书中给出的熔断阈值依据很具体——曾有一个会话在某条恢复路径上连续失败三千余次，仅这类无效重试每天就浪费约 25 万次 API 调用；逾千个会话出现过 50 次以上连续失败。这类"从真实会话统计里取经验拐点"的做法，比经验值更有说服力。

## Q5-8 文件编辑有哪几种方案？各自的取舍是什么？

- 章节: ch06 §5.1.8　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 五种编辑方案对比

> 📖 **原文** (ch06 §5.1.8)：文件编辑的难点不在于操作本身，而在于如何让 LLM 以高效又可靠的方式告诉系统 “改哪里、怎么改”。

> 📖 **原文** (ch06 §5.1.8)：**差异描述 + Apply Model**：模型不是直接指定如何编辑文件，而是生成一份变更描述——可以是类似 git diff（即 `git diff` 命令输出的那种“删了哪几行、加了哪几行”的格式）的差异文本，也可以是带省略标记的代码骨架（用“此处保持不变”之类的注释跳过未修改部分）。这份描述随后交给专门的“应用模型”（Apply Model）——通常是另一个更小、更快的 LLM——负责与原文件合并、产出完整的新文件。

> 📖 **原文** (ch06 §5.1.8)：**旧字符串到新字符串**（Old String → New String）：Claude Code、Codex 和今天 Cursor 采用的方案。模型提供 old string（要被替换的原文）和 new string（替换后的新文本），框架执行简单的字符串查找替换。优势是可预测性和透明性——old string 在文件中存在且唯一则成功，否则失败，不存在模棱两可。代价是删除大段代码时需完整输出所有原始内容，一个字符的偏差就会匹配失败；同一代码出现多次时需提供更长的上下文来消除歧义。

> 📖 **原文** (ch06 §5.1.8)：**行号定位**（Old Line Numbers → New String）：模型指定 “删除第 X 到 Y 行，插入新内容”。只要读文件工具提供了行号信息，模型就可以精确地看到欲删除内容的行号。行号精确无歧义，大段删除只需首尾行号两个数字。但问题是，每次编辑后后续行号都会变化，模型一次思考可能会输出多处编辑，此时需要像 diff 一样，让模型在多次编辑中都使用初始行号来定位，以免出现混淆。

> 📖 **原文** (ch06 §5.1.8)：**字符串首尾匹配**（Old String Start + End → New String）：可以看作旧字符串替换方案的改进。模型不需要输出完整的 old string，只需提供要删除内容的开头几行和结尾几行，中间部分可省略。框架通过匹配这个开头和结尾来定位替换区域，只要这对 “首尾” 组合在文件中唯一就能准确定位。

🧭 **归纳**：五种方案的取舍：

| 方案 | 模型要输出 | 优势 | 风险 |
|---|---|---|---|
| 差异描述 + Apply Model | diff 或代码骨架 | 主模型专注高层逻辑 | 合并环节脆弱，微小出入就可能合错位置 |
| 旧字符串 → 新字符串 | old + new 全文 | 可预测、透明、唯一即成功 | 删大段代码要全量输出，差一个字符就失败 |
| 行号定位 | 起始行号 + 新内容 | 无歧义，大段删除只给两个数字 | 多次编辑后行号漂移 |
| 类 Vim 命令 | 编辑命令序列 | 重组代码高效 | 学习负担大，模型算不准修改后行号 |
| 字符串首尾匹配 | 开头几行 + 结尾几行 | 综合了可靠与效率，模型犯错率低 | 首尾组合需在文件中唯一 |

值得注意的一条判断：Vim 这类编辑器是为人类设计的——人类需要不断看到当前状态、规划下一步的简单操作；而模型的工作模式是经过较长时间的思考，再批量进行较复杂的操作。

## Q5-9 致命三要素是什么？持久记忆为什么算第四个维度？

- 章节: ch06 §5.1.9　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 攻击闭环与持久记忆

> 📖 **原文** (ch06 §5.1.9)：Coding Agent 拥有读写文件、执行命令、访问网络的权限，这意味着一旦被注入恶意指令就可能造成不可逆的损失。Simon Willison 将这种风险概括为著名的 “致命三要素”：

> 📖 **原文** (ch06 §5.1.9)：1. **访问私有数据**——Agent 能读取用户文件和密码管理器

> 📖 **原文** (ch06 §5.1.9)：攻击路径由此闭合：恶意指令藏在不受信任的内容中进入 Agent，驱使它读取私有数据，再经对外通道传出。

> 📖 **原文** (ch06 §5.1.9)：在此基础上，笔者补充第四个维度——**持久记忆**。它不是并列的第四个必要条件，而是攻击的放大器：攻击者可将看似无害的偏见或恶意指令写入 Agent 的长期记忆，跨会话潜伏，在合适的时机再触发，把一次性攻击升级为长期的潜伏与放大。

> 📖 **原文** (ch06 §5.1.9)：这也解释了为什么闭源的商业 Agent，如 Claude Cowork（Anthropic 面向知识工作的通用 Agent，复用 Claude Code 的架构，能读写本地文件、跨多个办公应用完成复杂任务），选择了保守的权限策略——不是技术做不到，而是安全风险太高。面对提示注入威胁，单靠输入过滤基本挡不住。重点不是识别所有攻击，而是让 Agent 即使被注入，也没有机会把危险动作真正执行出去。

> 📖 **原文** (ch06 §5.1.9)：同一上下文中的 Agent 很难判断自己是否已被注入，因此关键操作必须由上下文之外的机制复核，这一原则贯穿两章。

🧭 **归纳**：致命三要素 + 放大器：

1. **访问私有数据** — Agent 能读取用户文件和密码管理器
2. **暴露于不受信任内容** — 处理的邮件和网页可能包含恶意载荷
3. **具备外部通信能力** — 能发送邮件和执行命令

三者齐备即构成完整攻击闭环：**恶意指令藏在不可信内容里 → 驱使 Agent 读取私有数据 → 经对外通道传出**。

持久记忆是**放大器而非第四个必要条件**：把一次性攻击升级为跨会话潜伏。对应四类边界——数据边界、输入信任边界、输出影响边界、跨会话边界；四者兼备的全权限本地 Agent（如 OpenClaw）安全防护因此成为核心挑战。

防御思路的关键转向：重点不是识别所有攻击，而是让 Agent **即使被注入也没有机会真正执行危险动作**——关键操作必须由上下文之外的机制复核。

## Q5-10 代码执行沙盒的工程选型和命令安全校验怎么做？

- 章节: ch06 §5.1.9　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 沙盒四增量与语义解析

> 📖 **原文** (ch06 §5.1.9)：**网络出口控制**。这是最容易被忽视、却最关键的一项：默认断网，按需通过白名单代理放行有限目的地（包管理源、文档站点、任务明确需要的 API）。回看致命三要素的第 3 条——“具备外部通信能力”——网络出口控制正是它的执行面防御：即使提示注入成功、恶意代码在沙盒内读到了敏感数据，没有出口就传不出去。

> 📖 **原文** (ch06 §5.1.9)：**文件系统隔离范围**。源码目录以只读方式挂载（Agent 通过编辑工具修改代码，生成的补丁经审查后落盘，或将副本挂入可写工作区），单独的可写工作区目录承载生成物和中间文件；凭证类文件（`~/.ssh`、密钥、token）根本不挂载进沙盒。

> 📖 **原文** (ch06 §5.1.9)：**资源限额与超时**。CPU、内存、磁盘配额加超时，防御死循环、fork 炸弹（疯狂自我复制进程直到拖垮系统）和无限写盘。一个实践细节：超时和超限应向 Agent 返回结构化错误（“执行超过 120 秒被终止，最后输出如下……”）而非静默杀死进程，让 Agent 有机会在下一轮修正策略。

> 📖 **原文** (ch06 §5.1.9)：**安全：语义解析而非关键字黑名单**。第一章提到验证层应采用 “基于理解而非匹配” 的安全机制，Shell 命令安全校验是这一原则最具挑战性的应用场景。简单的关键字黑名单无法应对 Shell 的组合爆炸——命令可以通过管道、子 shell、变量展开等方式绕过任何静态规则（例如 `rm` 被禁了，攻击者可以用 `$(echo rm) -rf /` 绕过）。

> 📖 **原文** (ch06 §5.1.9)：语义解析能识别出这些嵌套的危险操作，而简单的命令黑名单无法捕获。

🧭 **归纳**：沙盒是四项工程决策而非一个开关：

| 决策项 | 做法 | 防御的是 |
|---|---|---|
| 网络出口 | 默认断网，白名单代理按需放行 | 致命三要素第 3 条 |
| 文件系统范围 | 源码只读挂载，凭证文件完全不挂载 | 数据边界 |
| 资源限额与超时 | CPU/内存/磁盘配额 + 超时，超限返回结构化错误 | 死循环、fork 炸弹、无限写盘 |
| 持久会话与隔离调和 | 按部署环境选隔离级别（进程级 → 容器 → microVM） | 执行面逃逸 |

命令安全校验要用**语义解析**：理解每个命令的参数类型和消费规则（哪些标志位会消费下一个参数），识别"看似无害的标志位实际隐藏危险载荷"这类模式——`find ... -exec rm {} \;` 通过合法参数嵌入删除，`curl -o /etc/crontab ...` 看似下载实则覆盖定时任务。

## Q5-11 Agent 到底站在谁那一边？多方委托下怎么保持忠诚？

- 章节: ch06 §5.1.9　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: 委托方忠诚与提示注入

> 📖 **原文** (ch06 §5.1.9)：前面的安全机制防的是“命令被做坏”，还有一类更微妙的安全问题——**委托方忠诚**（principal loyalty）：**Agent 到底站在谁那一边**。模型在训练时被灌输了一条朴素的默认原则——“谁在跟我说话，我就尽力帮谁”；

> 📖 **原文** (ch06 §5.1.9)：但真实的 Agent 常处在**多方委托**的处境里：它代表主人行事，打交道的却是利益相反的第三方——一个替你砍价的 Agent，对面坐着的不是“需要被帮助的用户”，而是**交涉对手**。此时“谁说话帮谁”就是危险的默认设置：对手只要开口，就可能把 Agent 策反。

> 📖 **原文** (ch06 §5.1.9)：把前沿模型放进这种处境实测，会看到一条清晰的**忠诚度光谱**，而且两端都会翻车[2](#fn2)：一端是**太老实**，把主人的私密信息（比如“我方底价是 12000”）直接抖给对手，被反复施压几轮就缴械让步；另一端是**太多疑**，连主人正当的请求也一概拒绝，反而没法完成任务。真正难的是，这两种失败是一根跷跷板——把泄密堵死往往就滑向过度拒绝，很难两全。

> 📖 **原文** (ch06 §5.1.9)：这对 Coding Agent 尤其贴切：仓库里读到的不可信内容、某个工具返回的输出、第三方 MCP 服务器发来的指令，都是试图让 Agent 倒戈的“对手”——**提示注入本质上就是一次策反**（第二、四章）。

> 📖 **原文** (ch06 §5.1.9)：因此 Harness 层要把“忠诚对象”显式钉死：主人的指令优先级最高，一切来自外部交互方的内容都默认降格为“可参考、但不具备指令效力”的数据。

> 📖 **原文** (ch06 §5.1.9)：本质上，这是在用 Harness 为模型补上一条它默认没有的立场：**对主人绝对忠诚，对外部交互方保持审慎**。

🧭 **归纳**：忠诚度光谱的两端都会翻车：

| 失败模式 | 表现 | 代价 |
|---|---|---|
| 太老实 | 把主人私密信息抖给对手，反复施压几轮就缴械 | 泄密 |
| 太多疑 | 连主人正当请求也一概拒绝 | 任务无法完成 |

两者是一根跷跷板——堵死泄密往往滑向过度拒绝。Harness 层要做的是**显式钉死忠诚对象**：主人指令优先级最高；一切来自外部交互方的内容默认降格为"可参考、但不具备指令效力"的数据。

书中的忠诚度守则要点：保护主人的私密信息乃至其"存在性"；拒绝时不逐条念出拒绝清单（那本身就在泄露）；私下的底线不等于对外的立场；只执行主人明确、具体的指令；顶住重复施压。

## Q5-12 代码作为"元能力"有哪六个方向？

| 层 | 方向 | 做什么 |
|---|---|---|
| 1 | **思维本身** | 用代码替代易错的自然语言推理（思考工具：符号计算、约束求解） |
| 2 | **业务规则** | 把模糊的政策编码为可执行约束 |
| 3 | **内容呈现** | 生成 PPT、视频与可视化产物 |
| 4 | **系统接口** | 桥接异构 API，自动适应数据格式演化 |
| 5 | **用户界面** | 动态构造表单与交互界面 |
| 6 | **Agent 自身** | 用代码创造或修复新 Agent，形成自举 |

这条"由内而外、最终回到自身"的脉络是理解代码价值的统一框架。配套的收益是：跨语言落地快（逻辑写一次，界面用 UI 框架、逻辑用脚本框架）、逻辑可版本控制并可测试。

## Q5-13 业务规则代码化：三重保障为什么缺一不可？

- 章节: ch06 §5.2.2　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: checklist与真值校验

> 📖 **原文** (ch06 §5.2.2)：Harness 的核心原则之一是“约束：编码化而非文档化”——将规则从自然语言文档转化为可执行的代码，使其成为系统行为的强制约束而非建议性指南。代码生成使 Agent 能够自主完成这个转化过程。

> 📖 **原文** (ch06 §5.2.2)：业务规则、办事流程、决策逻辑如果仅用自然语言描述，往往充满歧义。什么是“合理的退款请求”？什么算“紧急情况”？这些概念的边界在自然语言中很难界定——“购买后 7 天内可退款”看似清楚，但“7 天”是自然日还是工作日？“购买”是下单时间还是发货时间？相比之下，代码提供了无歧义的、可执行的知识表达方式——要么成功运行，要么抛出错误，不存在模棱两可。

> 📖 **原文** (ch06 §5.2.2)：**自然语言规则 vs 代码化规则：互补而非替代**

> 📖 **原文** (ch06 §5.2.2)：实践中应结合使用：系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具作为“守门员”确保合规性。

> 📖 **原文** (ch06 §5.2.2)：代码化规则的真正价值不在于优化 token 效率，而在于**防止不可逆的错误操作**——取消订单、转出资金、删除数据，这些操作一旦执行就无法撤销。代码化校验在操作前设置最后一道防线，这种安全保障的价值远超其实现成本。

> 📖 **原文** (ch06 §5.2.2)：**第一层：参数作为思考的 checklist**。工具描述中列出了完整的取消政策，并要求模型“调用前先查询订单详情、逐条核对”；可选的 `expected_*` 参数进一步促使模型把自己的判断依据显式写出来。为了填好这些参数，模型必须先调用查询工具获取订单详情，逐一确认每个条件——填写参数的过程本质上是一个**强制性 checklist**。

> 📖 **原文** (ch06 §5.2.2)：**第二层：服务端真值校验才是守门员**。注意代码中的关键设计：舱位等级、保险状态、预订时间、航段使用情况、航班状态，全部由服务端查询数据库获得；当前时间来自服务端时钟。**没有任何一条政策事实来自模型自报的参数**。

> 📖 **原文** (ch06 §5.2.2)：三重保障由此完整：(1) 系统提示词的自然语言规则帮助理解和解释；(2) 工具描述与参数设计作为 checklist，引导模型在调用前显式核对条件；(3) 服务端基于数据库真值的代码化校验作为最后守门员。前两重减少错误的发生，第三重确保错误不会变成不可逆的损失。

🧭 **归纳**：三种表达规则的分工：

| 形式 | 优势 | 适合 |
|---|---|---|
| 系统提示词中的自然语言规则 | 模型能据此向用户**解释政策**、**寻找变通方案**（如改签而非取消）、**调用前初判可行性** | 理解与沟通 |
| 代码化校验工具 | 精确无歧义、相同输入必产生相同输出、适合复杂规则组合 | 关键决策点的守门员 |

**三重保障**：① 提示词规则帮助理解；② `expected_*` 参数作为强制性 checklist 引导思考——但它只是模型的自我陈述，服务端从不把它当事实；③ 服务端基于数据库真值的代码化校验才是真正的守门员。校验逻辑放在工具内部而不是独立校验工具里，同时具备了三重保障。

**关键原则**：最后一道防线必须建立在模型无法伪造的数据之上。

## Q5-14 Agent 动态生成的界面与软件，安全边界该划在哪？

- 章节: ch06 §5.2.5　（原文：[ch06](../00-原书档案/fulltext/ch06.md)）
- 主题: A2UI Artifact模式与数据层信任

> 📖 **原文** (ch06 §5.2.5)：当 Agent 直接生成 HTML 和 JavaScript 代码作为 UI 时，存在一个根本性的安全问题：生成的代码可能包含恶意内容。例如，如果有人在输入中故意藏了一段指令，Agent 可能被提示注入操纵、不知不觉地生成一段会偷偷窃取用户数据的脚本。

> 📖 **原文** (ch06 §5.2.5)：以 A2UI（Agent-to-User Interface）为代表的声明式界面协议提供了一种更安全的方向：Agent 不直接生成可执行的代码，而是只输出一份“界面描述清单”（JSON 格式），比如“请显示一个包含 3 行 2 列的表格，标题是「销售数据」”。客户端收到这份清单后，用自己预先准备好的安全组件来渲染界面。这就像餐厅的菜单：顾客（Agent）只能点菜单上有的菜（预定义的组件），而不能走进厨房自己做（执行任意代码）。

> 📖 **原文** (ch06 §5.2.5)：这类协议的核心设计原则是**安全优先**：客户端维护一个受信任的组件目录（如 Card、Button、TextField、Table），Agent 只能请求渲染目录中已有的组件，无法注入任意代码。客户端用自己的原生组件渲染，而不是执行 Agent 生成的任意 HTML。

> 📖 **原文** (ch06 §5.2.5)：更好的方案是 **Artifact 模式**。图5-9 展示了 SQL 查询 Agent 的工作流程：Agent 不自己读数据，而是生成一段 SQL 查询代码，把这段代码作为一个独立的**可执行产物**（artifact）交给系统。系统拿着这段 SQL 直接去数据库查询，把查到的数据渲染成用户能看到的表格。整个过程中，数据从数据库直达用户界面，完全绕过了 LLM 这个“中间人”

> 📖 **原文** (ch06 §5.2.5)：因此，动态生成软件的安全目标不能是 “保证 AI 每次都把权限检查写对”，而应该是：**即使 AI 写错了代码，权限约束仍然无法被绕过**。如果权限检查本身也放在动态生成的业务逻辑中，它就与被约束的代码处在同一个信任域里。

> 📖 **原文** (ch06 §5.2.5)：更稳妥的架构是**把信任边界下移到数据层**。动态生成的应用层可以负责界面、流程和业务编排，而真正决定 “谁能对哪条数据做什么” 的规则，则由一层稳定、经过人类审查的机制强制执行。

> 📖 **原文** (ch06 §5.2.5)：把权限下沉并不意味着所有业务逻辑都要塞进数据库。应用层仍可做权限预检查，以便尽早给用户反馈；但数据层必须保留最终裁决权。

🧭 **归纳**：代码由 Agent 动态生成时，三个层面的边界设计：

| 层面 | 做法 | 拦住什么 |
|---|---|---|
| 界面 | A2UI 式声明式协议，Agent 只输出 JSON 界面描述清单，客户端用受信任组件目录渲染 | 提示注入 → 恶意脚本（成因是注入，效果类似 XSS） |
| 数据流 | Artifact 模式：Agent 只生成 SQL / 可视化代码，系统执行，数据从数据库直达用户界面，绕开 LLM 中间人 | LLM 抄写大数据出错、token 浪费 |
| 权限 | 把信任边界下移到数据层（行级安全策略、校验器、受控视图、绑定访问上下文），生成代码只能以受限身份访问 | AI 漏写权限检查、生成代码绕过已有判断 |

两条配套纪律：① Artifact 缩短了数据路径但不替代权限检查与执行隔离——执行层应用只读账号、只允许 `SELECT`、参数化绑定、可视化代码在隔离沙盒中运行；② 所有数据访问路径必须经过受信任的数据层，不能让生成代码绕过它直连数据库。
