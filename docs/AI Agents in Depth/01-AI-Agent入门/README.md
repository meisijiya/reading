# 第一章 AI Agent 入门

> 本模块是全书的概念地图：先给出 Agent = LLM + 上下文 + 工具的最小公式，再讲清 Model–Harness 的边界、ReAct 运行循环、Harness 工程的五要素与保障机制，最后落到编排模式、护栏和模型选型等工程决策。

## Q1-1 现代 Agent 的核心公式是什么？

- 章节: ch02 §1.1　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 核心公式 Agent = LLM + 上下文 + 工具，以及 Agent 与 Environment 的边界

> 📖 **原文** (ch02 §1.1)：现代 Agent 的最小工程实现可以用一个简洁的公式来表达：**Agent = LLM（大语言模型，Large Language Model）+ 上下文 + 工具**。

> 📖 **原文** (ch02 §1.1)：这里的加号表示工程组件的组合，而不是强化学习中的形式化定义；更重要的是，这个公式只描述 Agent 边界之内的实现，**不包含 Agent 与之交互的 Environment（环境）**。

> 📖 **原文** (ch02 §1.1)：换一种更直观的说法：**Agent = 大脑 + 眼睛 + 手脚**。大脑负责思考和决策，眼睛接收环境提供的观察，手脚将决策转化为作用于环境的行动。

> 📖 **原文** (ch02 §1.1)：外层是 **Agent 与 Environment 的交互关系**：环境包含文件、数据库、网页、用户、其他 Agent 以及物理或仿真世界，Agent 只能通过观察和行动接口与它交互。内层是 **Agent 的 Model–Harness 结构**：Model 负责策略决策；Harness 是 Agent 边界内环绕模型的运行与治理层，负责构造上下文、暴露工具接口、维护循环和状态，并实施权限、验证与纠正。

> 📖 **原文** (ch02 §1.1)：本节开头的工程公式可以据此重新展开：LLM 对应 Model，“上下文 + 工具”构成最小 Harness；生产系统还会在 Harness 中加入约束、验证和纠正。后文所有架构都遵循这条边界。

🧭 **归纳**：

| 直觉理解 | 实现组件 | 学术概念 | 职责边界 |
|---|---|---|---|
| **大脑** | LLM | **策略**（Policy） | 决定“下一步做什么”：理解意图、规划、判断该不该调工具 |
| **眼睛** | 上下文构造 | **观察与历史** | 把环境返回的观察与已有历史组织成当前决策所需的信息 |
| **手脚** | 工具与适配器 | **观察/行动接口** | 规定可读哪些观察、可发哪些行动、接口用什么格式 |

三条边界要点：

- 上下文只是环境在 Agent 内部的表示，**不是环境本身**；工具背后的文件系统、数据库、网页、用户或物理世界仍属于环境，不因被工具访问就成为 Agent 的一部分。
- LLM 不只是一组参数，而是 Agent 的整个决策内核：能力来自**预训练**积累的世界知识与**后训练**固化的决策策略两部分。
- 这三个组件可映射到 RL 的策略与交互接口，但不是严格一一等同：上下文不等于整个观察空间，工具定义的是接口而不是环境对象本身。

## Q1-2 为什么说扩展观察空间与动作空间是最主要的能力杠杆？

- 章节: ch02 §1.1.1 + §1.3　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 观察空间 / 动作空间与 Manus、OpenClaw 的演进

> 📖 **原文** (ch02 §1.1.1)：**观察通道与动作接口共同构成了 Agent 与外部环境之间的边界**。Harness 把环境返回的观察转换为模型能够处理的上下文，再把模型选择的行动转换为对环境的工具调用。没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。

> 📖 **原文** (ch02 §1.1.1)：**在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间**。用本书的术语说，就是扩展上下文和工具。许多看似需要“更聪明模型”的问题，其实只是接口问题：把任务所需的数据纳入上下文，或把完成任务所需的操作封装成工具，原本不可解的任务就可能变得可解。

> 📖 **原文** (ch02 §1.1.1)：Manus 的突破在于率先把三者放进同一个有广泛影响力的生产级 Agent：虚拟浏览器扩大了观察空间，文件系统、代码执行与命令行执行扩大了动作空间。它没有仅靠替换一个更强的模型来成为通用 Agent，而是取三类 Agent 观察空间与动作空间的并集，使同一个 Agent 能跨越原有产品边界完成任务。

> 📖 **原文** (ch02 §1.1.1)：OpenClaw 又把这两个空间向外推进了一层。它通过用户已经在使用的 WhatsApp、Telegram、Slack、Discord、iMessage 等消息渠道接收任务和返回结果，让 Agent 可以随时随地被触达；同时采用本地 Gateway，连接 Google Drive、Notion 等云应用以及本地文件系统。

> 📖 **原文** (ch02 §1.1.1)：值得注意的是，Manus 后来也加入了 Google Drive 连接器和桌面端本地访问，这恰好再次说明，产品能力的演进往往就是观察空间和动作空间的演进

> 📖 **原文** (ch02 §1.3)：**扩展眼睛和手脚是最主要的能力杠杆**：在模型固定时，重新定义或扩展观察空间与动作空间——也就是扩展上下文和工具——往往能直接把原本不可解的任务变为可解。Manus 和 OpenClaw 的演进都说明，通用性很大程度上来自接口边界的扩大；这种扩大必须按需进行，并配合权限控制和验证。

🧭 **归纳**：

| 产品 | 扩展了哪一侧 | 具体做法 |
|---|---|---|
| Manus | 两侧合并 | 把深度调研、代码生成、电脑操控三条路线的观察空间与动作空间取并集 |
| OpenClaw | 两侧外扩 | 消息渠道扩展触达面（观察/交互），本地 Gateway 接入云应用与本地文件系统 |

通用 Agent 产品的对照视角（眼睛 / 手脚 / 策略三维度）：Coding Agent 读需求、代码片段、目录列表、终端输出，开放式地搜索、改代码、跑命令，走“理解需求→搜索→编辑→测试→调试”的增量开发；搜索 Agent 读搜索结果、网页、论文摘要，开放式地查询、阅读、生成报告，走迭代深化；手机助手读截图与 App 状态，开放式地点击滑动输入；个人办事 Agent 读授权账户记录，开放式地打电话、发邮件、填表单。

五类产品的共同特征：**开放式的动作空间**（能生成任意自然语言和代码）、**内部思考**、**持续交互**。

➕ **补充**：按第五章的口径，“扩展接口边界”不是免费的——每扩一个入口就多一个提示注入面（见 Q2-13），每扩一个动作就多一类不可逆风险（见 Q2-17 的护栏）。因此书中的说法是“必须按需进行，并配合权限控制和验证”。

## Q1-3 工具按与外界互动的方向分哪五类？

- 章节: ch02 §1.1.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 感知 / 执行 / 协作 / 事件触发 / 用户沟通五类工具

> 📖 **原文** (ch02 §1.1.2)：工具是 Agent 与外部世界交互的桥梁：感知类工具承载环境到 Agent 的观察，执行类工具承载 Agent 到环境的行动。这里把工具作为广义接口讨论，指工具定义、调用协议和适配器，而不是把搜索引擎、文件系统、数据库或外部 API 服务本身划入 Agent。没有工具，Agent 只能“纸上谈兵”；有了工具，它才能真正读取或改变世界。

> 📖 **原文** (ch02 §1.1.2)：**感知工具**让 Agent 能访问信息：搜索引擎提供实时网络数据，文件系统读取本地文档，API 和数据库则对接外部服务和企业核心数据。

> 📖 **原文** (ch02 §1.1.2)：**执行工具**让 Agent 改变世界：代码执行、文件操作、系统命令、外部 API 调用——决策由此变成实际行动。

> 📖 **原文** (ch02 §1.1.2)：**协作工具**让 Agent 与其他 Agent 分工合作：委托子 Agent 完成专项任务，在关键决策点请求人类确认，或在多 Agent 系统中协调行动。

> 📖 **原文** (ch02 §1.1.2)：**事件触发工具**与前三类在调用方式上有本质的区别——它们不是 Agent 主动调用的，而是作为外部输入来驱动 Agent 开始执行任务。比如收到一封新邮件、到了某个预定时间点、或另一个系统发出了 Webhook 回调，这些事件会激活 Agent，让它开始后续的思考和行动。虽然事件触发不是 Agent 主动调用的，但它是 Environment 向 Agent 提供观察的通道之一，因此本书将事件适配器归入广义的工具体系；邮件、时间变化和 Webhook 的来源仍属于 Environment。

> 📖 **原文** (ch02 §1.1.2)：**用户沟通工具**是 Agent 主动与用户建立连接、传递信息的渠道。与执行工具改变外部世界不同，用户沟通工具专注于信息的传递和交互——通过文字消息、语音通话、邮件等方式，将 Agent 的执行进展或主动关怀传达给用户。

> 📖 **原文** (ch02 §1.1.2)：工具设计的质量直接决定了 Agent 能走多远——接口定义不清晰，模型就会乱用工具；错误处理不到位，工具一旦失败就会变成 Agent 的死锁；权限控制太宽泛，Agent 一旦出错，后果就难以挽回。

🧭 **归纳**：

| 类别 | 方向 | 代表场景 | 是否 Agent 主动调用 |
|---|---|---|---|
| 感知工具 | 环境 → Agent | 搜索、读文件、API / 数据库查询 | 是 |
| 执行工具 | Agent → 环境 | 代码执行、文件操作、系统命令、外部 API | 是 |
| 协作工具 | Agent ↔ Agent / 人 | 委托子 Agent、请求人类确认、多 Agent 协调 | 是 |
| 事件触发工具 | Environment → Agent | 新邮件、定时点、Webhook 回调 | 否（作为外部输入驱动启动） |
| 用户沟通工具 | Agent → 用户 | 文字消息、语音通话、邮件 | 是 |

三类工具设计缺陷对应的后果：接口不清晰→乱用工具；错误处理不到位→死锁；权限过宽→出错不可挽回。MCP（Model Context Protocol）的推广正是在让工具接入变得更容易。

## Q1-4 工具调用的四步流程是什么，通用工具与专用工具如何取舍？

- 章节: ch02 §1.1.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 工具调用四步流程 + 通用性 vs 约束性

> 📖 **原文** (ch02 §1.1.2)：**工具调用**（Tool Calling，也称 Function Calling）是现代 LLM Agent 的一项核心能力，它让模型能够通过结构化的方式调用外部工具。这种能力将 LLM 从一个纯粹的文本生成器转变为能够执行实际操作的智能系统。

> 📖 **原文** (ch02 §1.1.2)：工具调用的流程分为四步：首先，在上下文里告诉模型有哪些工具可用（包括名称、用途和参数）；然后，模型自主判断要不要调用工具、调用哪个、传什么参数；接着，工具执行完毕后，结果被追加到上下文中；最后，模型据此决定下一步行动。这个循环就是后文要介绍的 ReAct 的基础。

> 📖 **原文** (ch02 §1.1.2)：在为 Agent 设计工具时，可以先从任务所需的最窄能力起步，再随任务复杂度提升逐步扩展。如果任务只是做四则运算，一个参数清晰的计算器就足够了；当任务升级为读取表格、清洗缺失值、计算统计量并绘图时，受限的 Python 代码解释器就比不断叠加专用工具更容易组合和探索。但通用性也扩大了出错和攻击面：代码必须在隔离沙盒中运行，默认不能访问网络，也不能读取授权工作目录以外的文件，并对执行时间、CPU、内存和输出大小设置上限。

> 📖 **原文** (ch02 §1.1.2)：同样，单一日志工具适合记录一段执行过程；对于需要数小时甚至数天的长程任务，受控的虚拟工作目录则可以同时保存计划、中间结果、运行日志和最终产物，让 Agent 能在多次执行之间接续工作。这个目录也应限定可读写的路径、容量和文件类型，并防止路径越界，而不是把宿主文件系统全部暴露给 Agent。

> 📖 **原文** (ch02 §1.1.2)：通用工具并不总是优于专用工具。支付、删除数据、发送邮件和生产部署等高风险或强业务约束操作，仍应封装为参数明确、权限受限且全程可审计的专用工具，必要时再加上预览和人工确认。因此，工具设计的核心原则是：**通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作**。

🧭 **归纳**：

四步流程（以查天气为例）：

| 步骤 | 发生方 | 内容 |
|---|---|---|
| 第一步 | 框架 → 模型 | 在上下文里声明可用工具（名称、用途、参数） |
| 第二步 | 模型 | 自主判断要不要调、调哪个、传什么参数 |
| 第三步 | 框架 | 执行工具，把结果追加到上下文 |
| 第四步 | 模型 | 基于结果决定下一步（收敛或继续） |

开发者只负责“定义工具 + 执行调用”，模型自主完成“要不要调、调哪个、传什么参数”。这个循环即 ReAct 的雏形。

取舍判据：能力窄→参数清晰的专用工具；任务可组合探索→受限的通用工具（但必须沙盒、断网、限定路径、配额封顶）；长程任务→受控虚拟工作目录承接计划、中间结果与产物；高风险 / 强业务规则 → 参数明确、权限受限、全程可审计的专用工具 + 预览 + 人工确认。

## Q1-5 “模型即 Agent”会不会让 Harness 最终被模型吃掉？

- 章节: ch02 §1.1.3.1　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: Model as Agent 与苦涩的教训

> 📖 **原文** (ch02 §1.1.3.1)：“模型即 Agent”（Model as Agent）这一新范式代表了 AI Agent 发展的最新方向。先进模型通过后训练（特别是强化学习）将工具调用能力内化为原生能力：何时调用工具、调哪个、传什么参数，都由模型自己决定，无需人工编排。但这并不意味着框架层变得不重要了。恰恰相反，模型越强大，围绕模型构建的 Harness 就越关键。

> 📖 **原文** (ch02 §1.1.3.1)：Harness 这个词原指马具，即套在马身上的缰绳与挽具，不是为了限制马的奔跑能力，而是把这种力量引导到正确的方向上。换到 Agent 语境里，模型是那匹强大但不可预测的马，Harness 则是把它的能力引导成可靠任务执行的工程外壳。

> 📖 **原文** (ch02 §1.1.3.1)：模型自主决策的空间越大，出错时的影响面也越大，因此需要更精细的约束、验证和纠正机制来确保可靠性。模型厂商的真正优势不是 “让框架变薄”，而是能对模型与外围 Harness 进行协同优化，持续迭代。

> 📖 **原文** (ch02 §1.1.3.1)：以此衡量，Harness 里的约束、验证与纠正，有多少属于“人的先验”，注定会被模型内化？本书的立场是：**方向认同，节奏务实**。方向上，本书不怀疑模型会持续吃掉 Harness——工具调用、长程规划都曾靠外部编排，如今已是模型的原生能力；但在节奏上，这个“吃”远比直觉慢：训练以月计，模型也无法一次内化真实业务中所有的约束与偏好，模型此刻的能力边界，就是 Harness 此刻的价值所在。因此 Harness 工程不是对苦涩的教训的抵抗，而是这一教训在工程时间尺度上的实践：模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新的能力前沿。

🧭 **归纳**：

| 立场 | 含义 |
|---|---|
| 方向认同 | 模型会持续吃掉 Harness（工具调用、长程规划已从外部编排变为原生能力） |
| 节奏务实 | 训练以月计，业务约束无法一次内化；模型此刻的能力边界就是 Harness 此刻的价值所在 |
| 工程落法 | 模型做不稳的 Harness 先补；模型内化一层，Harness 卸下一层并兜底新的能力前沿 |

➕ **补充**：Rich Sutton 的《苦涩的教训》原意是通用方法靠规模取胜，人为编码的领域先验长期会输；本章的立场不是反驳这条规律，而是把它放到工程时间尺度上——Harness 是“这一轮模型还没内化完”的临时补丁集合。

## Q1-6 Agent 的学习机制有哪三条路径？

- 章节: ch02 §1.1.3.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 上下文适应 / 外部产物 / 参数更新

> 📖 **原文** (ch02 §1.1.3.2)：前面讨论了模型可以通过强化学习将工具调用策略内化为原生能力。但 Agent 的行为改变不只发生在训练阶段。按照更新发生的位置和持续时间，可以把它理解为三条互补路径（图1-2）：任务内的上下文适应、跨任务的外部产物（artifact）更新，以及训练周期中的参数更新。

> 📖 **原文** (ch02 §1.1.3.2)：**上下文适应**发生在当前任务中。示例、状态和检索结果进入上下文后，模型可以立即调整行为，却不会因此改变下一次会话的持久状态。它的优势是快速、低成本，局限是受上下文窗口和信息组织方式约束

> 📖 **原文** (ch02 §1.1.3.2)：要让变化跨越任务保留下来，可以更新**外部产物**：把事实和经验整理为知识文档，把可语言化的策略写进 Prompt 或 Skill，把确定性流程与约束写成程序和 Harness。这些产物可审计、可修订，执行时仍需通过上下文或工具接口被 Agent 使用。

> 📖 **原文** (ch02 §1.1.3.2)：当目标是医疗影像理解、自然语言风格或隐式决策策略等高维能力时，外部规则难以完整表达，就需要通过后训练更新**模型参数**。参数更新的部署成本较高，却能形成自然、广泛的泛化能力

> 📖 **原文** (ch02 §1.1.3.2)：三条路径因此不是互斥分类，而是不同时间尺度上的协同机制：上下文负责临场适应，外部产物负责可控积累，参数负责内化难以显式表达的能力。

🧭 **归纳**：

| 路径 | 发生位置 / 时间尺度 | 典型载体 | 优势 | 局限 |
|---|---|---|---|---|
| 上下文适应 | 当前任务内 | 示例、状态、检索结果 | 快速、低成本、立即生效 | 受上下文窗口与信息组织方式约束，不跨会话 |
| 外部产物 | 跨任务 | 知识文档、Prompt / Skill、程序与 Harness | 可审计、可修订、可回滚 | 执行时仍需上下文或工具接口才能被用上；难表达高维隐式能力 |
| 参数更新 | 训练周期 | 后训练参数 | 泛化自然、广泛 | 部署成本高 |

选型判据：能在上下文里说清、且只需当前任务生效 → 走上下文；要跨任务保留、需要可审计可修订 → 走外部产物；属于难以显式表达的高维能力（影像理解、语言风格、隐式决策策略）→ 走参数。

## Q1-7 上下文由哪五个部分组成？消融实验说明了什么？

- 章节: ch02 §1.1.4 + 实验 1-1　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 上下文的五个组成部分与消融实验结论

> 📖 **原文** (ch02 §1.1.4)：**系统提示词**（System Prompt）：与用户每次输入的提示词不同，系统提示词由开发者编写，在整个对话过程中保持不变，相当于 Agent 的“岗位说明书”——定义它的身份、权限和行为准则。

> 📖 **原文** (ch02 §1.1.4)：**工具定义**（Tool Definitions）：声明 Agent 可用工具的名称、功能描述和参数格式。没有工具定义，Agent 就无法识别和调用任何工具——消融实验（实验 1-1）将验证这一点。工具定义与系统提示词一起构成对话中保持不变的**静态前缀**（这是基础模式；2026 年以来，生产框架中工具的完整 schema 也可以按需动态加载到上下文末尾而不破坏前缀，详见第二章工具定义一节和第四章）。

> 📖 **原文** (ch02 §1.1.4)：**模型回复**（Assistant Messages）：模型之前生成的回复，最多包含三个部分——思考过程（`reasoning`，即内部思考链，保持思维连贯性和决策可解释性）、文本内容（`content`，即对用户的回复）和工具调用请求（`tool_calls`，即 Agent 采取行动的方式）。在一次具体的回复中，三者不一定同时出现：例如 Agent 决定调用工具时通常只有 `reasoning` + `tool_calls`，给出最终回答时通常只有 `reasoning` + `content`。

> 📖 **原文** (ch02 §1.1.4)：**工具执行结果**（Tool Results）：Agent 框架执行工具后返回的结果。这些结果是 Agent 下一步思考的直接依据，也让它能够从执行结果中学习、避免重复犯错。

> 📖 **原文** (ch02 §1.1.4)：前两项（系统提示词 + 工具定义）是静态前缀，后三项（用户消息 + 模型回复 + 工具执行结果）是随交互不断增长的动态消息历史。这五个部分共同构成了 LLM 每次推理时的上下文。

> 📖 **原文** (ch02 §1.1.4 + 实验 1-1)：实验结果揭示了每个上下文组件不可替代的作用。**工具定义**（Tool Definitions，静态前缀的一部分）是 Agent 行动能力的基础，没有它，Agent 就无法识别和调用任何工具。**工具执行结果**（Tool Results）是闭环控制的关键，缺失它会导致 Agent “盲目”执行，陷入无限循环。**思考过程**（模型回复中的 reasoning 部分）保留了 Agent 做出之前决策的原因，使思维流程更加连贯，避免做出前后矛盾的决策。**历史消息**（之前轮次的用户消息、模型回复和工具执行结果）则防止了冗余操作，保持任务执行的连贯性，避免重复犯同样的错误。

> 📖 **原文** (ch02 §1.1.4 + 实验 1-1)：这个实验的核心洞察是：**上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策**。

🧭 **归纳**：

| # | 组成部分 | 归属 | 作用 | 缺失后果（消融实验） |
|---|---|---|---|---|
| 1 | 系统提示词 | 静态前缀 | 身份、权限、行为准则、用户记忆、环境状态 | 不参与消融——没有角色认知，测试无意义 |
| 2 | 工具定义 | 静态前缀 | 工具名称、功能描述、参数格式 | 完全丧失行动能力，无法识别和调用任何工具 |
| 3 | 用户消息 | 动态历史 | 用户输入，可能含 RAG 引入的外部知识 | — |
| 4 | 模型回复 | 动态历史 | reasoning / content / tool_calls | 剥离思考过程 → 前后决策互相矛盾 |
| 5 | 工具执行结果 | 动态历史 | 下一步思考的直接依据 | 看不到上一步反馈 → 反复调用同一工具、陷入无限循环 |

实验设计：一组保留全部组件的完整基线 + 四组各缺失一个组件。历史消息缺失同样致命——Agent 等于失忆，会从头开始整个任务流程，重复执行已完成的步骤。

## Q1-8 ReAct 循环是什么？Agent 上下文为什么等于“静态前缀 + 轨迹”？

- 章节: ch02 §1.1.5　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: ReAct 三环节循环与轨迹（trajectory）结构

> 📖 **原文** (ch02 §1.1.5)：Agent 执行任务的核心模式叫做 **ReAct**（Reasoning + Acting）。虽然名字只体现了思考（Reasoning）和行动（Acting）两个词，但实际循环包含三个环节：模型先**思考**当前应该做什么，然后调用工具**行动**，再**观察**工具返回的结果并继续思考下一步。这个“想→做→看→想→做→看”的循环不断重复，直到任务完成。

> 📖 **原文** (ch02 §1.1.5)：让我们通过一个多币种收入汇总的具体例子来理解 Agent 的**轨迹**（trajectory）。轨迹是 Agent 在执行任务过程中不断积累的消息历史——用户消息、模型回复（包括思考过程和工具调用）、工具执行结果。每一次调用 LLM 时，它接收的完整上下文由**静态前缀**（系统提示词 + 工具定义）和**轨迹**（动态消息历史）两部分组成（图 1-4）。这揭示了一个关键事实：**Agent 的上下文 = 静态前缀 + 轨迹**。

> 📖 **原文** (ch02 §1.1.5)：在我们的实验中，这个循环展现得淋漓尽致。第一轮，Agent 分析任务后并行调用三个货币转换工具；第二轮，基于转换结果调用代码解释器进行复杂计算；第三轮，确认所有计算完成后生成最终答案。整个过程仅用了 3 次迭代、4 次工具调用就完成了复杂的多步骤任务。

> 📖 **原文** (ch02 §1.1.5)：在这种最基本的设计中，大模型看到的上下文是不断追加的。每次 LLM 调用都能看到完整的轨迹，这让它能够理解当前处于任务的哪个阶段、之前尝试了什么、得到了什么结果。

> 📖 **原文** (ch02 §1.1.5)：轨迹不仅是执行的记录，更是 Agent 能力的体现。通过分析大量的轨迹，我们可以发现 Agent 的行为模式、优化决策路径、改进工具设计。轨迹数据甚至可以总结到知识库中，或者通过强化学习来训练更好的 Agent 模型，实现从经验中学习的闭环优化。

🧭 **归纳**：

多币种汇总任务的轨迹演化（3 次迭代 / 4 次工具调用）：

| 轮次 | 模型 reasoning | 模型动作 | 工具结果 |
|---|---|---|---|
| 1 | 需要把所有货币转换为 USD | 并行调用 3 次 `convert_currency`（EUR / GBP / JPY） | 三条换算结果 |
| 2 | 已获得转换结果，现在需要汇总计算 | 调用 `code_interpreter` | 总收入 $9,602,895.73 等 |
| 3 | 所有计算完成，总结结果 | 无工具调用，输出 FINAL ANSWER | — |

三点结构性认知：轨迹里看不到系统提示词和工具定义，因为它们作为静态前缀每次被自动拼接在轨迹前面；轨迹的结构化特性（用户消息 / 模型回复 / 工具结果清晰分区）同时带来可解释性与可调试性；轨迹本身是训练与优化的数据源。

## Q1-9 强化学习内化的是决策能力，还是工具执行本身？

- 章节: ch02 §1.1.5 + 实验 1-2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: Kimi K3 原生 Agent 能力与决策 / 执行的归属

> 📖 **原文** (ch02 §1.1.5 + 实验 1-2)：Kimi K3 是一个约 2.8 万亿参数的混合专家（MoE, Mixture of Experts）模型——可以把 MoE 想象成一个专家团队：面对不同类型的问题，系统会自动选择最合适的几位专家来作答，而不需要所有专家同时上阵，这样既保证了能力又提高了效率。它拥有 100 万 token 的上下文窗口、原生的视觉理解能力，以及始终开启的“思考模式”（thinking mode）；模型通过强化学习训练，将工具调用的**决策策略**内化为原生能力——何时调用工具、调用哪个、传什么参数都由模型自主决定，从而能够自主完成网络搜索等任务。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-2)：需要说明的是，被内化的是“何时调用、如何调用”的决策，而 `web_search`、`code_runner` 等工具本身仍作为 API 层面的内置工具在服务端执行（Kimi 通过名为 Formula 的服务端脚本引擎运行这些官方工具）。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-2)：关键观察包括：模型自己决定何时搜索、搜索什么，展现了真正的自主性；它能根据搜索结果动态调整策略，自主判断信息是否充足。这里需要厘清一个常见的误解，关键在于分清两件事的归属。**强化学习赋予模型的是决策能力**——何时该调用工具、调用哪个、传入什么参数、拿到结果后是否继续、如何把几十上百次调用串联成连贯的推理，这些“用不用、怎么用”的判断被写进了模型参数。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-2)：**而工具本身及其执行则由 Agent 框架（或 API 内置工具）提供**——`web_search`、`code_runner` 的真实实现、代码沙盒环境、调用的发起与结果回传，都在模型之外的基础设施里完成。RL 优化的是决策策略，而不是把搜索引擎或代码沙盒“装进”模型的权重。因此编排循环并没有消失，而是从客户端移到了服务端，同时决策权交给了模型

> 📖 **原文** (ch02 §1.1.5 + 实验 1-2)：Kimi K3 在 Agent 任务中的一个突出优势是**长链工具调用的稳定性**——它能够连续执行 200～300 次工具调用而保持思考的一致性，远超多数模型在数十次调用后就开始退化的表现。

🧭 **归纳**：

| 归属 | 内容 | 是否被 RL 内化 |
|---|---|---|
| 模型参数 | 何时调、调哪个、传什么参数、拿到结果是否继续、如何把上百次调用串成连贯推理 | 是 |
| 模型之外的基础设施 | `web_search` / `code_runner` 的真实实现、代码沙盒、调用发起与结果回传 | 否（仍由框架或 API 内置工具提供） |

结论一句话：编排循环没有消失，而是从客户端移到服务端，决策权交给模型。因此判断一个 Agent 产品能力时，必须分别看“决策质量”与“托管工具的丰富度”，不能把后者记到模型账上。

## Q1-10 自由格式工具调用和意图澄清带来了什么变化？

- 章节: ch02 §1.1.5 + 实验 1-3　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: GPT-5.6 原生 Deep Research 能力

> 📖 **原文** (ch02 §1.1.5 + 实验 1-3)：GPT-5.6 一个便利的特性是**自由格式工具调用**（Freeform Tool Calling）。传统方式中，模型调用工具时必须把所有参数打包成严格的 JSON 格式（一种结构化的数据格式），这就像填表格一样有很多格式限制。自由格式工具调用（在 API 中通过 `type: "custom"` 的工具类型声明）允许模型直接向工具发送原始文本（比如一段 Python 代码、一条 SQL 查询），省去了 JSON 转义的麻烦。要说明的是，这是 API 参数格式的演进，而非模型架构的革新——客户端的工具调用循环（检测 `tool_calls` → 执行 → 回传结果）逻辑保持不变，改变的只是参数从 JSON 字符串变成了原始文本。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-3)：GPT-5.6 配合 Responses API 的**网络搜索和代码解释器**内置工具——这正是 Deep Research 的核心：模型能够自主搜索网络获取实时信息，并编写代码进行深度分析，实现“搜索 -> 阅读 -> 分析 -> 再搜索”的迭代研究过程。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-3)：更重要的是，GPT-5.6 将 **OpenAI Deep Research** 产品的设计理念内化到了模型层面，引入了**意图澄清过程**。当用户提出研究需求后，GPT-5.6 不会立即动手执行，而是首先通过一系列问题来澄清用户的真实意图。以“搜索最近一个月的比特币走势，做技术分析”为例，它会先问：“您偏好使用哪个数据源？需要分析哪些技术指标？”通过这种交互式的意图澄清，GPT-5.6 能够生成更精准、更符合用户需求的研究报告。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-3)：这让“用户说了什么”和“用户真正想要什么”之间的差距，在任务执行之前就得到了弥合。

> 📖 **原文** (ch02 §1.1.5 + 实验 1-3)：需要说明的是，这个实验并不绑定某一家厂商。没有 OpenAI 额度的读者完全可以用具备等价托管工具的提供商复现：例如阿里云百炼 qwen3.7-plus 的 Responses API 同样内置 `web_search` 与 `code_interpreter`；Kimi K3 的 Formula 托管搜索与 `code_runner` 也属于同类能力。

🧭 **归纳**：

两项能力要分清性质：

| 变化 | 性质 | 客户端是否需要改 |
|---|---|---|
| 自由格式工具调用 | API 参数格式演进（非模型架构革新），参数从 JSON 字符串变成原始文本 | 不改，工具调用循环逻辑保持不变 |
| 意图澄清过程 | 把 Deep Research 的产品设计内化到模型层 | 不改，但任务在执行前多一轮交互 |

➕ **补充**：意图澄清本质上是把第一章说的“用户说的往往不是他真正想要的”这一判断前置到执行之前，属于成本换准确率的一类权衡——在长程、高信息不对称的任务里通常划算，在用户意图已经明确的短任务里反而是多余的一轮往返。

## Q1-11 Harness 工程的方程与五要素是什么？

- 章节: ch02 §1.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: Agent = Model + Harness；上下文管理 + 工具接口 + 约束 + 验证 + 纠正

> 📖 **原文** (ch02 §1.2)：把 LLM 抽象为核心组件 Model，把 Agent 边界内负责支撑模型运行、并中介模型与环境交互的代码、配置和服务统称为 Harness。两个视角并非替代关系，而是不同抽象层次上对同一 Agent 实现的描述。之所以换用更通用的 “Model” 一词，是因为 Harness 工程的原则适用于任何具备推理和工具调用能力的模型，不限于某种特定模型类型。Harness 的核心是原公式中的“上下文管理 + 工具接口”，再加上三层保障机制：**约束**（限定 Agent 能做什么、不能做什么）、**验证**（检查 Agent 做得对不对）和**纠正**（做错了怎么补救）。

> 📖 **原文** (ch02 §1.2)：**Agent = Model + Harness**

> 📖 **原文** (ch02 §1.2)：**Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**

> 📖 **原文** (ch02 §1.2)：**Harness 不是模型之外的一切**，而是 **Agent 边界内、模型之外**的运行与治理层。它负责中介 Model 与 Environment 的交互，但不包含被交互的环境本身：工具定义、调用适配器、沙箱的权限与重置机制属于 Harness；沙箱内随行动变化的文件和进程、外部数据库、网页、用户及物理世界属于 Environment。物理部署位置也不能决定概念归属——即使仿真环境与 Agent 运行在同一进程中，它仍然是 Environment。

> 📖 **原文** (ch02 §1.2)：举个例子帮助理解：上下文中嵌入退款政策是“上下文管理”的范畴，而校验退款金额不超过订单金额则属于“约束”；`process_refund` 的工具定义、调用适配器和权限检查属于 Harness，而订单服务及其数据库状态属于 Environment；API 超时后自动重试则属于“纠正”。

> 📖 **原文** (ch02 §1.2)：以 Claude Code 为例，它的 Harness 中绝大部分代码都是约束、验证与纠正，而非上下文与工具——工具本身（文件读写、命令执行、搜索）只是一小部分，而围绕这些工具构建的保障机制才是真正的核心。这些机制包括：

🧭 **归纳**：

| 功能 | 一句话职责 | 与上下文/工具的关系 |
|---|---|---|
| **Context（上下文）** | 为模型提供感知信息 | 核心能力 |
| **Tools（工具接口）** | 为模型提供观察与行动手段 | 核心能力 |
| **Constrain（约束）** | 设定行为边界——能做什么、不能做什么 | 围绕上下文和工具构建的安全边界 |
| **Verify（验证）** | 自动判断操作结果的对错 | 围绕工具执行结果构建的检查机制 |
| **Correct（纠正）** | 发现问题时自动修正或回退 | 围绕工具调用失败构建的恢复机制 |

退款的对照例子（同一个模型，结果天壤有别）：

- 没有 Harness：看不到退款政策（缺上下文）、不知道调哪个 API（缺工具）、直接编造退款结果（缺验证）、用户发现退款没发生（缺纠正）。
- 有了 Harness：系统提示词写明 7 天退款政策（上下文）、调用 `query_order` 与 `process_refund`（工具）、校验退款金额不超过订单金额（约束）、校验数据库状态确认成功（验证）、API 超时自动重试（纠正）。

成熟度曲线的关键判断：早期框架关注上下文与工具，让 Agent “能做事”；生产级系统的重心已经转向约束、验证与纠正，确保工具调用安全、上下文经过管理、错误可恢复。Claude Code 的五类机制：流程状态管理、多层上下文压缩、权限分类、熔断器（错误连续发生就自动“断电”，如同保险丝跳闸）、错误恢复机制（捕获异常、回滚到上一稳定状态、重试或交还人类）。

## Q1-12 从提示工程到 Graph 工程有几波演进？Harness 五功能各有什么核心原则？

- 章节: ch02 §1.2.1 + §1.2.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 工程范式演进弧线 + 五功能设计原则

> 📖 **原文** (ch02 §1.2.1)：**提示工程**（Prompt Engineering）是第一波创新——通过优化输入给模型的自然语言指令来提升输出质量。

> 📖 **原文** (ch02 §1.2.1)：**上下文工程**（Context Engineering）是第二波——人们认识到单纯优化提示词还不够，需要系统性地管理模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）。

> 📖 **原文** (ch02 §1.2.1)：**Harness 工程**是第三波——它将视野从“模型能看到什么”进一步扩展到“Agent 如何组织模型运行并与环境交互”，涵盖上下文与工具接口、约束机制、验证手段、反馈循环和错误恢复等 Agent 边界内、模型之外的运行与治理机制。

> 📖 **原文** (ch02 §1.2.1)：随后出现的 **Loop 工程**（Loop Engineering）又把视野从单次运行扩展到跨轮次的持续自主运转：谁来发现下一件该做的事、何时验证、何时才算真正完成（第十章将结合多 Agent 协作系统展开）。

> 📖 **原文** (ch02 §1.2.1)：2026 年 7 月，业界又开始用 **Graph 工程**（Graph Engineering）描述一种更高层的编排视角：把 Agent 循环、确定性程序和人工审批组织成显式的执行图，其中节点承担具体能力，边规定路由与依赖，结构化状态沿边传递并在关键边界处持久化

> 📖 **原文** (ch02 §1.2.1)：这五个阶段不是替代关系，而是层层包含的：提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集。每一层都在前一层的基础上扩展了工程师的关注范围和影响力。**当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践**。

> 📖 **原文** (ch02 §1.2.2)：五个功能构成一个闭环：上下文与工具支撑决策，约束预防错误，验证发现偏差，纠正闭合循环。缺少任何一个环节，系统都会出现可靠性缺口。

🧭 **归纳**：

| 波次 | 关注范围 | 核心问题 |
|---|---|---|
| 提示工程 | 单次调用的输入指令 | 怎么把话说清楚 |
| 上下文工程 | 模型能看到的所有信息 | 看到什么、以什么结构看到 |
| Harness 工程 | 模型运行与环境的交互治理 | 怎么安全、可靠地跑 |
| Loop 工程 | 跨轮次的持续自主运转 | 谁来决定下一步、何时算完成 |
| Graph 工程 | 显式执行图 | 节点能力、边路由、状态持久化 |

Harness 五功能的核心原则：

| 功能 | 核心原则 | 实际例子 |
|---|---|---|
| 上下文 | 信息充分性：让 Agent 在每个决策点都基于足够的信息判断 | 系统提示词、知识库、Agent 状态栏、Sidecar 旁路查询 |
| 工具 | 接口清晰：工具命名直观、参数有例子、边界有说明 | MCP 工具、代码解释器、搜索工具 |
| 约束 | 故障安全默认值：所有能力默认关闭，必须显式开放（类似手机 App 权限管理） | Claude Code 中每个工具默认需要用户授权才能执行 |
| 验证 | 输入隔离：安全检查只看结构化数据（如工具返回的 JSON 字段），而不是模型自由生成的文本 | Linter 检查、类型系统、工具调用结果校验 |
| 纠正 | 在确认无法恢复之前，不暴露中间态 | 静默重试、接续生成、连续失败时回退到人工判断（熔断机制） |

➕ **补充**：验证原则里的“输入隔离”带攻击面理由——书中第二章指出攻击者可能通过提示注入操纵模型输出，因此安全检查不能读模型的自由文本。

## Q1-13 构建 Agent 的三个核心原则是什么？模型该怎么选？

- 章节: ch02 §1.2.3 + §1.2.4　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 简单 / 透明 / ACI 原则 + 模型选型维度与策略边界

> 📖 **原文** (ch02 §1.2.3)：根据 Anthropic 的经验，成功的 Agent 系统遵循三个核心原则。

> 📖 **原文** (ch02 §1.2.3)：**保持简单**。从最简单的方案开始，只在确实必要时才增加复杂度。直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象。因为每多一层抽象都会成为以后调试时新的盲区。

> 📖 **原文** (ch02 §1.2.3)：**保持透明**。明确显示 Agent 的规划步骤、执行日志和决策轨迹——这不只是为了调试方便，也是让用户建立信任的前提。因为黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。

> 📖 **原文** (ch02 §1.2.3)：这种“用设计消除错误”的思路，在制造业里有一个专门的术语，叫**防呆**（Poka-yoke），源自丰田生产体系。设计不好的工具会让再强的模型也频繁出错——因为模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性的错误。

> 📖 **原文** (ch02 §1.2.4)：选模型时不要只看排行榜，**要在你自己的任务上做评估**（见第六章）。

> 📖 **原文** (ch02 §1.2.4)：**能力之外，还要考虑模型的策略边界。** 模型在基准测试中具备某种能力，并不意味着承载它的产品一定允许用户调用这种能力。不同厂商会对网络安全、模型蒸馏、模型提取、隐私数据和高风险操作设置不同的策略边界；同一个任务在聊天产品、Coding Agent 和 API 中也可能得到不同结果。

> 📖 **原文** (ch02 §1.2.4)：**绝大多数 Agent 需要支持思考（Reasoning）的模型。** Agent 需要进行多步思考、工具选择等复杂决策，不带思考能力的模型在这些任务上表现往往很差。只有极少数场景例外，比如只执行单步简单任务、或 Computer Use 中仅需点击固定位置的简单 GUI 操作，此时不带思考的模型也能胜任。

> 📖 **原文** (ch02 §1.2.4)：一是**输出 token 的速度**：Agent 往往需要多轮推理，每轮都要等待模型输出完成才能执行下一步，所以输出速度直接决定了端到端的响应延迟——如果一个 Agent 任务需要 20 轮推理，每轮慢 2 秒就意味着总共多等 40 秒。

🧭 **归纳**：

三个核心原则：

| 原则 | 含义 | 反面 |
|---|---|---|
| 保持简单 | 从最简单方案起步，直接 API 调用优于复杂框架 | 每多一层抽象就多一个调试盲区 |
| 保持透明 | 展示规划步骤、执行日志、决策轨迹 | 黑箱错误既无法定位也无法纠正，用户也无法建立信任 |
| 设计好工具接口（ACI） | 从 Agent 视角而非程序员视角设计接口；容易误用处用防呆设计让错误无法发生 | 模型与工具之间唯一的沟通通道就是接口，模糊接口会被模型放大成系统性错误 |

ACI 的防呆参照：SIM 卡的缺角让卡片只能从一个方向插进卡槽；微波炉门没关好就绝不加热。

模型选型维度：

| 维度 | 判据 |
|---|---|
| 能力与成本 | 闭源通常领先但贵；开源与闭源差距在 6 个月以内而成本显著更低，适合成本敏感或数据合规场景 |
| 策略边界 | 基准能力 ≠ 产品允许；同一任务在聊天产品 / Coding Agent / API 中结果可能不同；服务条款是否允许 |
| 思考能力 | 绝大多数 Agent 必须选支持 Reasoning 的模型；例外仅限单步简单任务、固定位置 GUI 点击 |
| 输出速度 | 直接决定端到端延迟，20 轮 × 每轮慢 2 秒 = 多等 40 秒 |
| 多模态 | 需要理解图片 / 音频 / 视频时就是硬性要求 |
| 落地兜底 | 业务关键任务应提前准备人工接管或其他合规模型作为替代路径 |

## Q1-14 工作流与自主 Agent 怎么选？护栏与人工干预怎么落地？

- 章节: ch02 §1.2.5 + §1.2.6 + §1.2.6.2　（原文：[ch02](../00-原书档案/fulltext/ch02.md)）
- 主题: 编排模式选择与混合、护栏分层、人工干预触发条件

> 📖 **原文** (ch02 §1.2.5)：在构建 LLM 应用时，应遵循“从简单到复杂”的原则：首先考虑单个 LLM 调用——如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统；当需要多步骤处理时，对于可以清晰分解为固定子任务的场景，考虑使用工作流；只有当需要动态决策和灵活的执行路径时，才使用自主 Agent。需要记住的是：Agent 系统通常会用延迟和成本换取更好的任务性能，应该谨慎权衡这种交换是否值得。

> 📖 **原文** (ch02 §1.2.5)：工作流模式有两个核心优势。第一是**严格的流程控制**：开发者可以确保关键步骤不被跳过或乱序执行，例如“付款前不能预订”这类业务规则通过代码强制执行，不依赖 LLM 的判断。第二是**安全性**：由于执行路径是确定的，提示注入或模型犯错最多只能影响当前节点内部的处理，无法让 Agent 跳到不该执行的分支——攻击面被限制在单个节点内。

> 📖 **原文** (ch02 §1.2.5)：工作流的主要局限是**缺乏变通性**。当出现预设流程未覆盖的情况时（例如用户在付款环节临时想改签、或航班突然取消需要推荐替代方案），固定的节点路径无法灵活应对，只能走预设的异常处理分支或将控制权交还给人类。

> 📖 **原文** (ch02 §1.2.5)：这意味着自主 Agent 需要具备自主规划的能力——自主决定执行步骤，还需要能识别失败、调整策略，而不只是在出错时停下来。但自主性不等于无限制——必须设计明确的**停止条件**（任务完成、达到最大迭代次数或遭遇不可恢复的错误），否则 Agent 容易陷入死循环或过度执行。

> 📖 **原文** (ch02 §1.2.5)：实践中，工作流和自主 Agent 并非非此即彼——很多系统会混合使用两种模式：关键的、有严格合规要求的流程用工作流来确保可靠性，需要灵活决策的部分切换到自主模式。

> 📖 **原文** (ch02 §1.2.6)：可以将护栏理解为分层防御机制。单个护栏不太可能提供足够的保护，但将多个专门的护栏组合使用，就能构建出更有韧性的 Agent 系统。

> 📖 **原文** (ch02 §1.2.6)：护栏也存在另一类失败：**误拒绝**。为了降低危险请求被放行的概率，模型可能同时拒绝一部分合法但形式敏感的任务，例如经过授权的安全测试、模型蒸馏研究。因此，护栏评估不能只测试“应当拒绝的请求是否被拦截”，还要测试“明确允许的请求是否能够正常完成”。

> 📖 **原文** (ch02 §1.2.6)：按防护位置可以分为三类：输入侧、执行侧和输出侧。

> 📖 **原文** (ch02 §1.2.6.2)：通常有两种主要情况会触发人工干预：**超过失败阈值** 为 Agent 的重试次数或操作次数设置上限。如果 Agent 超过了这些限制，就应该升级到人工干预。**高风险操作** 涉及敏感、不可逆或高风险的操作时，应触发人工监督，至少在团队对 Agent 可靠性建立起足够信心之前是如此。典型的例子包括授权大额退款或付款等。

🧭 **归纳**：

编排模式对照：

| 维度 | 工作流（Workflow） | 自主 Agent |
|---|---|---|
| 路径来源 | 开发者预先设计，代码写死 | Agent 依据环境反馈实时决定 |
| 控制 | 关键步骤不被跳过或乱序，业务规则由代码强制 | 需明确停止条件，否则死循环或过度执行 |
| 安全 | 攻击面被限制在单个节点内 | 更高成本与复合错误风险，需沙盒测试、护栏、监控 |
| 局限 | 缺乏变通性，只能走异常分支或交还人类 | 延迟与成本更高 |
| 典型场景 | 订机票这类可分解为固定子任务的流程 | 开放式问题：Coding Agent 解决 SWE-bench、Computer Use、迭代研究 |

按“从简单到复杂”的推进顺序：单次 LLM 调用 → 工作流 → 自主 Agent；实践中两者常混合使用（n8n 同系统内既有工作流节点也有自主 Agent 节点）。

护栏按防护位置分三类：

| 位置 | 机制 |
|---|---|
| 输入侧 | 相关性分类器、安全分类器（越狱 / 提示注入）、内容审核、基于规则的保护（黑名单、长度限制、正则过滤器） |
| 执行侧 | 工具风险评级：按可逆性、权限等级、财务影响标注低 / 中 / 高，高风险需额外审查或人工确认 |
| 输出侧 | PII 过滤器（身份证号、手机号等）、输出验证（内容与品牌价值一致） |

注意越狱与提示注入的区别：越狱是用户自己试图绕过模型安全限制；提示注入是攻击者通过外部数据（网页内容、文档）间接操纵模型行为。护栏评估必须双向测试——既要测拦截率，也要测合法请求的通过率（误拒绝）。

人工干预的两种触发条件：超过失败阈值（重试或操作次数上限）、涉及敏感 / 不可逆 / 高风险操作（在团队建立足够可靠性信心之前都应触发人工监督）。
